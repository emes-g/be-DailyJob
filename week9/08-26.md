## 작업 과정에서 어려웠던 점 & 배운 점
### QA
해커톤 3일차가 되었다. 당장 19시에 코드 프리즈가 예정되어 있었기 때문에, 어떻게든 개발을 마무리해야 하는 하루였다.

오늘의 작업은 크게 3가지였는데, 그중에서도 QA가 가장 기억에 남는다.
1. 담당 페이지 구현
2. FE/BE 연동
3. QA

문제를 해결하는 것 자체도 쉽지는 않지만, 그에 앞서 수많은 테스트 시나리오부터 상정해야 했기 때문이다. 가령,
- 이미 정산이 완료된 프로필로 접속하는 경우
- 같은 프로필로 여러 클라이언트가 접속하는 경우
- 이미 사진 업로드를 마친 상황에서, 뒤로가기를 통해 다시 사진 업로드 페이지로 돌아간 경우
- 팀 정산을 앞둔 상태에서, 개인 정산을 수정하려고 하는 경우
- ...

또한, 문제가 발견됐다고 해서 무작정 고치려고 해서는 안 됐던 것도 기억에 남는다. 가령,
- 문제라고 생각했지만, 알고 보니 내가 기획을 잘못 이해한 상황일 수 있다.
- 반대로 기획에서 고려하지 못한 문제가 발견될 수도 있다.
- ...

QA 과정을 거치면서, 다른 직군인 기획 팀원들과의 적극적인 소통 또한 중요하다는 사실을 깨닫게 되었다.

나아가, 다른 직군과 소통할 때는 상황을 더 간단명료하게 설명해야 한다는 깨달음도 얻을 수 있었다.

BE가 기획/디자인 업무까지 수행했던 메인 프로젝트에서는 크게 생각지 못했는데, 이번 해커톤에서는 기획 팀원이 추가됨에 따라 실감할 수 있는 부분이었다.

# 2. 종합 회고
## 잘한 점
### 주도적인 문제 해결
- QA 과정에서 맞닥뜨린 문제를 여러 방면에서 생각하려고 노력했다. 가령,
  - 구체적으로 어떠한 상황에서, 왜 발생하는지 (재현 가능한지)
  - 기획 의도와 정말 다른 것인지, 아니면 내가 잘못 이해한 것인지
  - 어떤 해결 방안들이 있고, 특정 방안을 도입하게 됐을 때 다른 코드에 영향이 갈 수도 있는지
  - ...
- 단순히 에이전트에게 '이러한 문제가 있으니까 해결해 줘'라고 하면 해결이야 되겠지만, 개발자로서는 적절하지 않은 태도라고 생각했기 때문이다.
  - 본인이 성장할 수도 없고, 다른 팀원들이 질문했을 때 대답조차 할 수 없다.
- 그래서 문제를 무작정 해결하려고 하기보다는, 발생 원인, 문제 여부, 해결 방안 및 근거 등 다양한 관점에서 해당 상황을 이해하려고 노력했는데, 이러한 점이 좋았다고 생각한다. 

## 아쉬웠던 점
### 일일 회고가 밀렸다
- 소프티어 교육 과정에서 매일 지켜왔던 원칙 중 하나가 '일일 회고를 밀리지 않는 것'이었다.
- 일일 회고를 당일에 진행하지 않으면, 당시의 생각이나 감정도 상당 부분 잊어버릴 뿐 아니라 회고 소요 시간 또한 증가하기 때문이다.
- 하지만 며칠 동안 제대로 된 수면 시간을 확보하지 못했고, 이로 인해 내일 부스에 차질이 생길 수도 있겠다고 생각하여 오늘은 당일 회고를 작성하지 않았다.
- 합당한 사유가 있었지만, 회고가 밀렸다는 사실 자체는 아쉽다.

## 개선할 점
### 키워드만이라도 적어두기
- 집 근처 버스가 끊겨서, 역에서부터 집까지 걸어가는 순간이 있었다.
- 당시 노래를 들으면서 귀가했는데, 그때 회고에 작성할 핵심 키워드만이라도 적어두면 어땠을까 싶다.

# 3. 학습 내용
## 패키지 매니저
- Node.js 환경에서 외부 라이브러리(의존성)를 관리하고 프로젝트 스크립트를 실행하는 도구다. 
- 백엔드의 Gradle, Maven과 동일한 역할을 수행한다.

### npm (Node Package Manager)
- **기본 구조:** 
  - Node.js 설치 시 기본 제공되는 패키지 관리자다.
- **의존성 저장 방식 (Flat 구조):** 
  - `node_modules` 디렉토리에 의존성을 평평하게(Flat) 설치하여 중복을 줄이려 하지만, 프로젝트마다 동일 라이브러리를 중복 다운로드하므로 디스크 용량을 많이 차지한다.
- **유령 의존성 (Phantom Dependency):** 
  - `package.json`에 직접 명시하지 않은 서브 의존성 모듈을 코드에서 직접 `import`해 사용할 수 있는 구조적 문제가 존재한다.

### pnpm (Performant npm)
- **하드 링크 & 심볼릭 링크 기반:** 
  - 전역 저장소(Global Content-addressable Store)에 패키지를 1회만 다운로드하고, 각 프로젝트의 `node_modules`에는 하드 링크 및 심볼릭 링크(Symlink)로 연결한다.
- **디스크 공간 절약:** 
  - 여러 프로젝트에서 동일 버전의 라이브러리를 공유하므로 중복 저장을 방지한다.
- **빠른 설치 속도:** 
  - 캐시 및 링크 구조 덕분에 npm 및 yarn classic 대비 설치 속도가 대폭 향상된다.
- **유령 의존성 차단:** 
  - 엄격한 디렉토리 분리(Strict node_modules layout)를 적용하여 `package.json`에 명시된 의존성만 참조할 수 있도록 강제한다.

## Orval
### 개념
- OpenAPI(Swagger) 명세서를 기반으로 TypeScript 타입 정의, API 클라이언트 함수, React Query 훅을 자동 생성해 주는 코드 생성 도구다.

### 동작 방식
- 백엔드(Spring Boot)에서 생성한 OpenAPI Specification(`swagger.json` 또는 `yaml`)을 읽어 프론트엔드용 TypeScript 인터페이스와 API 호출 로직을 생성한다.

### 특징
- **Type-Safe API 연동:** 백엔드 DTO 및 엔드포인트 변경 시 프론트엔드 타입이 자동으로 동기화되어 컴파일 타임에 오류를 감지한다.
- **TanStack Query 코드 자동 생성:** 단순 API 호출 함수뿐만 아니라 `useQuery`, `useMutation` 훅까지 규격에 맞춰 자동 생성한다.

## TanStack Query (React Query)
### 개념
- 서버 상태(Server State) 관리 및 비동기 데이터 페칭(Fetching), 캐싱, 동기화를 담당하는 라이브러리다.
- 클라이언트 상태(UI 토글, 폼 입력값 등)와 서버 상태(DB 데이터)를 분리하여 관리한다.

### 주요 기능
- **선언적 데이터 패칭:** 
  - `isLoading`, `isError`, `data` 등의 상태를 자동으로 관리하여 보일러플레이트 코드를 줄인다.
- **캐싱 및 무효화 (Invalidation):** 
  - `staleTime`과 `gcTime`(구 cacheTime)을 기반으로 데이터를 캐싱하며, 쓰기 작업(Mutation) 후 `queryClient.invalidateQueries()`를 통해 최신 데이터를 다시 조회한다.
- **자동 리페칭 (Refetching):** 
  - 네트워크 재연결, 윈도우 포커스 전환 등의 트리거 발생 시 최신 데이터를 자동으로 동기화한다.
- **낙관적 업데이트 (Optimistic Updates):** 
  - 서버 응답 전에 UI를 먼저 갱신하고, 실패 시 롤백하는 기능을 지원한다.

## 기술 스택 간 연계 흐름
```text
[Spring Boot (REST API)]
        │
        ▼ (OpenAPI / Swagger 명세서 노출)
   [Orval Generator]
        │
        ├─ TypeScript DTO (타입 정의)
        └─ TanStack Query Hooks (useQuery, useMutation)
        │
        ▼
[React App (pnpm 환경)] ── TanStack Query로 서버 상태 캐싱 및 UI 렌더링
```
- **개발 생산성:** 
  - 백엔드 컨트롤러/DTO 수정 후 명세서 갱신 시, 프론트엔드는 Orval 빌드 명령어 한 번으로 API 연동 코드와 캐싱 훅을 일괄 동기화한다.
- **안정성:** 
  - 백엔드 API 변경에 따른 런타임 타입 불일치 오류를 프론트엔드 빌드 단계에서 사전에 차단한다.
