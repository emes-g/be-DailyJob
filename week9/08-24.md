## 작업 과정에서 어려웠던 점 & 배운 점
### 현재 할 수 있는 일을 하기
메인 프로젝트가 끝나고, 해커톤이 시작되었다.

메인 프로젝트와 달리, 해커톤은 3일간 기획 파트원들과 함께 진행하게 된다.

BE로만 구성되지 않은 점은 좋았으나, 3일이라는 시간이 정말 순식간에 지나갈 것 같다는 예감이 들었다.

그래서 기획 파트원 분들이 기획을 해주시는 동안, 우리 BE는 현재 할 수 있는 일에 집중하기로 했다. 가령,
- 코드 컨벤션
- 개발 프로세스 논의
- AWS 인프라 세팅
- CI/CD
- ...

기획이 확정되지 않아도 할 수 있는 일들을 찾아보니, 생각보다 할 것이 많았다.

내일 점심시간 전에 기획을 받기로 했는데, 만약 그때까지 기다리기만 하고 있었다면 어땠을까?

안 그래도 촉박한 시간이 더욱 부족해져서, 새우지 않았어도 될 밤을 새웠을지도 모른다. 여기서 끝나면 그나마 다행인데, 이는 결국 컨디션 난조로 이어져 다음 날의 프로젝트 진행에도 영향을 미쳤을 것이다.

현재 할 수 있는 일에 집중한 덕분에, 내일은 오롯이 개발에 집중할 수 있게 되었다.

업무를 수동적으로 기다리기보다, 지금 할 수 있는 업무를 찾아 나서는 태도는 앞으로도 유지하고 싶다.

# 2. 종합 회고
## 잘한 점
### 익숙하지 않은 작업 담당하기
- 메인 프로젝트에서 맡지 않았던 업무인 CI/CD를 자원했다. 이유는 크게 두 가지였다.
  1. 익숙하지 않은 업무를 피하기만 해서는 성장할 수 없다.
  2. 내가 익숙한 업무를 다른 팀원이 맡게 되는 구조이므로, 해당 팀원이 막히는 부분에 대해서 알려줄 수 있다. 이 과정에서 두 사람 모두 성장하게 된다.
- 실제로 오늘 팀원으로부터 AWS 인프라 세팅 중 '팀원들이 인스턴스에 접속하게 하기 위해서는 어떻게 해야 하냐'는 질문을 받게 되었고, 이에 개별 공개키 등록 방식에 대해 알려줄 수 있었다.
- 교육 과정인 것도 한몫했지만, 새로운 업무에 도전하려는 태도는 앞으로도 유지하고 싶다.

## 아쉬웠던 점
### 장황하게 설명하기
- 상대방의 질문에 대한 답변 내용은 정했으나, 말이 정돈되지 않아 장황하게 설명할 때가 있다.
- 처음 의식한 이래로 줄이긴 했으나, 여전히 종종 이러한 경우가 발생하는 것 같아 아쉽다.

## 개선할 점
### 당장 말해야 한다는 부담 내려놓기
- 빠르게 전달하면 좋겠다는 생각에 정돈되지 않은 말을 뱉으면, 결국 혼란만 가중시키고 작업이 더욱 지연될 수 있다.
- 머릿속에서 답변 내용을 정하는 것과 이를 상대방에게 명확히 전달하는 것은 엄연히 다른 영역이다.
- 당장 말해야 한다는 부담을 내려놓고, 상대방이 명확히 이해할 수 있도록 답변을 구성하는 것부터 우선하자.

# 3. 학습 내용
## GitHub Actions
### Workflow
- **개념:** 
  - `.github/workflows/` 아래에 있는 YAML 파일 하나가 워크플로 하나다. 
  - `push`, `pull_request`, `schedule` 같은 특정 이벤트가 발생하면 실행된다.
- **특징:** 
  - 워크플로 하나는 여러 Job으로 구성된다. 
  - `needs`로 순서를 지정하지 않는 한, Job들은 기본적으로 병렬로 실행된다.

### Job
- **개념:** 
  - 워크플로 안에서 하나의 실행 단위다. 
  - 여러 Step으로 구성된다.
- **runs-on + steps:** 
  - 일반적인 Job은 `runs-on`으로 어떤 환경(runner)에서 돌릴지 지정하고, 그 아래 `steps` 목록을 순서대로 실행한다.
- **uses(Job 레벨):** 
  - Job 자체가 다른 워크플로(재사용 가능한 워크플로, reusable workflow)를 통째로 호출할 때 쓴다.

```yaml
jobs:
  call-shared:
    uses: org/repo/.github/workflows/shared.yml@main
```
- **차이:** 
  - `runs-on + steps`는 이 Job이 직접 스텝을 실행하겠다는 뜻이고, `uses`는 이 Job이 스텝 없이 다른 워크플로 전체를 그대로 가져와 실행하겠다는 뜻이다. 
  - 하나의 Job은 이 둘 중 하나만 쓸 수 있다.

### Step
- **개념:** 
  - Job 안에서 실제로 실행되는 가장 작은 단위다. 
  - 순서대로 하나씩 실행된다.
- **run:** 셸 명령어를 직접 실행한다.
```yaml
steps:
  - run: ./gradlew build
```

- **uses(Step 레벨):** 다른 사람이 미리 만들어둔 재사용 가능한 액션(Action)을 가져다 실행한다.
```yaml
steps:
  - uses: actions/checkout@v4
```

- **차이:** 
  - `run`은 "이 명령어를 셸에서 그대로 실행해라"이고, `uses`는 "이미 자바스크립트나 도커 컨테이너로 패키징된 재사용 로직을 가져다 실행해라"다. 
  - 예를 들어 `actions/checkout@v4`는 단순한 `git clone` 한 줄이 아니라, PR 체크아웃, 서브모듈, sparse checkout 같은 여러 옵션을 캡슐화한 액션이다.

### 요약

| | run / runs-on+steps | uses |
|---|---|---|
| Job 레벨 | runs-on으로 실행 환경을 지정하고 steps 목록을 실행한다 | 다른 워크플로 전체를 호출한다(reusable workflow) |
| Step 레벨 | 셸 명령어를 직접 실행한다 | 재사용 가능한 액션 하나를 실행한다 |

## GitHub Actions Runner
- **개념:** 
  - 워크플로의 `run:`, `uses:` 스텝을 실제로 실행해주는 컴퓨터(에이전트)다.
- **GitHub-hosted runner:** 
  - 기본값(`runs-on: ubuntu-latest`)이다. 
  - 워크플로가 실행될 때마다 GitHub이 새로 만들어주는 임시 가상머신이고, 실행이 끝나면 통째로 삭제된다. 
  - 배포 대상 서버와는 완전히 별개의 컴퓨터다.
- **Self-hosted runner:** 
  - GitHub이 주는 임시 VM 대신, 직접 가진 서버를 runner로 등록해서 쓰는 방식이다. 
  - 그 서버에 GitHub이 제공하는 에이전트 프로그램을 설치하면, 그 서버는 "GitHub이 작업을 지시할 때까지 대기하는 워커"가 된다. 
  - `runs-on: self-hosted`로 지정하면 그 스텝들이 임시 VM이 아니라 등록해둔 그 서버 안에서 직접 실행된다.

### Self-hosted runner를 쓰는 이유
- **GitHub-hosted + SSH 방식:** 
  - 워크플로는 여전히 GitHub의 임시 VM에서 돌고, 그 VM이 배포 대상 서버로 SSH 접속해서 명령을 대신 실행시킨다. 
  - 이때 SSH 프라이빗 키를 GitHub Secrets에 올려둬야 한다.
- **Self-hosted runner 방식:** 
  - 워크플로 자체가 이미 배포 대상 서버 안에서 돌고 있으니, "jar를 복사한다"는 스텝이 그냥 그 서버의 로컬 파일시스템에서 일어나는 평범한 `cp` 명령이 된다. 
  - 외부에서 그 서버로 접속할 필요 자체가 없어서 SSH 키가 전혀 필요 없다.

## 데몬 (Daemon)
- **개념:** 특정 터미널 세션에 딸려 있지 않고, 백그라운드에서 독립적으로 계속 돌아가는 프로세스다.
- **배경:** 
  - SSH로 접속해서 `java -jar app.jar`를 그냥 실행하면, 그 프로세스는 그 SSH 세션의 자식 프로세스가 된다. 
  - SSH 연결을 끊으면 부모 세션이 죽으면서 이 프로세스도 같이 죽는다.
- **왜 필요한가:** 
  - SSH 연결이 끊겨도, 서버가 재부팅해도 계속(또는 재부팅 시 다시) 떠 있는 서버 프로세스가 필요한데, 그게 데몬이다.

## systemd
- **개념:** 
  - 리눅스가 부팅될 때 가장 먼저 뜨는 프로세스(PID 1)이자, 그 뒤로 뜨는 모든 백그라운드 서비스(데몬)를 관리하는 매니저다.
- **특징:** 
  - 서비스를 등록해두면 서버 부팅 시 자동 시작, 프로세스가 죽으면 자동 재시작, 로그를 표준화된 방식으로 수집(`journalctl`로 조회), 시작/중지/재시작을 표준 명령어로 통일해서 처리해준다.
- **역할:** 
  - "우리 앱을 어떻게 데몬으로 만들지"를 표준화해주는 도구다.

### Unit 파일
- **개념:** 
  - systemd에게 "이 프로세스를 관리해줘"라고 등록하는 설정 파일이다. 
  - `/etc/systemd/system/myapp.service` 같은 경로에 둔다.

```
[Unit]
Description=My Spring Boot App
After=network.target

[Service]
ExecStart=/usr/bin/java -jar /home/ubuntu/app/app.jar
Restart=always
User=ubuntu

[Install]
WantedBy=multi-user.target
```

- **ExecStart:** 
  - 이 서비스를 시작할 때 실행할 명령어다. 
  - SSH로 직접 쳤던 `java -jar app.jar`가 여기 들어간다.
- **Restart=always:** 
  - 프로세스가 죽으면 systemd가 자동으로 다시 실행한다.
- **WantedBy=multi-user.target:** 
  - 서버 부팅 시 자동 시작 대상으로 등록한다.

## systemctl
- **개념:** systemd에게 명령을 내리는 CLI 도구다.
- **start / stop / restart:** 
  - 유닛 파일의 ExecStart 명령으로 프로세스를 시작, 종료, 또는 종료 후 재시작한다. 
  - 배포할 때 쓰는 건 restart다.
- **status:** 지금 떠 있는지, 최근 로그는 어땠는지 확인한다.
- **enable:** 서버 부팅 시 자동 시작되도록 등록한다(최초 1번만 하면 된다).

## Self-hosted Runner 방식의 배포 흐름
### 사전 준비 (서버에서 최초 1번)
- GitHub 저장소 Settings → Actions → Runners에서 나오는 설치 스크립트를 서버에서 실행해 self-hosted runner로 등록한다.
- `myapp.service` 유닛 파일을 작성하고 `systemctl enable`로 등록한다.
- 필요하면 앱 디렉터리, 환경변수, 시크릿 값을 서버에 미리 준비해둔다.

### 배포가 실행될 때마다 (워크플로 안에서)
1. 새로 빌드된 jar를 다운로드한다.
2. `cp {새로운 jar} /home/ubuntu/app/app.jar`로 로컬 파일을 덮어쓴다.
3. `sudo systemctl restart myapp.service`로 기존 프로세스를 내리고 새 jar로 재기동한다.

### 동작 원리
- app.jar 경로는 그대로 두고 파일 내용만 새 jar로 덮어쓴 다음 재시작하기 때문에, systemd 입장에서는 그냥 같은 명령을 다시 실행하는 것뿐인데 결과적으로 새 버전이 뜨는 것이다.
