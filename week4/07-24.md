그 어느 때보다도 파란만장했던 한 주가 지나갔다.

기획, 디자인, FE, BE, AI, 데이터, 인프라, 협업 기술까지 정말 다루지 않은 영역이 없었고, 프로젝트 또한 기존과는 전혀 다른 방식으로 진행되었다.

지금까지의 프로젝트는 페어 프로그래밍을 통한 깊은 이해를 바탕으로 진행되었다면, 이번 프로젝트는 굉장히 속도감 있게, 한 겹 한 겹은 얕지만 층층이 쌓여 가는 구조로 진행되고 있다.

속도, 깊이, 업무 그 무엇 하나 익숙하지 않지만, 이번 프로젝트에서만큼은 새로운 흐름에 타보고 싶어졌고, 그렇게 할 계획이다.

언제까지나 익숙한 일만, 익숙한 방식으로 진행할 수는 없다. 

아니, 정확히 할 순 있지만 그래서는 성장할 수 없다. 기회가 왔을 때 경험하고 적응해 둔다면, 실무에서 언제, 어떤 업무를, 누구와 진행하게 되더라도 한결 편한 마음으로 임할 수 있을 것이다.

낯설다고, 잘하지 못한다고 피하게 되면 어느 순간 정체되기 마련이다. 현재에 안주하지 말고, 도전하는 태도를 유지하자.

# 2. 종합 회고
## 잘한 점
### 익숙하지 않은 업무에 자원하기
- AWS 인프라 환경 세팅, FE 디렉터리 구조 결정 등 익숙하지 않은 업무를 자원해서 수행했다.
- 백엔드 개발자라고 해도, 백엔드 업무에 국한되지 않고 프로젝트 전체 개발 프로세스에 대한 이해를 갖추는 것이 좋겠다고 생각했기 때문이다. 
- 낯선 분야를 두려워하지 않고 적극적으로 도전하려는 자세는 앞으로도 유지하고 싶다.

## 아쉬웠던 점
### 답장 시간이 너무 늦어졌다
- 팀에서 프로젝트를 진행하다 보면 구두가 아니라, 글로 의견을 제시하는 경우도 많다.
- 이러한 경우에는 코멘트 역시 글로 달릴텐데, 완벽하게 답장하려는 과정에서 속도가 많이 지체되었던 것 같다.
- 여러 일을 병렬적으로 처리해야 하기 때문에, 완벽을 추구한다면 우선순위에 따라 코멘트 답변은 기약없이 밀려날 수 있다.

## 개선할 점
### 유연하게 답장하자
- 완벽하게 답장하려 하면, 그만큼 응답 속도가 늦어진다.
- 새로 발행하는 글이 아니라, 티키타카가 필요한 경우에는 답변의 속도가 더욱 중요할 수 있다.
- 매번 답장을 완벽하게 보내려고 하기보다는, 현재 상황에 적합한 구성은 무엇일지부터 고민해보자.

# 3. 학습 내용
## AWS NAT
### NAT Gateway
- AWS에서 인프라를 프로비저닝하고 운영을 대신해 주는 완전 관리형(Managed) 서비스다.
- **운영 편의성 최적화:** 
  - 사용자는 단순히 서브넷에 NAT Gateway를 생성하고 라우팅 테이블에 연결하기만 하면 된다. 
  - 그 외의 운영체제 관리, 스크립트 작성, 보안 패치 작업이 전혀 필요하지 않다.
- **성능과 안정성 보장:** 
  - 기본적으로 최대 45Gbps의 대역폭을 지원하며, 트래픽이 폭증하면 최대 100Gbps까지 자동으로 성능을 확장한다. 
  - 또한 가용 영역(AZ) 내에 장애가 발생하더라도 AWS 측에서 이중화된 시스템을 통해 서비스를 지속한다.

### NAT 인스턴스
- 사용자가 직접 EC2 인스턴스를 하나 띄우고, 그 위에 NAT 역할을 수행하는 소프트웨어(예: iptables 등)를 설정하여 네트워크 트래픽을 중계하도록 만든 가상 서버다.
- **높은 관리 오버헤드:** 
  - 말 그대로 일반적인 EC2 서버이기 때문에 NAT 라우팅 설정, 보안 그룹 규칙 지정, 네트워크 라우팅 기능 활성화(IP 포워딩, 마스커레이딩) 등의 작업을 개발자가 직접 수행해야 한다.
    - **IP 포워딩:** OS 내부에서 패킷을 전달
    - **마스커레이딩:** 사설 IP를 공인 IP로 변환
  - 특히 프라이빗 서브넷의 트래픽이 방금 만든 NAT 인스턴스(EC2 서버)를 거쳐 나갈 수 있도록 하기 위해서는, '소스/대상 확인'을 비활성화한 후 라우팅 테이블을 수정해야 한다.
- **성능의 한계와 병목:** 
  - 해당 EC2 인스턴스 타입이 지원하는 네트워크 대역폭(예: `t3.micro`의 경우 최대 5Gbps)에 성능이 묶인다. 
  - 인프라 규모가 커져서 처리해야 할 트래픽이 인스턴스의 한계를 넘어서면 병목 현상이 발생한다.
- **활용 환경:** 
  - 유지보수에 공수가 들더라도 매우 저렴한 EC2(예: `t4g.nano` 등)를 활용해 극단적으로 비용을 절감해야 하는 토이 프로젝트 환경 
  - 프록시 설정 및 커스텀 포트 포워딩 등 일반적인 NAT 기능 이상의 세밀한 네트워크 제어가 필요한 경우

## 키 페어
### 개념
- 키 페어(Key Pair)는 공개 키 암호화 방식을 사용하여 EC2 인스턴스에 안전하게 접속(SSH)하기 위한 인증 수단이다. 
- AWS가 퍼블릭 키를 서버(EC2)에 저장하고, 사용자는 프라이빗 키 파일을 로컬 PC에 다운로드하여 접속할 때 자격 증명으로 사용하게 된다.

### 유형
- **ED25519:** 최신 타원 곡선 암호화 알고리즘으로, RSA보다 키 길이가 짧아 처리 속도가 빠르면서도 높은 보안성을 제공한다. 
- **RSA:** 전통적으로 가장 널리 사용되는 표준 암호화 알고리즘이다.

### 프라이빗 키 파일 형식
- **.pem:** 
  - OpenSSH 표준 형식으로, 별도의 프로그램 설치나 변환 없이 즉시 사용할 수 있어 편리하다.
- **.ppk:** 
  - 'PuTTY'라는 특정 원격 접속 프로그램에서만 전용으로 사용하는 형식이다.

## SSH (Secure Shell)
### 개념
- 네트워크 상에 떨어진 다른 컴퓨터(주로 서버)에 원격으로 로그인하거나 운영체제 명령을 실행하기 위해 사용하는 네트워크 통신 프로토콜(규약)이다. 
- 통신을 위해 기본적으로 22번 포트를 사용한다.

### 특징
- **원격 제어 목적:**
  - 클라우드 데이터 센터에 있는 서버에 물리적인 키보드나 모니터를 연결할 수 없으므로, 관리자는 자신의 로컬 PC에서 SSH 클라이언트를 사용하여 원격 서버의 CLI(명령줄 인터페이스) 환경에 접속하여 서버를 구성하고 제어한다.
- **강력한 암호화 (Secure):** 
  - 과거에 원격 제어용으로 사용되던 텔넷(Telnet)과 같은 프로토콜은 명령어와 비밀번호를 암호화 없이 평문으로 전송하여 중간에서 데이터를 탈취당할 위험이 컸다. 
  - 반면 SSH는 클라이언트와 서버 간에 오가는 모든 데이터를 암호화하여 통신의 기밀성과 무결성을 보장한다.
- **키(Key) 기반 인증:** 
  - 단순한 비밀번호 입력 외에도, 암호학적 구조로 이루어진 한 쌍의 키(퍼블릭 키, 프라이빗 키)를 사용하여 안전하게 사용자를 인증하는 방식을 지원한다. 
  - AWS EC2 인스턴스를 생성할 때 다운로드하는 키 페어(.pem 등)가 바로 이 SSH 원격 접속을 증명하기 위한 보안 파일이다.

### 권한 설정 관련 이슈
```text
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

Permissions 0644 for '{pem 키 경로}' are too open.

It is required that your private key files are NOT accessible by others.

This private key will be ignored.

Load key "{pem 키 경로}": bad permissions

ubuntu@{IP Address}: Permission denied (publickey).
```
- 로그에 표시된 `Permissions 0644 ... are too open`이라는 문구는 현재 pem 키 파일이 시스템의 다른 사용자도 읽을 수 있는 상태(권한 0644)로 설정되어 있다는 뜻이다. 
- SSH는 보안상 프라이빗 키가 파일의 소유자 본인만 읽을 수 있는 상태(권한 400)일 때만 해당 키의 사용을 허용한다.

### 예시 (인바운드 규칙으로 SSH 22번 포트를 연 상황)
- 방화벽(보안 그룹 등)의 인바운드 규칙에 'SSH / 22번 포트 / 허용'을 추가한다는 것은, 현재 서버가 외부로부터 22번 포트를 통해 들어오는 통신 연결을 수락할 상태가 되었음을 의미한다.
- 이러한 상황에서 외부의 컴퓨터(예: 관리자의 개인 PC)가 현재 서버의 IP 주소와 22번 포트를 목적지로 지정하여 접속 요청을 보내면, 서버의 방화벽은 이를 차단하지 않고 통과시킨다.

## 인바운드와 아웃바운드
### 인바운드
- 외부 환경에서 현재 서버 내부로 들어오는 트래픽이다.
- **인바운드 규칙:** 외부의 클라이언트나 다른 서버가 현재 서버로 접근하여 요청을 보내는 것을 허용할지 제어한다.

### 아웃바운드
- 현재 서버에서 외부 환경으로 나가는 트래픽이다.
- **아웃바운드 규칙:** 현재 서버가 외부 인터넷 API를 호출하거나 다른 서버로 데이터를 전송(발신)하는 것을 허용할지 제어한다.

## SSH 키 관리 및 원격 서버 접속 전략
### 종류 
- **WAS 서버에 PEM 키 직접 저장 방식:**
  - 중간 서버(Bastion Host 등)나 WAS 서버 자체에 타겟 서버로 가기 위한 비밀키(.pem)를 물리적으로 저장해두고 접속하는 방식이다.
  - **단점:** 서버가 해킹당하면 비밀키도 함께 유출되므로 보안상 매우 위험하다.
- **SSH 에이전트 포워딩 방식:**
  - 내 로컬 컴퓨터의 SSH 에이전트에 키를 등록해두고, 중간 서버를 거칠 때 내 로컬의 인증 권한을 전달(포워딩)하여 타겟 서버에 접속하는 방식이다.
- **프록시 점프 방식:**
  - 중간 거점 서버(Bastion Host)를 단순히 네트워크 통로(프록시)로만 사용하고, 내 로컬 컴퓨터에서 타겟 서버로 직접 종단 간(End-to-End) 암호화 연결을 맺는 방식이다.
  - 우리 프로젝트를 예시로 들면, 로컬 PC가 경유지(WAS)를 통해 목적지(DB)로 연결할 때, 경유지는 단순히 데이터 통로(TCP 터널) 역할만 수행하고 실제 SSH 암호화 통신과 인증은 로컬 PC와 목적지 DB 서버가 직접 수행하는 방식을 의미한다.

### 에이전트 포워딩 방식 vs 프록시 점프 방식
- 두 방식 모두 로컬 PC의 프라이빗 키 파일(.pem)을 외부 서버(WAS)에 복사하지 않는다는 장점이 있지만, 내부적인 보안 메커니즘에서 큰 차이가 있다.
- **세션 가로채기(Hijacking) 위험성:** 
  - 에이전트 포워딩은 연결이 유지되는 동안 WAS 서버 내부에 임시 인증 소켓을 생성한다. 
  - 만약 WAS 서버가 해킹당해 최고 관리자(root) 권한이 탈취되면, 해커가 이 열려있는 소켓을 가로채어 DB 서버로 무단 접근할 수 있는 보안 취약점이 존재한다. 
  - 프록시 점프는 이러한 인증 소켓 자체를 공유하지 않으므로 가로채기 위험이 원천적으로 차단된다.
- **통신 암호화 구간:** 
  - 프록시 점프는 로컬 PC부터 DB 서버까지 하나로 이어진 종단 간 암호화(End-to-End Encryption)가 적용된다. 
  - WAS 인스턴스는 지나가는 데이터가 어떤 내용인지 전혀 해독할 수 없다. 
- **설정 편의성:** 
  - 에이전트 포워딩은 로컬 환경에서 별도의 백그라운드 서비스(ssh-agent)를 실행하고 키를 등록하는 선행 작업이 필요하다. 
  - 반면 프록시 점프는 최신 OpenSSH 클라이언트에서 명령어 옵션(-J) 하나로 즉시 실행이 가능하다.
- 결론적으로 프록시 점프(ProxyJump) 방식을 사용하는 것이 권장된다. 
  - 에이전트 포워딩은 과거에 주로 사용되던 방식이며, 현재 실무 인프라 환경에서는 보안성이 훨씬 뛰어난 프록시 점프 방식이 표준으로 사용된다.

# 4. 주간 프롬프트 회고
### 1. 내가 최종 선택한 가장 잘 작성했다고 생각하는 프롬프트
원본 프롬프트:
```text
다음의 요소들을 활용해서 AWS 인프라 환경을 구축하려고 해.
- VPC: Region 내 논리적인 영역 (10.0.0.0/16)
- Subnet: Private, Public 각각 1대씩, 총 2대
- EC2: Private 서브넷에는 DB(MySQL 8.4)용 인스턴스 1대(micro), Public 서브넷에는 WAS(Java 21)용 인스턴스 1대(micro)와 NAT 인스턴스 1대(nano)
- Security Group: EC2 레벨에서의 가상 방화벽으로 디폴트로 모두 닫혀있기 때문에 요청을 받을 특정 포트는 별도로 열어줘야 함. 서브넷 레벨에서의 방화벽인 NACL과 구분되는 특징임.
- IGW: VPC 인바운드/아웃바운드 요청을 처리하기 위함
- Routing Table: 각 서브넷에 연결할 라우팅 테이블

1. 이해하고 있는 바가 틀렸거나 누락된 항목이 있다면 보완해줘.
2. 인스턴스를 micro, nano 등으로 뭉뚱그렸는데, t4g나 t3 중에 선택해야 해. Java 21, MySQL 8.4 환경에 적합한 인스턴스들을 추천해줘.
```

**선택한 이유:**
- 단순히 "AWS 인프라 구축 방법을 알려달라"고 포괄적으로 질문하지 않고, 내가 설계한 아키텍처 구성 요소(VPC, Subnet, EC2, SG 등)와 각 요소에 대한 이해도를 먼저 구체적으로 제시하여, AI가 처음부터 설계도를 짜는 대신 배경 지식을 검증하고 보완하는 데 집중할 수 있도록 유도했다. 
- 기술 스택(Java 21, MySQL 8.4)과 인스턴스 후보군(t3, t4g)을 상황에 적합한 인스턴스를 제시할 수 있도록 유도했다.

### 2. 원본 프롬프트 구조 분석
- **문제 상황:**
  - AWS 인프라 환경을 직접 구축하기 위해 네트워크 및 컴퓨팅 아키텍처를 설계하고 이를 검증받아야 하는 상황이다. 
  - 또한, 구성할 서비스에 맞춰 최적의 인스턴스 타입을 결정해야 한다.
- **원하는 결과를 어떻게 요구했는가:**
  - 번호(1, 2)를 매겨 요구사항을 명확히 분리했다. 
  - 1번에서는 내가 이해한 아키텍처 개념 중 오개념이나 누락된 항목에 대한 팩트 체크를 요구했고, 2번에서는 특정 소프트웨어 구동을 위한 인스턴스 타입 추천을 요구했다.
- **필요한 맥락이 포함되어 있는가:**
  - VPC 대역(10.0.0.0/16), 서브넷의 개수 및 역할(Public/Private), 각 EC2의 용도(DB, WAS, NAT) 및 사용될 핵심 소프트웨어 버전(Java 21, MySQL 8.4) 등 인프라 설계에 필요한 구체적인 네트워크 및 스펙 맥락이 적절하게 포함되어 있다.
- **판단 기준이나 제약 조건이 있는가:**
  - 인스턴스 타입을 추천받을 때, 무작위 추천이 아닌 't4g(ARM)나 t3(x86) 중에서'라는 명확한 후보군 제약 조건을 설정했다.
- **출력 방식이 명확한가:**
  - 출력 형식을 특정(마크다운, 표 등)하지는 않았으나, 질문을 1, 2번으로 넘버링하여 AI 역시 각 번호에 맞춰 구조화된 형태로 답변을 출력하도록 유도했다.
- **나의 가설, 우려, 의도가 드러나는가:**
  - Security Group을 설명하며 NACL과의 차이점을 명시해 방화벽 동작에 대한 올바르게 이해하고 있는지 확인받았다. 
  - 또한 인스턴스를 선택할 때 아키텍처(ARM vs x86)에 따라 Java 21 및 MySQL 8.4 환경에서의 호환성이나 성능 차이가 있을 수 있다는 우려와 의도가 잘 나타나 있다.

- 프롬프트 개선안
```text
다음의 요소들을 활용해서 AWS 인프라 환경을 구축하려고 합니다. 현재 설계한 아키텍처 구성은 다음과 같습니다.

[인프라 구성 요소]
- VPC: Region 내 논리적인 영역 (10.0.0.0/16)
- Subnet: Private, Public 각각 1대씩, 총 2대
- EC2: 
  - Private 서브넷: DB(MySQL 8.4)용 인스턴스 1대
  - Public 서브넷: WAS(Java 21)용 인스턴스 1대, NAT 인스턴스 1대
- Security Group: EC2 레벨에서의 가상 방화벽 (기본 차단이므로 특정 포트 허용 필요, 서브넷 레벨의 NACL과 구분됨)
- IGW: VPC 인바운드/아웃바운드 요청 처리
- Routing Table: 각 서브넷에 연결할 라우팅 테이블

위 내용을 바탕으로 다음 두 가지 항목에 대해 답변해 주세요.

1. 아키텍처 검토 및 보완: 제가 작성한 개념 중 기술적으로 틀린 부분(오개념)을 정정해 주시고, 실제 환경 구축 시 누락되어 반드시 추가해야 할 요소(예: EIP(탄력적 IP) 등)가 있다면 그 이유와 함께 설명해 주세요.
2. 인스턴스 타입 추천: DB(micro), WAS(micro), NAT(nano) 용도로 t4g(ARM) 아키텍처와 t3(x86) 아키텍처 중 어떤 것이 더 적합할지, 'Java 21 및 MySQL 8.4의 호환성'과 '가성비'를 기준으로 비교 분석해 주세요. 최종 추천 결과는 표 형태로 정리해 주세요.
```

### 4. AI가 개선한 프롬프트 분석
- **더 명확해진 목표 및 출력 형식:** 
  - 최종 인스턴스 추천 결과를 '표 형태'로 정리해달라고 명시하여 답변의 구조화를 유도했다.
- **추가된 제약 조건:** 
  - 호환성뿐만 아니라, 가격 성능 대비라는 제약 조건이 추가되었다.
- **구체적 판단 기준 제시:**
  - 아키텍처 보완을 요청할 때 EIP와 같은 구체적인 예시가 함께 제공되었다.
  - 이를 통해 AI는 네트워크 라우팅 및 인프라 실무 관점에서 필요한 컴포넌트들을 어느 정도 깊이로 보완해줘야 할지에 대한 이해를 갖추게 되었다.
- **답변 품질이 좋아질 것으로 예상되는 이유:** 
  - 평가 기준이 추가되었기 때문에, AI가 t4g(ARM)와 t3(x86) 아키텍처 간의 차이점과 발생할 수 있는 이슈를 중심으로 심도 있는 리뷰를 제공할 수 있다. 
  - 결과적으로 현재 기술 스택에 보다 적합한 인프라 설계 가이드를 얻을 수 있게 되었다.
