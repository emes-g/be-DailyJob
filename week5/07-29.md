## 작업 과정에서 어려웠던 점 & 배운 점
### 담당 업무에 대한 책임감 갖기
어제 S3 및 CloudFront 배포 생성까지 진행했는데, 오늘 출근하고 보니 이후 작업이 완료되어 있었다.

관련하여 팀원에게 물어보니, 오늘 아침에 본인 작업을 처리하는 김에 겸사겸사 수행했다고 한다.

바로 다른 업무로 넘어갈 수도 있었겠지만, 기존 인프라 담당이 나였기 때문에 끝까지 책임을 지는게 맞다고 생각했다.

그래서 수행된 작업 내역을 봤는데, CloudFront 배포에서 WAS 인스턴스를 가리키는 오리진의 기본 포트가 8080번이 아니라 80번으로 잡혀 있는 문제를 발견할 수 있었다. 

오리진 기본 포트를 수정한 후, 이에 맞춰 WAS 보안 그룹의 인바운드 규칙도 편집해 해결하였다.

나아가 CloudFront 도메인에서 여러 테스트를 거치며 Default Root Object 설정과 사용자 정의 오류 응답을 추가하였는데, 그 과정에서 SPA를 S3, CloudFront로 서빙할 때의 동작 흐름 또한 학습할 수 있었다.

맡은 업무에 대한 책임감을 가져야 한다고 생각해 검토했을 뿐인데, 많은 부수 효과를 얻게 된 것이었다.

동료를 믿는 것도 중요하지만, 담당 업무는 본인이 책임감을 갖고 임해야 한다고 생각하게 된 경험이었다.

# 2. 종합 회고
## 잘한 점
### 프로젝트에만 열중하지 않았다
- 프로젝트 기간에도 수업, 실습 등 프로젝트 이외의 활동이 병행된다.
- 사실 프로젝트만 진행하기에도 시간이 넉넉하진 않지만, 정해진 시간만큼은 해당 활동에 전념하고 있다.
- 오늘 오전에는 실습과 수업이 각각 1시간씩 진행되었는데, 그 과정에서 인덱스에 대해 많은 것을 배울 수 있었다.
- 앞으로 더욱 시간에 쫓기겠지만, 배정된 시간만큼은 해당 활동에 몰입하는 태도를 유지하고 싶다.

## 아쉬웠던 점
### 프로젝트 개발에 착수하지 못했다
- 오늘 많은 작업을 수행하긴 했지만, 정작 프로젝트 개발에 착수하지는 못했다.
- 프로젝트 기간에도 수업이나 실습이 병행되므로 프로젝트에 할애 가능한 시간은 한정되어 있는데, 그 시간조차 온전히 개발에 활용할 수 없기 때문이다. 기획, 인프라, FE, 정기/비정기 회의, 산출물 검토, 자료 조사, 학습 등의 작업도 병렬적으로 수행해야 한다.
- 데드라인이 없거나 길다면 괜찮겠지만, 이제는 슬슬 개발을 시작해야 한다. 코드 프리즈까지 채 3주도 남지 않았다.

## 개선할 점
### 내일부터는 개발도 병행하자
- 프로젝트 전체를 보는 시야를 기르는 것도 좋지만, 내일부터는 본격적으로 개발을 시작하자.
- 어느 직무든 마찬가지겠지만, 결국 데드라인 준수를 최우선으로 해야 하기 때문이다.

# 3. 학습 내용
## 커버드 인덱스 (Covered Index)
### 핵심 개념
- 쿼리 처리에 필요한 모든 컬럼을 가지고 있는 인덱스를 의미한다.
- 쿼리의 `SELECT`, `WHERE`, `ORDER BY`, `GROUP BY` 등에 사용되는 모든 컬럼이 특정 인덱스에 포함된 상태를 말한다.

### 동작 원리 (Index-Only Scan)
- **일반적인 쿼리 실행:** 
  - 인덱스를 스캔하여 조건에 맞는 데이터의 위치를 찾은 후, 실제 테이블의 데이터 블록에 접근하여 나머지 컬럼 값을 읽어온다. 
  - 이 과정에서 디스크 랜덤 I/O가 발생한다.
- **커버드 인덱스 실행:** 
  - 쿼리에 필요한 모든 데이터가 이미 인덱스 내부에 존재한다. 
  - 따라서 실제 테이블 데이터 블록에 접근하는 과정을 생략하고, 인덱스 리프 노드의 데이터만 읽어서 결과를 바로 반환한다.

### 장점
- **디스크 I/O 대폭 감소:** 데이터 블록을 읽기 위한 랜덤 디스크 I/O가 전혀 발생하지 않는다.
- **쿼리 성능 향상:** 테이블 접근이 생략되고 메모리에 적재된 인덱스 블록만으로 처리가 완료되므로 조회 속도가 비약적으로 빨라진다.

### 단점 및 한계
- **인덱스 크기 증가:** 여러 컬럼을 인덱스에 포함시켜야 하므로 인덱스의 물리적인 크기가 커진다.
- **메모리 자원 소모:** 인덱스가 커짐에 따라 DB의 메모리(Buffer Pool)를 더 많이 차지하게 된다.
- **DML 성능 저하:** 데이터의 추가, 수정, 삭제 작업 시 무거운 인덱스를 함께 갱신해야 하므로 쓰기 성능이 저하된다.
- **적용 한계:** 모든 컬럼을 인덱스로 만들 수는 없기 때문에, `SELECT *` 와 같이 수많은 컬럼을 조회하는 쿼리에는 사실상 적용이 불가능하다.

### 적용 전략
- 시스템에서 호출 빈도가 매우 높고 성능 최적화가 필수적인 핵심 조회 쿼리에 제한적으로 설계한다.
- 조회 조건과 반환해야 할 컬럼의 수가 적은 쿼리를 타겟으로 설정한다.

## SameSite
### 핵심 개념
- 브라우저가 쿠키를 다른 사이트로 가는 요청에도 실어 보낼지 결정하는 쿠키 속성이다.
- 값은 `Strict`, `Lax`, `None` 세 가지로 나뉜다.

### Strict
- 같은 사이트에서 시작된 요청에만 쿠키를 싣는다.
- 다른 사이트의 링크를 눌러 처음 진입할 때도 쿠키가 실리지 않아, 로그인이 풀린 것처럼 보일 수 있다.

### Lax (브라우저 기본값)
- 다른 사이트에서 링크 클릭 등으로 페이지를 이동해 들어오는 요청에는 쿠키를 싣는다.
- 다른 사이트가 뒤에서 몰래 보내는 요청(이미지 태그, `fetch` 등)에는 쿠키를 싣지 않는다. 이 부분이 CSRF 방어로 이어진다.
- 프론트와 API가 같은 출처(CloudFront 단일 도메인 등)로 묶여 있으면 이 값으로 충분하다.

### None
- 어떤 요청이든(다른 출처로 가는 요청 포함) 쿠키를 싣는다.
- 대신 `Secure` 속성(HTTPS 전용)을 필수로 요구한다.
- 프론트와 API가 서로 다른 출처일 때만 필요한 설정이다.

## 캐시 무효화(Invalidation) vs 캐시 비활성화(CachingDisabled)
### 핵심 개념
- CachingDisabled는 특정 경로에 대해 CloudFront가 응답을 저장하지 않도록 미리 걸어두는 캐시 정책이다.
- Invalidation은 이미 캐시에 저장된 콘텐츠를 강제로 지우는 일회성 조치다.

### CachingDisabled
- 캐시 여부를 판단하지 않고 매 요청을 오리진으로 그대로 전달한다.
- 저장된 사본이 없으므로 지울 대상도 없다.
- API, SSE처럼 응답이 매번 달라지는 경로에 적용한다.

### Invalidation
- 캐싱이 켜진 경로에서, 원본이 바뀌었는데도 캐시 유효 기간이 안 끝나 옛날 사본이 계속 나갈 때 강제로 지우는 조치다.
- 정적 파일처럼 캐싱이 유리한 경로에 적용한다.
