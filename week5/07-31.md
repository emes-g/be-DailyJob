## 작업 과정에서 어려웠던 점 & 배운 점
### 나 자신을 너무 몰아세우지 말자
전일 작성했던 동료/셀프 피드백 내용을 바탕으로 수업 및 조별 활동이 진행되었다.

동료 덕분에 팀에 생긴 긍정적인 변화는 무엇이었는지, 반대로 해당 동료가 개선하면 좋을 습관으로는 어떤 것이 있는지에 대해서 작성했었는데, 해당 내용들이 취합되어 수업에서 익명의 통계 자료 형태로 제공되었다.

다양한 내용이 나왔지만, 공통적으로 하드 스킬보다 소프트 스킬에 관련된 내용이 상위권에 포진해 있었다. 가령,
- 고민을 깊이 하는 것은 좋은데, 혼자서는 너무 깊이 고민하지 않았으면 좋겠다. 공유해서 같이 고민했으면 좋았을 것 같다.
- 협업에서는 개인의 페이스 조절이 요구된다. 느린 것뿐만 아니라, 혼자서 너무 빠른 것 또한 좋지 않다.
- 팀원들이 제지할 수 있기 때문에, 팀장으로서의 리더십/주도권을 보여주는 것도 좋을 것 같다.
- 이미 실력은 충분한데 자신감이 부족한 탓인지, 의견을 적극적으로 제시하지 않는 것이 안타까웠다.
- 의견을 명확하고 부드럽게 전달했으면 좋겠다.
- ...

하드 스킬 관련 내용들도 중위권 정도에는 포진해 있을 줄 알았는데, 대부분 리스트 밖이나 하위권에 위치할 정도로 우선순위가 높지 않았다. 나뿐만 아니라 대부분의 교육생이 소프트 스킬 위주로 작성한 점이 흥미로웠다.

수업이 끝난 직후, 통계 자료에 나온 항목을 바탕으로 메인 프로젝트 조원들끼리 2가지 활동을 진행하게 되었다.
1. 각자 '내가 개선해야 할 점'을 3가지 선정하고, 팀원들이 이에 동의하지 않으면(개선하지 않아도 된다고 생각하면) 마킹을 해주는 것
2. 각 팀원들에게 '이 사람이 유지하면 좋을 점'을 1가지씩 작성해 주는 것

수십 개의 항목이 있었는데, 평소에 내가 느꼈던 점들을 고려하여 다음 3가지 내용을 선정하였다.
- 깊은 고민/신중함으로 인한 실행 지연 
- 리더십/주도권 강화
- 의견/소통/질문/고민/공유를 더 적극적으로 표현하기

그런데 팀원들의 평가 결과가 조금 의외였다. 깨끗할 줄 알았는데, 모든 항목에 마킹되어 있었을 뿐 아니라 특히 첫 번째 항목에는 대부분의 인원이 마킹해주었던 것이다.

결과를 보고 나는 무의식적으로 '내 고민의 깊이가 그리 깊지는 않았나 보다'라는 생각을 하게 되었는데, 조별 활동 이후에 댕글님께서 해주신 말씀이 인상깊었다.

"팀원들은 크게 실행 지연이라고 느끼지 않는 것 같다."

듣고 보니 그렇게 생각할 수도 있었다. 나는 초점을 앞에 뒀던 것이고, 댕글님께서는 초점을 뒤에 두고 계셨던 것이다.

물론 내가 맞을 수도 있지만, 너무 당연하게도 전자라고 생각했던 점이 나로 하여금 '지금껏 내가 나를 너무 몰아세운 것은 아닌지, 엄격한 잣대로만 평가해온 것은 아닌지'에 대해 돌아보게 만들었다.

몰아세우기만 해서는 어느 순간 자신감이 결여되고, 의지가 꺾일 지도 모른다.

앞으로는 나부터가 나를 아끼고, 독려해 줘야겠다고 생각하게 되었다. 물론, 이 또한 너무 과해지지 않도록 균형을 잘 맞춰야 할 것이다.

# 2. 종합 회고
## 잘한 점
### 모르는 점은 적극적으로 물어보기
- 소프티어 기간이 끝나면, 취업하기 전까지 팀 프로젝트를 할 경험이 많지 않다고 생각했다.
- 그래서 데모 부스 시간에 최대한 여러 팀을 돌아다니면서, 궁금한 점을 적극적으로 물어보았다.
- 어떤 프로젝트인지, 어떻게 동작하는 기능인지도 당연히 물어봤지만, 단순한 결과보다는 '어떠한 과정을 통해 그런 결과가 나오게 되었는지'를 알려고 노력했다.
- 다양한 사람의 의견을 듣는 과정에서, '이후 내 프로젝트에는 어떻게 접목시킬 수 있을지' 고찰해 볼 수 있었다.
- 팀을 위해서도, 나를 위해서도 앞으로도 모르는 점은 적극적으로 물어보는 태도를 유지하고 싶다.

## 아쉬웠던 점
### 프로젝트 전반을 이해하고 있지는 못하다
- 프로젝트 전반을 이해하고 있지는 못해서, 스쿼드 세션에서 대답해주지 못한 항목들이 있던 것이 아쉬웠다.

## 개선할 점
### 너무 조급해하지 말자
- 프로젝트 진행 기간과 볼륨을 생각하면, 현재 내 담당이 아닌 파트에 대한 이해는 낮을 수 밖에 없다.
- 이는 남은 기간 동안 팀원들과 꾸준히 의견 교류를 하며, 채워 나가야 할 부분이다.
- 처음부터 완벽을 바라지 말자. 작업 회고에서 서술했던 '나 자신을 몰아세우지 말자'라는 부분과도 통용된다.

# 3. 학습 
## 세션 vs JWT
가장 큰 차이는 상태 저장 위치이다.

### 세션
- **Stateful (상태 유지):** 서버(인메모리, DB, Redis 등)에 사용자의 인증 상태를 저장한다.
- **데이터 보관:** 클라이언트는 식별 용도의 세션 ID(Session ID)만 보관한다.
- **검증 방식:** 서버는 요청을 받을 때마다 세션 ID를 통해 저장소를 조회하여 유효성 및 사용자 정보를 확인한다.
- **확장성:** 트래픽 증가 시 애플리케이션 서버뿐만 아니라 세션 저장소(Redis 클러스터 등)의 스케일 아웃이 함께 고려되어야 한다.

### JWT (JSON Web Token)
- **Stateless (무상태):** 클라이언트가 인증 정보를 가지고, 서버는 서명만 검증한다.
- **데이터 보관:** 클라이언트는 사용자 인증 정보가 모두 담긴 토큰 본체(Payload)를 보관한다.
- **검증 방식:** 서버는 저장소 조회 없이, 내장된 비밀키(Secret Key)나 공개키(Public Key)를 통해 토큰 서명(Signature)의 위변조 여부를 확인한다.
- **확장성:** 중앙 저장소에 의존하지 않으므로 서버 자체의 스케일 아웃이 매우 용이하다.

### MSA 환경에서 JWT가 활용되는 이유 및 동작 방식
서버를 다수 운용하는 마이크로서비스 아키텍처(MSA) 환경에서 JWT가 갖는 핵심 이점은 다음과 같다.

#### I/O 작업(네트워크 통신) 최소화
- 세션 방식은 요청마다 서버와 Redis 간의 네트워크 통신이 발생한다.
- JWT는 토큰 내부에 식별 정보가 포함되어 있어, 외부 서버나 DB 조회 없이 서버 내부의 CPU 연산(암호학적 검증)만으로 인증을 완료한다.

#### 마이크로서비스 간 독립성 확보
- 수많은 서비스가 단일 세션 클러스터(Redis 등)에 의존하여 발생하는 병목 현상과 결합도를 낮춘다. 
- 서비스는 키(Key)만 가지고 있으면 독자적으로 권한을 인가할 수 있다.

#### 플랫폼 확장성 (이기종 클라이언트 지원)
- 웹 브라우저의 쿠키(Cookie)에 종속적인 세션과 달리, HTTP 헤더(`Authorization: Bearer`)를 사용하여 웹, 모바일(iOS/Android), 서드파티 앱 등 다양한 환경에서 동일한 방식으로 통신한다.

### MSA에서의 JWT 실제 검증 흐름
네트워크 횟수를 줄이는 실제 인증 구조는 다음과 같이 동작한다.
- **발급 (최초 1회):** 사용자가 인증 서버를 통해 로그인한다. 이때만 DB를 조회하여 계정을 확인하고 JWT를 발급한다.
- **요청:** 클라이언트가 API Gateway로 JWT를 포함하여 요청을 보낸다.
- **자체 검증:** API Gateway는 인증 서버와 통신하지 않고 자체적으로 서명을 검증한다. (네트워크 I/O 없음)
- **라우팅:** 검증 완료 후, 페이로드에서 식별자(User-Id 등)를 추출하여 내부망의 목적지(결제, 주문 등) 마이크로서비스로 요청을 전달한다.

### 세션(Redis) 방식이 여전히 널리 활용되는 이유 (JWT의 한계)
네트워크 왕복 횟수를 줄이는 JWT의 확실한 메리트에도 불구하고, 세션 방식이 유지되는 핵심 이유는 '통제력'과 '실시간성'에 있다.

#### 서버의 중앙 통제력 상실
- JWT는 한 번 발급되면 만료 시간이 지나기 전까지 서버에서 물리적으로 접근을 막을 방법이 없다.
- 토큰이 탈취되거나 관리자가 악성 사용자를 즉시 강제 차단(로그아웃)해야 할 때 대처가 불가능하다.
- 반면 세션은 중앙 저장소(Redis)의 데이터만 지우면 즉각 모든 접근을 차단할 수 있어 보안이 중요한 도메인에서 필수적이다.

#### 데이터의 실시간성 (상태 불일치 문제)
- JWT는 페이로드 내부에 권한(Role) 등 사용자 정보를 담고 있다. 
- 결제 등으로 사용자 등급이 즉시 변경되어도, 재발급을 받지 않는 한 기존 토큰은 이전 정보를 유지한다.
- 반면 세션은 요청마다 중앙 저장소를 조회하므로 최신 상태와 권한을 즉각적으로 반영할 수 있다.

#### 내부망 통신 속도와 페이로드 크기의 트레이드오프
- 동일한 VPC 내부망에 위치한 앱 서버와 Redis 간의 통신 지연은 통상 1ms 미만이다. 
- 중앙 저장소를 조회하는 네트워크 오버헤드가 전체 응답 시간에 미치는 영향은 지극히 미미하다.
- 오히려 JWT는 자체 데이터로 인해 크기가 크기 때문에, 느린 외부 인터넷망(모바일 환경 등)에서 매번 HTTP 헤더에 담아 전송하면 대역폭 관점에서 불리할 수 있다.

#### 클라이언트 측 저장의 보안 취약성
- 브라우저 환경에서 JWT를 Local Storage에 저장할 경우 XSS(교차 사이트 스크립팅) 공격에 의해 토큰을 통째로 탈취당할 위험이 크다.
- 세션 ID는 `HttpOnly` 속성을 부여한 쿠키에 저장함으로써 브라우저 내 자바스크립트의 접근을 원천 차단하여 탈취를 방어하기 용이하다.

### 절충안 (Access Token + Refresh Token)
성능(Stateless)과 보안 제어력(Stateful)의 두 마리 토끼를 잡기 위해, 실무에서는 두 방식의 장점을 혼합한 구조를 표준적으로 채택한다.

#### Access Token (JWT 형태)
- 만료 시간을 매우 짧게(15~30분) 설정하여 발급한다.
- 인증 서버 통신 없이 각 서버에서 즉각적인 검증 용도로 사용하여 성능 이점을 취한다. 
- 탈취 시 피해 시간을 최소화할 수 있다.

#### Refresh Token (중앙 저장소/Redis 보관)
- 만료 시간을 길게(1~2주) 설정하여 발급하고, 클라이언트와 더불어 서버(Redis)에도 함께 저장한다.
- Access Token이 만료되었을 때, 인증 서버와 통신하여 재발급을 요청하는 용도로만 사용된다.
- 관리자가 사용자를 강제 차단하고 싶을 때 Redis의 Refresh Token을 삭제해 버리면, 이후 Access Token 갱신이 막히면서 간접적인 통제력을 행사할 수 있다.

```text
  - 갱신된 문서와 새로 추가된 문서를 고려해줘.
```

선택한 이유:
- 이전 대화에서 AI가 오해한 개념(애플리케이션 락 관련)을 명확히 바로잡고, 최신화된 문서 컨텍스트를 명시하여 AI의 이전 판단을 재검토하도록 논리적으로 통제했기 때문이다. 
- 또한, 동시성 제어 방식(조건부 업데이트 vs 비관적 락)에 대한 기술적 사전 지식을 먼저 제시함으로써, AI가 기초적인 개념 설명을 생략하고 더 깊이 있는 아키텍처 관점의 차이를 설명하도록 유도했기 때문이다.

### 2. 원본 프롬프트 구조 분석
- **문제 상황:**
  - 이전 대화에서 AI가 '애플리케이션 락'을 명시적 락 객체(ReentrantLock)로 오해하여 부적절한 동시성 문제를 지적했고, 에이전트가 참조하던 ERD 문서마저 구버전(stale)이어서 설계 판단에 오류가 발생한 상황이다.
- **원하는 결과를 어떻게 요구했는가:**
  - 3가지 구체적인 질문 및 정정 사항을 넘버링하여 제시한 뒤, 해당 내용들을 바탕으로 '앞선 판단을 다시 검토해 줄 것'을 명확히 요구했다.
- **필요한 맥락이 포함되어 있는가:**
  - 내가 파악하고 있는 동시성 제어 방식의 특징(커넥션 점유 문제, 스토리지 엔진 레벨의 affectedRow 판단 등)
  - 실제 의도했던 락 구현 방식
  - 에이전트가 새롭게 참고해야 할 파일
- **판단 기준이나 제약 조건이 있는가:**
  - 조건부 업데이트와 비관적 락의 차이를 설명할 때 '내가 알고 있는 사실 외에'라는 제약 조건을 걸어 불필요한 중복 설명을 방지했다. 
  - 또한, 명시적 락이 아닌 경우를 기준으로 동시성 문제 해결 여부를 평가하도록 기준을 설정했다.
- **출력 방식이 명확한가:**
  - 출력 형식을 특정(마크다운, 표 등)하지는 않았으나, 3가지 항목에 대해 순차적으로 답변하고 최종적으로 이전 판단을 번복 또는 재평가하는 논리적 흐름의 답변을 강제하고 있다.
- **나의 가설, 우려, 의도가 드러나는가:**
  - 락 객체를 명시적으로 사용하지 않고도 AI가 지적한 동시성 이슈를 안전하게 해결할 수 있을 것이라는 가설이 드러난다. 
  - 또한, 에이전트가 낡은 문서를 기반으로 잘못된 설계를 이어갈 것을 우려하여, 문서를 갱신하고 이를 인지시키는 의도가 잘 나타나 있다.

### 3. AI에게 프롬프트를 개선 요청하기
- 프롬프트 개선안
```
이전 대화에서 나눴던 설계 판단을 갱신된 문서를 바탕으로 다시 검토하고자 합니다.
먼저, `@docs/03-erd.md` 파일을 최신 상태로 갱신했고 `@docs/03-erd-reference.md` 문서를 새로 추가했으니 해당 파일들을 읽고 컨텍스트를 동기화해 주세요. 
이후, 아래 2가지 항목에 대해 분석하고 이전의 판단을 어떻게 수정해야 할지 답변해 주세요.

1. 조건부 업데이트 vs 비관적 락의 차이 심층 분석
- 두 방식 모두 커넥션 풀 고갈 문제가 발생할 수 있고, 조건부 업데이트는 스토리지 엔진 레벨에서 affectedRow로 판단하며, 비관적 락은 정합성은 강력하지만 커넥션을 오래 점유한다는 점은 이미 인지하고 있습니다.
- 제가 아는 이 내용들을 제외하고, 트랜잭션 경합이 심한 상황에서의 성능 차이나 데드락 발생 가능성 등 두 방식의 추가적인 아키텍처적 차이를 설명해 주세요.

2. 애플리케이션 락 방식에 대한 오해 정정 및 재평가
- 제가 제시한 방식은 `ReentrantLock` 같은 명시적 락 객체를 사용하는 것이 아니라, `ConcurrentHashMap<OrderId, Boolean>` 자료구조의 `putIfAbsent` 메서드를 활용하여 락과 유사한 효과를 내는 방식이었습니다.
- 락 객체를 직접 사용하지 않는 이 방식을 적용했을 때, 에이전트가 이전에 지적했던 동시성 문제가 동일하게 해결될 수 있을지 기술적 의견을 제시해 주세요.
```

### 4. AI가 개선한 프롬프트 분석
- **더 명확해진 목표 및 출력 형식:** 
  - 문서 동기화(Read) 작업을 선행하도록 명시적으로 지시하고, 답변해야 할 항목을 2가지로 구조화하여 AI가 논리적 흐름에 따라 검토 결과를 출력하도록 유도하였다.
- **추가된 제약 조건:** 
  - 기존 프롬프트는 '아는 사실 외의 차이를 알려달라'며 비교적 열린 질문을 던졌으나, 개선안에서는 '트랜잭션 경합 시의 성능 차이'와 '데드락 발생 가능성'으로 AI가 분석해야 할 기술적 범위를 명확히 제약했다.
  - 또한, 에이전트가 동시성 제어 방식이나 락에 대한 답변을 생성하기 전에 '반드시 최신 문서를 먼저 읽고 동기화할 것'을 요구하여 작업의 순서를 강제하는 제약이 추가되었다.
- **구체적 판단 기준 제시:** 
  - 조건부 업데이트와 비관적 락을 비교할 때 '트랜잭션 경합 시의 성능 차이' 및 '데드락 발생 가능성' 등 실무적으로 필요한 핵심 평가 기준을 추가로 제시하였다.
- **답변 품질이 좋아질 것으로 예상되는 이유:** 
  - 에이전트의 인지 흐름(최신 문서 동기화 → 기술적 분석 → 판단 재검토)이 논리적으로 재배치되었기 때문이다. 
  - 변경된 ERD 문서를 바탕으로 컨텍스트를 먼저 업데이트하게 함으로써, AI가 답변을 도출할 때 구버전 스키마를 섞어서 발생할 수 있는 논리적 오류를 원천 차단했다.
