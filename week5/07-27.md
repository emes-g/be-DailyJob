## 작업 과정에서 어려웠던 점 & 배운 점
### ERD 학습 과정
프로젝트 ERD를 학습하는 과정에서 어려움을 겪었는데, 크게 2가지 원인이 추정된다.
1. 업무 분담 구조상 ERD 설계, 엔티티 클래스 코드 검증 작업에 많이 참여하지 못했다. 
2. 우선순위에 따라 개발은 크게 3-phase로 진행될텐데, 중간에 스키마를 변경하는 공수가 크다고 생각해 처음부터 전체 분량의 ERD를 설계했다고 한다.

안 그래도 설계 볼륨이 컸는데, 데이터 모델링 작업이 진행되는 동안 다른 업무를 처리하고 있었으니, 필연적으로 ERD 학습에 어려움을 겪을 수 밖에 없던 것이다.

이러한 상황을 경험하니, 다음 2가지 사안에 대한 고민이 생겼다.

먼저, 데이터 모델링 볼륨을 어느 정도로 잡아야 하는가에 대해서다. 크게 다음의 2가지를 생각해 볼 수 있을 것 같다.
1. 페이즈 단위로 컴팩트하게 만들어서 점진적으로 추가하기 → 이해하기는 용이하지만, 페이즈가 전환될 때마다 스키마를 변경하는 공수가 확정적으로 들어간다. 
2. 처음부터 모든 페이즈를 고려하여 설계하기 → 볼륨이 커서 이해하기 어려울 수는 있지만, 페이즈 전환 시의 공수는 필요하지 않다.

실무에서는 후자를 택하긴 하지만, 이는 모델링 이후 DB를 수정할 일이 거의 없기 때문이다. 모델링 이후에 변동될 가능성이 높고, 볼륨이 크면 이해하기도 어렵다는 점을 고려했을 때 우리는 전자를 고르는 것이 합리적이었다고 생각한다.

다음으로, 과도하게 분업되지는 않았는가에 대해서다.

효율성을 위해 업무를 분담하는 것은 좋은데, 같이 했어야 할 작업도 나눠버린 것은 아닐까 하는 생각이 들었다. 실제로 데이터 모델링을 일부 인원만 진행한 결과, 다른 업무를 맡은 인원들은 ERD에 대한 이해도가 떨어지게 되었다.

돌이켜 보면 아쉽긴 하지만, 어떻게 보면 이번에 경험해서 깨달을 수 있었기 때문에 나쁘지만은 않았다고 생각한다.

앞으로도 이렇게 하나둘 깨달으면서, 프로젝트 진행에 대한 이해를 넓힐 수 있었으면 좋겠다.

# 3. 학습 내용
## 협업 과정에서 EC2 인스턴스 접속 방식
### 1. 단일 PEM 키 공유 방식
- **개념:** 
  - 인스턴스 최초 생성 시 발급받은 1개의 프라이빗 키(.pem) 파일을 팀원 전체가 공유하여 사용하는 방식이다.
- **장점:** 
  - 초기 설정이 빠르고, 키 파일만 전달하면 누구나 즉시 접속 가능하다.
- **단점:** 
  - 접속 주체 추적 및 보안 관리가 불가능하다. 
  - 키가 유출되거나 팀원 변동(퇴사 등)이 발생하면 새로운 키 페어를 생성하여 교체해야 한다.

### 2. AWS SSM (Session Manager) 방식
- **개념:** 
  - 별도의 SSH 키 없이 AWS IAM 권한을 기반으로 브라우저나 CLI를 통해 인스턴스에 접속하는 관리형 서비스이다.
- **장점:** 
  - 보안성이 가장 뛰어나다. 
  - 방화벽(보안 그룹) 22번 포트를 열 필요가 없고, 누가 언제 접속해서 어떤 명령어를 실행했는지 중앙에서 로깅 및 감사가 가능하다.
- **도입 한계:** 
  - 인스턴스 프로파일 연결 및 SSM 접근 제어용 IAM 권한 설정이 필수적이다. 
  - 현재 팀이 부여받은 계정 권한으로는 해당 설정을 구성할 수 없어 도입을 보류했다.

### 3. 개별 공개키 등록 방식 (채택)
- **개념:** 
  - 팀원 각자가 자신의 로컬 PC에서 고유한 SSH 키 페어(Private/Public)를 생성한 뒤, 각자의 '공개키(.pub)'만 EC2 서버의 `~/.ssh/authorized_keys` 파일에 개별 등록하는 방식이다.
- **도입 배경:** 
  - 권한 부족으로 인한 SSM 방식의 한계를 우회하면서도, 단일 PEM 키 공유가 가지는 심각한 보안 취약점을 해결하기 위해 선택한 대안이다.
- **장점:** 
  - 자신의 프라이빗 키를 타인과 공유하지 않으므로 안전하다. 
  - 인원 변동 시 권한을 회수하려면 `authorized_keys` 목록에서 해당 인원의 공개키 텍스트 한 줄만 지우면 되므로 관리가 유연하다.
- **단점:** 
  - 방화벽의 22번 포트를 열어두어야 하며, 새로운 팀원이 올 때마다 서버에 접속해 수동으로 키를 등록해 주어야 하는 관리 비용(오버헤드)이 발생한다.

## EIP (Elastic IP, 탄력적 IP)
### 개념
- 인터넷을 통해 접속할 수 있는 고정적인 퍼블릭 IPv4 주소이다.
- 특정 EC2 인스턴스의 하드웨어에 영구적으로 종속되지 않고 AWS 계정에 할당되는 독립적인 리소스다. 
- 장애가 발생하면 다른 인스턴스로 IP를 즉시 재연결(Remapping)하여 트래픽을 우회시킬 수 있다.

### 도입 배경 및 동적 퍼블릭 IP와의 차이
- **기본 퍼블릭 IPv4:** 
  - 서브넷 설정에 의해 자동 할당된 퍼블릭 IP는 인스턴스를 '중지(Stop)'한 후 '재시작(Start)'하면 기존 IP를 반납하고 새로운 IP 주소를 발급받게 된다. 
  - 클라이언트가 도메인 없이 IP로 직접 접속하거나, 외부 API(PG사 결제 연동 등) 방화벽에 IP를 화이트리스트로 등록해 둔 경우 통신 장애가 발생한다.
- **EIP (고정 IP):** 
  - 인스턴스를 중지하거나 재시작해도 IP 주소가 변경되지 않고 유지된다. 
  - 따라서 외부 통신을 위해 고정된 IP가 반드시 필요한 웹 서버(WAS), 베스천 호스트(Bastion Host), NAT 게이트웨이 등에 필수적으로 사용된다.

### 요금 정책
- 과거에는 인스턴스에 연결되어 실행 중일 때는 EIP 요금이 면제되었으나, 2024년 2월부로 AWS의 퍼블릭 IPv4 과금 정책이 변경되었다.
- 현재는 '자동 할당된 기본 퍼블릭 IPv4'와 'EIP' 모두 인스턴스 연결 여부와 관계없이 시간당 동일한 요금(약 $0.005)이 부과된다.
- 결과적으로 어차피 동일한 비용을 지불해야 하므로, IP 변동 리스크가 있는 기본 퍼블릭 IP를 사용할 이유가 없어졌으며 EIP를 할당하는 것이 권장된다. 
  - 단, 인스턴스와 연결되지 않은 채 방치된(유휴 상태의) EIP에 대해서도 요금이 부과되므로 사용하지 않는 EIP는 계정에서 릴리즈(Release)해야 한다.
