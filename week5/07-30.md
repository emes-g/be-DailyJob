# 3. 학습 내용
## GitHub CLI (gh)
### 개념
- GitHub CLI (gh)는 개발자가 웹 브라우저를 열지 않고도 터미널 환경에서 GitHub의 기능들을 직접 사용할 수 있도록 지원하는 공식 커맨드라인 도구다.
- 이를 통해 코드 작성, 버전 관리(Git), 그리고 협업 작업을 모두 터미널 창 하나에서 연속적으로 처리할 수 있다.

### 주요 기능
- **Pull Request (PR) 관리:** PR 생성, 상태 확인, 코드 리뷰, 병합(Merge) 및 특정 PR의 코드를 로컬로 가져오는(Checkout) 작업을 터미널에서 수행할 수 있다.
- **이슈(Issue) 관리:** 새로운 이슈를 작성하거나 기존 이슈 목록 확인, 필터링, 담당자 지정 및 상태 변경을 할 수 있다.
- **저장소(Repository) 관리:** 새로운 저장소 생성, 기존 저장소 복제(Clone), 포크(Fork) 및 저장소 기본 설정을 터미널에서 직접 처리한다.
- **GitHub Actions 제어:** CI/CD 워크플로우의 실행 상태를 모니터링하고, 실패한 작업을 재실행하거나 로그를 직접 확인할 수 있다.
- **Gist 및 Release 관리:** 코드 조각(Gist)을 빠르게 공유하거나 프로젝트의 새로운 버전을 릴리스할 수 있다.

### 장점
- **작업 전환(Context Switching) 최소화:** 코드 편집기, 터미널, 웹 브라우저 사이를 오가는 시간을 줄여 작업 효율성을 높인다.
- **자동화 용이성:** 다른 터미널 명령어 및 쉘 스크립트와 결합하여 반복적인 GitHub 관련 작업을 쉽게 자동화할 수 있다.
- **Git 명령어와의 연계:** 기존의 git 명령어 워크플로우에 자연스럽게 통합되어 사용이 직관적이다.

### 기본 사용법 및 명령어 예시
가장 먼저 GitHub 계정 연동을 위한 인증 과정을 거쳐야 한다.
```bash
gh auth login
```
인증을 완료한 후에는 다음과 같은 명령어들을 사용할 수 있다.
- **gh repo create [프로젝트명]:** 새로운 GitHub 저장소 생성
- **gh issue list:** 현재 저장소에 등록된 이슈 목록 확인
- **gh pr create:** 현재 작업 중인 브랜치를 바탕으로 새로운 PR 생성
- **gh pr checkout [PR번호]:** 특정 PR의 코드를 로컬 브랜치로 가져와 테스트
- **gh run list:** 최근 실행된 GitHub Actions 워크플로우 상태 및 결과 확인

## 프록시와 연관관계 로딩 전략
### 프록시(Proxy) 객체
- JPA가 DB 조회를 최대한 미루기 위해 사용하는 가짜 객체다.
- 실제 엔티티 클래스를 상속받아 만들어지며, 내부에는 실제 데이터 대신 실제 객체를 가리키는 참조(Target)를 가진다.
- 프록시의 **실제 데이터에 최초로 접근할 때** 영속성 컨텍스트에 초기화를 요청하여 DB에서 실제 데이터를 가져온다. 
  - 단순히 참조를 꺼내는 것만으로는 쿼리가 나가지 않고, 내부 값을 실제로 참조하거나 순회할 때 비로소 초기화된다.

```java
List<PhoneNumber> phones = member.getPhoneNumbers(); // 쿼리 발생 안 함(프록시만 반환)

phones.size();                                        // 쿼리 발생(초기화)
phones.get(0);                                         // 쿼리 발생(초기화)
for (PhoneNumber p : phones) { ... }                   // 쿼리 발생(초기화)
```

### 연관관계 로딩 전략
> 엔티티 내부에 연관된 다른 엔티티가 존재할 때, 그 연관된 데이터를 DB에서 언제 가져올지 결정하는 전략이다.

#### 즉시 로딩 (`FetchType.EAGER`)
- 엔티티를 조회할 때 연관된 엔티티도 그 시점에 한꺼번에 DB에서 조회해 온다.
- 단건 조회(`em.find()`)에서는 JPA 엔진이 매핑 정보를 미리 분석해 OUTER JOIN이 포함된 단일 쿼리로 최적화한다.
- 다건 조회(JPQL)에서는 이 최적화가 적용되지 않아 N+1 문제가 발생할 수 있는데, 이는 애플리케이션 레벨에서 해결할 수 있다(후술).

#### 지연 로딩 (`FetchType.LAZY`)
- 엔티티를 조회할 때 연관된 엔티티는 실제 데이터 대신 프록시 객체로 채워 넣는다.
- 프록시의 실제 데이터가 필요한 시점(사용되는 시점)에 영속성 컨텍스트에 초기화를 요청하여 DB에서 실제 데이터를 가져온다.
- 즉시 로딩은 예측하기 어려운 대형 쿼리를 한 번에 유발할 수 있다. 그래서 실무에서는 연관관계를 기본적으로 지연 로딩으로 설정하고, 필요한 곳에만 아래 최적화 기법을 골라 적용하는 것을 표준으로 삼는다.

### LazyInitializationException (지연 로딩의 또 다른 문제)
- 프록시를 실제 데이터로 초기화하려면 영속성 컨텍스트(트랜잭션)가 살아있어야 한다.
- 트랜잭션이 이미 종료된 뒤(예: Service 계층에서 트랜잭션이 끝나고 Controller 계층으로 넘어간 뒤) 프록시의 실제 값에 접근하면, 초기화할 방법이 없어 예외가 발생한다.

```java
@Transactional
public Member getMember(Long id) {
    return memberRepository.findById(id).get();
    // 여기서 트랜잭션 종료, 영속성 컨텍스트도 닫힘
}

// Controller 영역
Member member = memberService.getMember(1L);
member.getPhoneNumbers().size(); // LazyInitializationException, 초기화 불가
```

## N+1 문제의 발생 원리와 JPQL의 한계
### N+1 문제
- 단일 쿼리 1번으로 N개의 결과 레코드가 반환된 상황에서, 그 N개의 레코드 각각에 대해 연관된 데이터를 채우기 위해 추가 쿼리가 발생하는 문제를 말한다.
- 즉, 쿼리를 1번 수행하려고 했는데 내부적으로 쿼리가 **N+1번** 발생하게 되는 문제다.

### 지연 로딩(LAZY)에서 N+1이 발생하는 과정
- 목록 조회 쿼리로 N개의 엔티티를 가져오면, 각 엔티티의 연관관계 필드는 프록시 객체로 채워진다.
- 이후 반복문 안에서 각 엔티티의 프록시에 최초로 접근하는 순간마다 초기화 쿼리가 발생한다. 가령 멤버 100명을 조회한 뒤 `for (Member m : members) { m.getPhoneNumbers().size(); }`처럼 순회하면, 루프를 돌 때마다 전화번호 단건 조회 쿼리가 100번 추가로 발생한다.
- 결국 목록 조회 쿼리 1번에, 프록시를 초기화하는 쿼리 N번이 더해진다.

### 즉시 로딩(EAGER)에서도 N+1이 발생하는 이유
- `FetchType.EAGER`는 연관 엔티티를 항상 함께 채워 넣는다는 뜻이지, 항상 SQL JOIN 한 번으로 채운다는 뜻은 아니다.
- JPQL은 작성된 문자열 자체를 SQL로 직역하므로, JPQL로 다건을 조회하면 일차적으로 대상 엔티티만 조회하고 연관관계의 EAGER 설정은 뒤늦게 처리된다.
- `SELECT m FROM Member m`을 실행하면, 멤버 100명을 가져오는 쿼리가 먼저 실행되고, 그다음 영속성 컨텍스트가 연관관계의 EAGER 설정을 확인하고, 마지막으로 100명 각각에 대해 연관 데이터를 채우는 쿼리가 100번 추가로 실행된다.
- 지연 로딩은 실제 값을 써야 쿼리가 나가지만, 즉시 로딩은 목록을 조회하는 그 순간 바로 N번이 나가버려서 오히려 원인 파악이 더 어렵다.

### JPQL의 한계
> JPQL은 객체(엔티티)를 대상으로 하는 객체지향 쿼리일 뿐, SQL의 JOIN을 자동으로 생성해 주는 도구가 아니다.

앞에서 본 두 문제(즉시 로딩·지연 로딩 각각에서 발생하는 N+1)는 사실 같은 원인에서 비롯된다.

- `SELECT m FROM Member m`처럼 JPQL 문장 안에 `m.phoneNumbers`라는 연관관계 경로 자체가 전혀 등장하지 않으면, Hibernate는 이 조회에서 phoneNumbers를 어떻게 처리해야 할지 판단할 근거가 없다. 그래서 결국 매핑에 적어둔 `FetchType`으로 돌아가 처리한다.
  - LAZY면 프록시로 채워두고 나중에 개별 초기화하고, EAGER면 그 자리에서 개별 조회를 추가로 실행한다. 
  - 어느 쪽이든 한 번에 묶어서 가져오지 못하고 개별 쿼리가 N번 발생하는 건 같다.
- 반대로 `SELECT m FROM Member m JOIN FETCH m.phoneNumbers`처럼 JPQL 문장 안에 그 경로를 직접 언급하면, Hibernate는 "이번 조회에서는 이 연관관계를 SQL JOIN으로 같이 가져와라"라는 명확한 지시를 받는다. 이게 바로 아래 나오는 Fetch Join이다.

### 해결 방법
전역 설정은 지연 로딩을 유지하고, 실제로 한 번에 조회해야 하는 지점에만 아래 기법을 골라 적용한다.

#### Fetch Join (`JOIN FETCH`)
- 위에서 본 대로 JPQL에 `JOIN FETCH`를 명시하면, 프록시가 아닌 실제 데이터를 SQL JOIN 한 번으로 가져온다. N+1이 해결되는 것은 물론, 트랜잭션이 끝난 뒤에도 그 연관 데이터에 안전하게 접근할 수 있다(LazyInitializationException이 나지 않는다).
- 컬렉션(`@OneToMany`) 관계에서는 페이징(`setFirstResult`/`setMaxResults`)이 불가능하다는 치명적인 단점이 있다. 두 개 이상의 컬렉션을 동시에 Fetch Join하면 데카르트 곱으로 결과 수가 부풀어나기 때문이다. 페이징이 필요하면 아래 배치 사이즈 방식을 쓴다.

#### 배치 사이즈 지정 (`@BatchSize`, `default_batch_fetch_size`)
- Fetch Join의 페이징 불가 문제를 해결하기 위한 대안이다. 프록시를 초기화할 때 식별자(PK)를 지정된 사이즈만큼 모아 `IN` 절 쿼리로 한 번에 조회한다.
- 설정: `spring.jpa.properties.hibernate.default_batch_fetch_size=1000`(전역) 또는 개별 필드에 `@BatchSize(size = 1000)`.
- 컬렉션 페이징 처리가 필요한 상황에서는 사실상 필수적인 최적화 기법이다.

#### `@EntityGraph`
- Fetch Join은 JPQL 문자열 안에 직접 써야 해서, Spring Data JPA가 메서드 이름만으로 자동 생성하는 쿼리(예: `findByStatus`)에는 적용할 수 없다.
- `@EntityGraph`는 "이 메서드를 호출할 때는 이 연관관계까지 함께 가져와라"를 어노테이션으로 선언하는 방식이다. JPQL을 직접 쓰지 않고도 Fetch Join과 같은 효과(연관 엔티티까지 SQL JOIN으로 한 번에 조회)를 낼 수 있다.

#### 애플리케이션 레벨에서 직접 배치 조회
- JPA의 자동 해결 기능에 기대지 않고, 연관관계 탐색 대신 조회 대상 ID를 먼저 전부 모아 `WHERE id IN (...)` 쿼리 한 번으로 미리 가져온 뒤 메모리에서 Map으로 매칭하는 방식이다.
- Fetch Join이 여의치 않은 상황(집계·DTO 프로젝션 등)에서 쿼리 수를 가장 확실하게 고정시킬 수 있다.
