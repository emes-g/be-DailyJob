# 1. 작업 회고
## 당일 수행 작업 목록
### 메인 프로젝트
- 프로젝트 학습
- 발표

## 작업 과정에서 어려웠던 점 & 배운 점
### 메인 프로젝트 심사
현대자동차 본사에서 메인 프로젝트 심사를 받게 되었다.

팀별로 정해진 시간 동안 면접관 앞에서 프로젝트 발표 및 질의응답을 진행하는 형태였다.

구체적인 내용을 밝힐 수는 없지만, 다방면에서 인사이트를 얻을 수 있었던 귀중한 경험이었다. 가령,
- 다대일, 다대다 면접이 아니라 다대팀 면접에서 갖춰야 할 자세는 무엇인지
- BE 개발자로서 AI를 어떻게 대해야 할지
- 지원자가 갖췄으면 하는 협업 가치관
- 질문 의도에 적확한 답변을 하고 있는지
- ...

심사를 마치고 가장 먼저 든 감정은, 아쉬움과 고마움이었다.

5주간 팀원들이 노력해 만든 결과물을 온전히 전달하지 못한 것 같아 아쉽기는 했지만, 그 결과물을 만들어내기까지 팀원들의 노고를 알기에 동시에 고맙기도 했던 것이다.

팀원들은 어떤 생각을 하고 있을까. 나는 그들에게 필요한 팀장이었을까?

저마다 생각은 다르겠지만, 모두가 있었기에 여기까지 올 수 있었다는 마음만큼은 동일했기를 바란다.

# 2. 종합 회고
## 잘한 점
### 적막을 깨고 의견 제시하기
- 특정 인원을 지목하지 않고 질문하실 때는 종종 적막이 발생했다.
- 나보다 더 잘 알고 있는 팀원이 있을지도 모른다든가, 조금 더 시간이 필요하다든가 이유는 여럿 있을 수 있겠지만, 적막이 오래 이어지는 것은 팀 차원에서 좋지 않겠다고 판단했다.
- 그래서 즉각 답변이 이루어지고 있지 않은 질문들 위주로 답변하려고 노력했다.
- 설령 나의 답변이 조금 부족하더라도, 잠깐이나마 여유 시간을 확보한다면 팀원들이 보강해 줄 것이라 믿었기 때문이다.
- 팀원을 믿고 현재 내가 할 수 있는 일에 집중하는 자세는 앞으로도 유지하고 싶다.

## 아쉬웠던 점
### 다른 팀의 발표를 듣지 못했다
- 이전에는 팀별로 분리되지 않고, 한 공간에서 차례차례 메인 프로젝트 심사를 받는 방식이었다고 들었다.
- 다른 팀의 발표에서 배울 점도 많았을 것 같은데, 참관이 불가능한 구조라는 점이 아쉬웠다.

## 개선할 점
### 쏟은 노력만큼 보여줄 수 있도록 고민하기
- 열심히 하는 것도 좋지만, 그 이상으로 올바른 방향 설정이 중요하다는 사실을 배울 수 있었다.
- 아무리 노력하더라도, 이를 온전히 보여주지 못한다면 그 가치가 반감될 수밖에 없기 때문이다.
- 어떻게 하면 내가 쏟은 노력만큼 보여줄 수 있을지에 대한 고민이 필요한 시점이다.

# 3. 주간 프롬프트 회고
### 1. 내가 최종 선택한 가장 잘 작성했다고 생각하는 프롬프트
원본 프롬프트:
```text
주문 취소 CORE 위키(@wiki/CORE-주문-취소.md)에 대해 질문이 있어.

1. Mermaid 도입 여부 결정
  - 문서가 현재 너무 글 위주로만 작성되어 있는 것 같아서, 독자 입장에서는 부담될 것 같아. 
  - 특히 흐름을 보여줘야 하는 부분에는 Mermaid를 도입하면 좋을 것 같은데, "문제: 취소 응답이 비결정적으로 갈린다"와 "문제: 취소는 됐는데 화면이 그걸 모른다" 파트가 적절할 것 같은데 어떻게 생각해?
2. 도메인 용어 작성 위치 결정
  - 간극, 논리적 만료와 같은 도메인 용어를 문서 최상단에 설명하는게 좋을지, 아니면 문서 내에서도 사용하는 파트의 최상단에 설명하는게 좋을지?
3. 비결정적 응답 관련 내용 올바르게 이해했는지 검증
  - 취소 요청 두 개가 거의 동시에 오는 상황을 가정해 보자.
  - 두 번째 취소 요청이 실패했을 때 일반적인 재조회를 수행하게 되면, 트랜잭션 내에서 최초에 조회한(findByIdAndCustomer_Id) 시점에 저장된 스냅샷이 읽히게 되니까 문제가 발생할 수 있다는 거지?
4. EventSource 관련 내용 올바르게 이해했는지 검증
  - 배송이 완료/취소되면 그 신호를 보낼 방법이 없었는데 이를 EventSource의 기본 성질을 이용해서 해결하겠다는 것이잖아.
  - 서버가 연결을 종료해서 브라우저가 재연결을 시도했는데, 서버가 거부하면 진짜 연결 종료로 파악하고 화면을 갱신한다는 로직을 완료/취소에 모두 적용하겠다는 것으로 이해하면 될까?
```

**선택한 이유:**
- 위키 문서의 가독성 개선(Mermaid 시각화, 용어 배치)과 복잡한 기술적 로직(동시성 제어, EventSource)에 대한 검증을 4가지 항목으로 명확하게 구조화하여 질문했기 때문이다.
- 단순히 기술적 개념을 묻는 것을 넘어, 내가 문서를 읽고 이해한 흐름과 가설을 먼저 제시한 뒤 이에 대한 팩트 체크를 요구하여 AI가 답변할 방향성을 정확히 통제했다.

### 2. 원본 프롬프트 구조 분석
- **문제 상황:**
  - '주문 취소 CORE 위키' 문서를 리뷰하고 다듬는 과정에서, 문서의 가독성 문제(글 위주의 서술)와 기술적 내용(비결정적 응답/EventSource 관련)에 대한 정확한 이해도 검증이 필요한 상황이다.
- **원하는 결과를 어떻게 요구했는가:**
  - 해결해야 할 안건을 문서 구조 개선(1, 2번)과 기술적 내용 검증(3, 4번)으로 나누어 총 4가지로 번호를 매겨 제시했다. 
  - 각 항목에 대해 내가 생각한 방안과 이해한 시나리오를 나열한 후, 이에 대한 동의 여부나 올바르게 이해했는지에 대한 검증을 요구했다.
- **필요한 맥락이 포함되어 있는가:**
  - 시각화가 필요한 문서 내 특정 파트 제목("취소 응답이 비결정적으로 갈린다" 등)과 사용될 도메인 용어(간극, 논리적 만료)를 구체적으로 명시했다. 
  - 비결정적 응답 상황에서의 트랜잭션 스냅샷 읽기(findByIdAndCustomer_Id) 문제와 EventSource의 재연결 거부를 활용한 브라우저 화면 갱신 로직 등 도메인 및 기술적 맥락이 상세히 포함되어 있다.
- **판단 기준이나 제약 조건이 있는가:**
  - 1번과 2번 질문에서는 '독자의 부담 감소'와 '문서의 가독성'을 판단 기준으로 설정하여 의견을 구했다. 
  - 3번과 4번 질문에서는 내가 제시한 '특정 동시성 상황(두 번째 취소 요청 실패 시)'과 'EventSource의 재연결 동작 원리'를 기준으로 삼아, 내 이해가 맞는지 평가하도록 답변 범위를 제약했다.
- **출력 방식이 명확한가:**
  - 특정 출력 포맷을 명시하지는 않았다. 
  - 하지만 질문을 4가지 번호로 명확히 분리하여, AI 역시 1~4번 항목에 맞춰 구조화된 답변을 제공하도록 자연스럽게 유도했다.
- **나의 가설, 우려, 의도가 드러나는가:**
  - 글 위주의 문서가 독자에게 부담을 줄 것이라는 우려와, 흐름도(Mermaid)가 필요하다는 설계적 의도가 잘 드러난다. 
  - 동시 취소 요청 시 트랜잭션 스냅샷으로 인해 문제가 발생할 것이라는 가설과, EventSource 연결 종료를 완료/취소 신호로 일관되게 활용할 수 있다는 기술적 가설이 명확하게 제시되어 있다.

### 3. AI에게 프롬프트를 개선 요청하기
- 프롬프트 개선안
```text
주문 취소 CORE 위키 문서를 리뷰하고 다듬기 위해 4가지 항목에 대한 피드백이 필요해. 단순한 동의보다는 기술적 근거나 부작용(Side Effect)을 바탕으로 내 가설을 철저히 검증해 줘.

[문서 구조 개선]
1. Mermaid 시각화 도입 여부
- 문제: "취소 응답이 비결정적으로 갈린다"와 "취소는 됐는데 화면이 그걸 모른다" 파트에 Mermaid 흐름도를 도입하려 해.
- 요청: 글 위주의 서술을 유지할 때와 흐름도를 도입할 때, 독자의 문맥 파악 측면에서 어떤 장단점이 있는지 비교해 줘.

2. 도메인 용어 작성 위치 결정
- 문제: '간극', '논리적 만료' 같은 도메인 용어의 설명 위치를 고민 중이야.
- 요청: 문서 최상단에 모아서 설명하는 방식과, 해당 용어가 처음 등장하는 파트 최상단에 분산 배치하는 방식 중 '기술 문서 작성 표준(Technical Writing)' 관점에서 어느 것이 더 적절한지 이유와 함께 알려 줘.

[기술 로직 검증]
3. 비결정적 응답 관련 동시성 로직 검증
- 내 가설: 두 번째 취소 요청이 실패했을 때 일반적인 재조회를 수행하게 되면, 트랜잭션 내에서 최초에 조회한(`findByIdAndCustomer_Id`) 시점의 스냅샷이 읽히게 되므로 문제가 발생한다.
- 요청: 이 가설이 맞는지 확인해 주고, 만약 틀렸거나 추가로 고려해야 할 DB 격리 수준(Isolation Level) 이슈가 있다면 구체적인 예시로 정정해 줘.

4. EventSource 연결 제어 로직 검증
- 내 가설: 배송 완료/취소 시 서버가 연결을 종료하여 브라우저가 재연결을 시도할 때, 서버가 이를 거부하면 클라이언트가 진짜 연결 종료로 파악하고 화면을 갱신하는 방식으로 상태 전파 문제를 해결할 수 있다.
- 요청: 이 전략이 표준 SSE(Server-Sent Events) 스펙이나 브라우저 동작 방식에 비추어 보았을 때 올바른 접근인지 검증해 주고, 예상되는 네트워크 예외 상황이나 문제점이 있다면 짚어 줘.
```

### 4. AI가 개선한 프롬프트 분석
- **더 명확해진 목표 및 출력 형식:**
  - 4가지 질문을 '문서 구조 개선(1, 2번)'과 '기술 로직 검증(3, 4번)'이라는 두 가지 카테고리로 묶어, AI로 하여금 질문의 맥락과 목적을 더 쉽게 파악하도록 구조화했다.
  - 질문마다 '내 가설(또는 문제)'과 '요청'을 명시적으로 분리하여, AI가 검증해야 할 대상과 출력해야 할 답변의 형태를 명확히 지정했다.
- **추가된 제약 조건:**
  - 도입부에 '단순한 동의보다는 기술적 근거나 부작용(Side Effect)을 바탕으로 내 가설을 철저히 검증해 줘'라는 조건을 추가하여, AI가 근거에 기반한 객관적인 리뷰를 하도록 강제했다.
- **구체적 판단 기준 제시:**
  - 2번 질문에서는 '기술 문서 작성 표준(Technical Writing)', 3번 질문에서는 'DB 격리 수준(Isolation Level)', 4번 질문에서는 '표준 SSE 스펙이나 브라우저 동작 방식'을 명시적인 판단 기준으로 제시하여 답변의 해상도를 높였다.
- **답변 품질이 좋아질 것으로 예상되는 이유:**
  - 내가 문서 작성 과정에서 가진 의문과 기술적 가설을 검증할 때, AI가 의존할 수 있는 명확한 기술적 키워드와 평가 기준을 미리 제시했기 때문이다.
