## 작업 과정에서 어려웠던 점 & 배운 점
### 콜 목록 조회 성능 개선하기
오전에 출근하고 보니, 콜 목록 조회 기능과 관련하여 Discussion이 올라와 있었다. 안건은 '부하 테스트 도중 앱 CPU 사용률이 높았던 원인이 콜 목록 조회 기능에 있음'이었다.

AVAILABLE(운행 가능) 상태의 라이더 700명이 콜 목록 화면에서 3초에 한 번씩 새로고침하는 상황을 가정했는데, 예상보다 앱 CPU 사용률이 높았다고 한다.

이유는 생각보다 명확했다.

현재는 delivery_order 테이블의 WAITING 상태인 주문을 그대로 가져와서 콜 목록 응답 생성에 활용하고 있다. 그런데 인스턴스를 생성하는 과정에서 사용 여부와는 무관하게 모든 컬럼을 추출해야 하기 때문에, 오버헤드(리소스 낭비)가 발생하는 것이었다.

설명만 나열하면 와닿지 않을 수 있으니, 간단하게 콜 목록 조회(새로고침) 요청이 들어온 상황을 생각해 보도록 하자.
1. 트랜잭션 시작: `@Transactional` 어노테이션을 통해 트랜잭션을 시작하게 된다. 
2. 쿼리 실행: `findWaitingOrdersWithinBoundingBox`(Bounding Box 안에 위치한 WAITING 상태의 주문 목록)에 등록된 쿼리가 실행되고, DB는 그 결과를 JDBC ResultSet에 담아 반환한다.
3. Hibernate의 변환: ResultSet에 담긴 각 Row를 Entity로 변환하는 과정이다. 크게 4개의 단계로 구성된다.
   1. 컬럼 추출: ResultSet에 담긴 바이트 데이터를 자바 타입으로 바꾼다. 컬럼을 추출하는 작업으로, 필연적으로 컬럼 수만큼 반복될 수밖에 없다.
   2. 객체 인스턴스화: 추출한 값들로 인스턴스를 구성한다.
   3. 영속성 컨텍스트 등록: 해당 인스턴스를 엔터티로서 영속성 컨텍스트에 등록한다. Row당 한 번만 수행되는 작업이다.
   4. 더티 체킹용 스냅샷 복사: 등록과 동시에, 해당 엔터티의 깊은 복사본 역시 영속성 컨텍스트에 나란히 등록해 둔다. 더티 체킹을 위함이다.

2번 과정까지는 전혀 문제가 없지만, 영속성 컨텍스트에 엔터티를 등록하기 위해 컬럼 추출과 객체 인스턴스화를 거치는 과정에서 오버헤드가 발생한다. 구체적으로는 다음 2가지 항목이 원인이다.
1. 실제로 콜 목록을 만들기 위해 사용하는 컬럼은 8개인데, 29개의 컬럼을 모두 추출.
2. 엔터티를 다시 참조할 일이 없는데, 영속성 컨텍스트에 등록.

이를 해결하기 위해, 콜 목록 조회 과정에서 엔터티 대신 프로젝션을 사용하기로 했다. 엔터티가 아니니까 영속성 컨텍스트에 등록되지도 않고, 콜 목록 응답 생성에 필요한 컬럼들만 추출할 수 있기 때문이었다.

전환 결과, 상기 언급한 예시 상황에서의 오버헤드를 크게 감축할 수 있었고, 문제를 해결하는 과정에서는 도구를 이해하고 사용하는 것의 중요성을 깨닫게 되었다.

Spring Data JPA라는 도구는 정말 편리하지만, 이는 반대로 생각하면 그만큼 많이 추상화되어 있기 때문이다.

도구를 이해하지 못하고, 단순히 사용하기만 해서는 오늘과 같은 문제를 해결하지 못 할 것이다.

도구가 주는 편리함을 활용하되, 유사시에는 문제를 직접 해결하는 개발자가 될 수 있도록 노력하자.

- 따라서 모든 흐름 대신 핵심 흐름만을 문서에 담아내고자 했고, 그 결과 단권화를 성공적으로 마무리할 수 있었다.
- 배차 수락, 콜 목록 조회 등 남은 CORE 위키도 이와 같은 방식으로 작성하고자 한다.

- 그러니 내 담당 파트부터 확실히 이해할 수 있도록 하자. 다른 파트 학습은 그 이후의 이야기다.

# 3. 학습 내용
## 엔터티 (Entity)
- **DB 테이블과 매핑되는 객체다:** 
  - `@Entity`로 선언하고, 필드가 테이블 컬럼과 매핑된다.
- **영속성 컨텍스트가 관리한다:** 
  - JPA(Hibernate)가 엔터티를 조회하는 순간 스냅샷을 떠두고, 트랜잭션이 끝날 때 값이 바뀌었으면 자동으로 UPDATE를 날린다(dirty checking). 
  - 그래서 조회한 엔터티의 필드를 그냥 바꾸기만 해도 DB에 반영된다.
- **연관관계를 매핑한다:**
  - `@OneToMany`, `@ManyToOne` 같은 어노테이션으로 다른 엔터티와의 관계를 표현하고, lazy 또는 eager 로딩으로 연관된 데이터를 가져온다.
- **조회 전용 화면에는 오버스펙일 수 있다:** 
  - 화면에서 몇 개 컬럼만 필요해도 엔터티는 매핑된 필드를 전부 가져온다. 
  - 연관관계를 lazy로 걸어놔도, 순회하면서 접근하는 순간 추가 쿼리가 나가는 N+1 문제가 생기기 쉽다.

## 프로젝션 (Projection)
엔터티 전체가 아니라, **화면이나 API 응답에 필요한 필드만 선택해서 조회**하는 방식이다. Spring Data JPA에서는 크게 세 가지 방식으로 쓸 수 있다.

### 인터페이스 기반 프로젝션
```java
public interface RiderCallSummary {
    Long getId();
    String getStatus();
    BigDecimal getFare();
}
```
- **Closed Projection:** 
  - getter 이름이 엔터티 필드 이름과 일치하면, Spring Data가 그 필드들만 SELECT하는 쿼리를 자동으로 만들어준다.
- **Open Projection:** 
  - `@Value("#{target.status + ' ' + target.fare}")` 같은 SpEL 표현식을 쓸 수도 있는데, 이 경우 엔터티 전체를 다 조회한 뒤 값을 조합하는 식으로 동작해서 최적화가 안 된다. 
  - 컬럼만 좁혀서 가져오려는 목적이면 Closed Projection 방식을 써야 한다.

### DTO(클래스) 기반 프로젝션
```java
@Query("SELECT new com.turkey.rider.dto.RiderCallSummaryDto(o.id, o.status, o.fare) FROM DeliveryOrder o")
List<RiderCallSummaryDto> findWaitingCalls();
```

- JPQL의 생성자 표현식(`new 패키지.클래스(...)`)으로 바로 DTO 객체를 만들어서 반환한다.
- 이 결과는 영속성 컨텍스트가 관리하는 엔터티가 아니라 순수한 값 객체다. dirty checking도 안 되고, 그냥 조회 결과를 담는 그릇일 뿐이다.

### Dynamic Projection
- 리포지토리 메서드에서 반환 타입을 파라미터로 받아, 같은 쿼리를 상황에 따라 다른 형태로 반환할 수 있다.
```java
<T> List<T> findByStatus(OrderStatus status, Class<T> type);
```

## 왜 엔터티 대신 프로젝션을 쓰는가
- **읽기 전용 화면에 딱 필요한 것만 가져온다:** 
  - 목록 조회처럼 일부 컬럼만 보여주면 되는 화면에서, 엔터티 전체를 로딩하는 건 그만큼 낭비다.
- **영속성 컨텍스트 관리 대상이 아니다:** 
  - 프로젝션 결과는 스냅샷을 안 들고 있으니, dirty checking 같은 부가 비용이 없다.
- **N+1 문제를 피하기 쉽다:** 
  - 필요한 컬럼을 애초에 조인해서 한 번에 뽑아오도록 쿼리를 짤 수 있어, 연관 엔터티를 나중에 순회하다가 추가 쿼리가 나가는 상황을 막을 수 있다.
- **네이티브 쿼리와도 잘 맞는다:** 
  - 네이티브 쿼리에서도 결과를 DTO나 인터페이스 프로젝션으로 받을 수 있어서, 복잡한 조회 쿼리에서 특히 자주 같이 쓰인다.

**목록처럼 데이터를 변경하지 않고 읽기만 하는 조회, 그리고 필요한 컬럼이 명확히 정해진 경우일수록 프로젝션이 엔터티보다 유리**하다.

## 요청 하나의 전체 흐름으로 보기
라이더 콜 목록 새로고침 요청 하나가 들어왔을 때 실제로 어떤 일이 일어나는지 순서대로 보면, 위에서 개념으로만 설명한 차이가 더 분명해진다.

### 1. 트랜잭션 시작
```java
@Transactional(readOnly = true)
public RiderDeliveryRequestPageResponse getDeliveryRequests(...)
```
- `@Transactional`로 메서드에 들어오면 Hibernate 세션(영속성 컨텍스트) 하나가 열리고, 커넥션 풀에서 JDBC 커넥션을 하나 빌려 묶는다.
- readOnly = true면 이 세션은 flush를 사실상 안 하는 쪽으로 동작한다.

### 2. 쿼리 실행
```java
@Query(value = "SELECT * FROM delivery_order FORCE INDEX (idx_delivery_waiting_location) ...", nativeQuery = true)
List<DeliveryOrder> findWaitingOrdersWithinBoundingBox(...)
```
- `FORCE INDEX`가 붙은 네이티브 쿼리가 MySQL로 나가고, 조건에 맞는 행을 테이블의 전체 컬럼(예: 29개)을 담아 응답한다.
- 이 시점까지는 순수 SQL, 네트워크 비용이고 아직 자바 객체가 아니다. JDBC ResultSet에 담긴 상태다.

### 3. Hibernate가 row를 엔터티로 되살리는 과정
row 하나가 엔터티(자바 객체)로 바뀔 때 매번 이런 일이 일어난다.

1. **컬럼 추출:** 
   - `ResultSet.getBigDecimal(i)`, `getString(i)` 같은 JDBC 호출로 바이트 배열을 자바 타입으로 바꾼다. 
   - 컬럼 수에 비례하는 비용이라, 29개 컬럼이면 29번 일어난다.
2. **객체 인스턴스화:**
   - 추출한 값들로 엔터티 인스턴스 하나를 만들고 필드를 채운다.
3. **영속성 컨텍스트 등록:** 
   - 이 객체를 (엔터티 타입, PK) 기준으로 1차 캐시(identity map)에 등록한다. 
   - 같은 트랜잭션 안에서 같은 id를 다시 조회하면 DB를 안 가고 이 객체를 그대로 돌려준다. row 한 개당 한 번, 컬럼 수와 무관한 고정비다.
4. **더티 체킹용 스냅샷 복사:** 
   - 등록 시점에 모든 필드 값을 복사한 배열을 하나 더 만들어 영속성 컨텍스트에 나란히 저장해둔다. 
   - 커밋 직전(flush 시점)에 현재 필드 값과 이 스냅샷을 비교해서 다른 게 있으면 그것만 골라 UPDATE를 자동 생성한다. 
   - `.save()`를 명시적으로 안 불러도 setter로 값만 바꾸면 커밋 시점에 UPDATE가 나가는 이유가 이거다.

### 4. readOnly = true가 실제로 생략하는 것
- readOnly = true는 위 네 단계 중 **더티 체킹용 스냅샷 복사** 하나만 생략한다. 로드된 엔터티가 read-only로 표시되어 비교용 스냅샷을 안 만들 뿐, 컬럼 추출, 객체 인스턴스화, 영속성 컨텍스트 등록은 그대로 다 일어난다.
- 즉 readOnly = true가 없애는 건 커밋 시점의 비교 작업뿐이고, row를 객체로 만들어 등록하는 비용은 그대로 남는다.

### 5. 응답 조립과 트랜잭션 종료
- Service는 이렇게 만들어진 엔터티에서 필요한 일부 필드(예: 8개)만 골라 DTO로 변환한다. 즉 전체 컬럼을 다 뽑아 객체로 만들어놓고 일부만 쓰고 나머지는 버리는 구조가 된다.
- 이후 JSON 직렬화, 응답 전송, 트랜잭션 종료(readOnly라 flush 없이 세션을 닫고 커넥션을 반납한다) 순서로 끝난다.

### 6. 프로젝션으로 바꾸면 달라지는 것
- 프로젝션(인터페이스 기반)을 쓰면 Spring Data가 이걸 엔터티가 아닌 값 객체로 취급한다.
- SQL 자체가 필요한 컬럼만 SELECT하도록 바뀌어서, 컬럼 추출이 필요한 컬럼 수만큼만 일어난다.
- 엔터티가 아니므로 영속성 컨텍스트 등록도, 스냅샷 복사도 아예 일어나지 않는다.
