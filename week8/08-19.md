## 작업 과정에서 어려웠던 점 & 배운 점
### 오해 바로잡기
CORE 위키 작성 관련하여, 일부 팀원들과 이해가 상충하는 부분이 있었다.

구체적으로는 CORE 위키의 목적을 다르게 이해하고 있어, 구성이 상이했던 것이다.

나는 CORE 위키 하나만 보더라도 해당 기능 및 그 흐름을 이해할 수 있도록 단권화시키는 것에 집중했고, 일부 팀원들은 CORE 위키를 링크 허브로 활용하고 있던 것이었다.

이런 까닭에 특정 팀원이 내게 '지난 주에 구조를 합의한 것 아니었냐, 근데 이렇게 다른 구조로 작성해 버리면 어떡하냐'는 의견을 제시하게 되었다.

나는 그 말을 통해 지난 주에 내가 했던 답변이 제대로 전달되지 않았음을 유추할 수 있었고, 현 상황을 해결하기 위해 다음의 2가지 행동을 즉각 수행했다.
1. 지난 주에 내가 했던 말을 그대로 인용하여, '해당 답변이 전달하고자 하는 바는 이러한 의미였다'는 사실을 먼저 확실히 하였다. 오해를 바로잡기 위함이었다.
2. 현 상황이 문제가 되지 않는 이유를 설명했다. README에서 CORE 위키를 타는 과정만 동일하면 됐지, 그 내부 구성까지 일관적으로 작성할 필요는 없다는 것이었다.

다행히 해당 팀원도, 다른 팀원들도 나의 설명을 납득해 주어서 무사히 작업을 이어 나갈 수 있었다.

위 경험을 통해, 크게 2가지 깨달음을 얻을 수 있었다.
1. 나의 입장을 확실히 표명할 수 있어야 한다. 내가 선택했던 행동들의 당위성이 입증된다면, 설령 오해가 있었더라도 해당 내용을 재검토해 볼 수 있다.
2. 애초에 오해가 발생하지 않도록, 보다 명확히 전달하는 것이 중요하다. 처음에 명확하게 전달하지 못했더라도, 한 번 더 짚고 넘어 갔다면 오해가 발생하지는 않았을 것이라고 생각한다.

# 2. 종합 회고
## 잘한 점
### 침착한 문제 해결
- 주문 취소 CORE 위키를 작성했던 세션(A)과 다른 세션(B)에서 콜 목록 조회 CORE 위키를 작성하였다.
- A 세션에서 CORE 위키를 작성하는 법을 문서화해 둬서, A가 아닌 다른 세션에서 작업하더라도 동일한 퀄리티가 보장될 줄 알았기 때문이다.
- 하지만 실제로는 기대에 훨씬 못 미치는 초안을 제공받게 되었고, 이에 수차례 검수하여 만족할 만한 퀄리티를 얻어낼 수 있었다.
- 이후에는 동일한 문제가 재발하지 않도록, CORE 위키 작성 기법이 담긴 문서 또한 개정하였다.
- 문제가 발생했다는 사실에 좌절하는 대신, 이를 해결하고자 노력하는 태도를 앞으로도 유지하고 싶다.

## 아쉬웠던 점
### 일일 그룹 회고를 하지 못했다
- CORE 위키 작성, 프로젝트 발표자료 작성, 발표 스크립트 작성 등 시급한 업무를 처리하는 과정에서, 일일 그룹 회고를 누락하게 되었다.

## 개선할 점
### 간단하게나마 진행할 수 있도록 하자
- 당일 수행한 업무를 정리하고, 느낀 점을 공유하는 일일 그룹 회고 또한 성장의 발판이 될 수 있는 중요한 업무이다.
- 바쁘더라도, 간단하게나마 회고를 진행할 수 있도록 하자.

# 3. 학습 내용
## Nginx
- **개념:** 
  - 경량 고성능 웹서버 겸 리버스 프록시다. 
  - 이벤트 기반(비동기) 아키텍처라 적은 스레드로도 많은 커넥션을 동시에 처리할 수 있다.
- **특징:** 
  - worker process 모델을 쓴다. 
  - master 프로세스가 여러 worker 프로세스를 만들고, 각 worker가 이벤트 루프 하나로 수많은 커넥션을 처리한다. 
  - 커넥션마다 스레드를 하나씩 할당하는 전통적인 모델(Apache 등)보다 메모리 효율이 좋다.
- **용도:** 
  - 정적 파일 서빙, 리버스 프록시, 로드밸런서, TLS termination(HTTPS 암복호화를 nginx가 대신 처리)까지 한 번에 담당하는 경우가 많다.

## 포워드 프록시 vs 리버스 프록시
### 포워드 프록시 (Forward Proxy)
- **개념:** 
  - 클라이언트 쪽에 위치한 프록시다. 
  - 클라이언트가 이 프록시를 거쳐서 외부 서버에 접속하고, 클라이언트는 프록시의 존재를 알고 사용한다.
- **용도:** 
  - 사내망에서 외부 접속을 통제하거나, 응답을 캐싱하거나, 클라이언트 IP를 감춰서 익명화하거나, 특정 사이트 접근을 차단하는 데 쓴다.
- **특징:** 
  - 서버 입장에서는 실제 요청을 보낸 클라이언트가 누군지 모르고, 프록시만 보인다.

### 리버스 프록시 (Reverse Proxy)
- **개념:** 
  - 서버 쪽에 위치한 프록시다. 
  - 여러 백엔드 서버 앞에서 요청을 대신 받아 내부로 라우팅하고, 클라이언트는 프록시가 있는지 모른 채 그냥 그 서버인 것처럼 접속한다.
- **용도:** 
  - 로드밸런싱, TLS termination, 캐싱, 정적 파일 서빙, 경로별로 여러 내부 서비스에 요청을 나눠주는 라우팅(`/api`, `/static` 등)까지 다양하게 쓰인다.
- **예시:** 
  - nginx가 리버스 프록시의 대표적인 구현체다.

## L4 vs L7 로드밸런서
### L4 (Transport Layer)
- **개념:** 
  - IP, 포트, TCP/UDP 헤더 수준에서 라우팅을 결정한다. 
  - 요청의 내용(HTTP 경로나 헤더)은 보지 않고, 커넥션 단위로 트래픽을 분산한다.
- **특징:** 
  - 요청 내용을 안 들여다보는 만큼 오버헤드가 적어서 빠르다. 
  - 라운드로빈이나 해시 기반의 단순한 분산 방식을 쓴다.

### L7 (Application Layer)
- **개념:** 
  - HTTP 헤더, 경로, 쿠키 같은 애플리케이션 레벨 정보까지 보고 라우팅한다.
- **예시:** 
  - `/api/customer`는 고객 서버로, `/api/rider`는 라이더 서버로 나누는 경로 기반 라우팅이 가능하다.
- **특징:** 
  - SSL termination, 세션 유지(sticky session), 컨텐츠 기반 라우팅을 지원한다. 
  - L4보다는 느리지만 훨씬 유연하다.

## ELB (AWS Elastic Load Balancer)
- **개념:** 
  - AWS가 제공하는 관리형 로드밸런서 서비스로, 직접 nginx 인스턴스를 띄워서 운영하지 않아도 된다.
- **ALB(Application Load Balancer):** 
  - L7 로드밸런서다. 
  - HTTP/HTTPS 기반이고, 경로나 호스트 이름 기준으로 라우팅할 수 있다.
- **NLB(Network Load Balancer):** 
  - L4 로드밸런서다. 
  - TCP/UDP 기반이고, 아주 낮은 지연과 높은 처리량이 필요할 때 쓴다.
- **CLB(Classic Load Balancer):** 
  - 예전 세대 로드밸런서로, 지금은 신규로 잘 안 쓴다.
