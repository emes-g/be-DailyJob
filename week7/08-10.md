## 작업 과정에서 어려웠던 점 & 배운 점
### 도메인을 처음 접하는 팀원도 이해할 수 있도록 풀어서 설명하기
오전에 출근하고 보니, 주문 상태 전달 방식과 관련하여 Discussion이 올라와 있었다. 안건은 'SSE 상태 전이 메시지가 유실되었을 때, 화면-서버 정합성을 어떻게 보장할까?'였다.

현재 주문 상태는 `WAITING`, `ASSIGNED`, `MOVING_TO_PICKUP`, `PICKED_UP`, `DELIVERING`, `COMPLETED`, `CANCELED` 이렇게 7개로 구성되어 있고, 주문 상태는 SSE를 통해 전달되고 있다.

여기서 문제는 주문이 종료(완료/취소)되는 시점에 SSE 상태 전이 메시지가 유실되면, 고객의 화면이 갱신되지 않을 수 있다는 것이다. 우리 애플리케이션에서는 주문 상태가 `WAITING → CANCELED` 혹은 `DELIVERING → COMPLETED`로 전이되는 시점을 의미한다.

지난 주에 '클라이언트가 본인이 만료되었다는 사실을 어떻게 알 수 있을지'에 대한 고민을 많이 했던 덕분일까, 나는 문제에 대한 답을 금방 찾을 수 있었다.

하지만 이를 팀원들에게 인식시키는 과정은 별개였다.

현재 문제를 해결하기 위해 필요한 배경 지식부터, 왜 이 방안이 해결책이 될 수 있는지까지 이해시키기 위해서는 많은 설명이 뒤따라야 했다. 가령,
- 주문 취소 기능에서만 사용하는 용어(논리적 만료, 물리적 만료, 간극 문제 등)
- 주문 취소 기능을 이해하기 위해 필요한 배경 지식
- 주문 취소 기능에서 발생할 수 있는 4가지 상황
- 현재 Discussion의 안건과 '내가 주문 취소 기능에서 고려한 문제'가 어떻게 맞닿아 있는지
- 제시한 방안이 왜 해결책이 될 수 있는지
- ...

'주문 취소 기능'을 처음 접한 팀원도 이해할 수 있게 상황을 풀어서 설명해야 했기 때문에, 글을 작성하는 데 생각보다 오랜 시간이 걸렸다.

하지만 그 과정에서 '주문 취소 기능'에 대한 이해가 한 층 더 깊어질 수 있었다. 남을 위해 시작했던 일이지만, 지나고 보니 나를 위한 일이 되기도 했던 것이다.

이러한 선순환은 지속되어야 한다고 생각한다. 그래서 앞으로 담당 도메인에 대한 Discussion을 작성할 때도, 오늘처럼 '도메인을 처음 접하는 사람도 이해할 수 있는 수준으로' 풀어서 작성하려고 한다.

다만 매번 오늘처럼 오래 걸려서는 안 될 것이다. 이건 아직 내가 익숙하지 않아서 그런 것도 있겠지만, 작문 능력이 높지 않은 것이 원인일 수도 있겠다고 생각했다.

작문 능력은 어떻게 키울 수 있을까?

사실 단기간에 키울 수는 없다고 생각한다. 하지만 꾸준히 글을 발행해 보고, 여러 종류의 글을 읽는다면 점진적으로 개선될 것이다. 

분야를 가리지 않고, 글을 가까이 하는 습관을 들일 수 있도록 하자.

# 3. 학습 내용
## InnoDB 아키텍처
### 전체 흐름
InnoDB는 크게 메모리에 있는 것(In-Memory Structures)과 디스크에 있는 것(On-Disk Structures)으로 나뉜다. 기본 원리는 다음과 같다.
1. 데이터를 바꿀 때 디스크를 바로 건드리지 않고, 먼저 메모리(버퍼 풀)에서 바꾼다. 
2. 그 변경 내용을 로그 버퍼에 적어뒀다가 redo log 파일로 먼저 내려보낸다(WAL 원칙, 로그를 먼저 쓴다). 
3. 실제 데이터 페이지는 나중에 한가할 때 디스크로 flush된다. 
4. 이렇게 하면 매번 랜덤한 위치에 쓰기 IO를 발생시키지 않아도 되니까 빠르다.

### In-Memory Structures (메모리에 있는 것들)
- **Buffer Pool**: 
  - 디스크의 데이터, 인덱스 페이지를 캐싱해두는 가장 큰 메모리 영역이다. 
  - 읽기든 쓰기든 일단 여기를 거친다. 
  - InnoDB 메모리의 대부분을 차지한다.
- **Adaptive Hash Index**: 
  - 버퍼 풀 안에서 자주 조회되는 페이지를 InnoDB가 알아서 감지해서 해시 인덱스를 만들어주는 자동 최적화 기능이다.
- **Change Buffer**: 
  - 세컨더리 인덱스를 수정할 때 그 자리에서 바로 디스크에 반영하지 않고 메모리에 모아뒀다가 나중에 한꺼번에 병합하는 공간이다. 
  - 원래는 랜덤 IO를 줄이려는 목적인데, DB 워크로드 대부분이 읽기 위주라 실제 효과가 크지 않은 경우도 많다.
- **Log Buffer**: 
  - 커밋 전 트랜잭션의 redo log 내용을 임시로 담아두는 작은 메모리 영역이다. 
  - 커밋되거나, 버퍼가 다 차거나, 일정 시간이 지나면 디스크로 내려간다.

### On-Disk Structures (디스크에 있는 것들)
- **System Tablespace (ibdata1)**: 
  - InnoDB의 기본 시스템 테이블스페이스다. 
  - 데이터 딕셔너리나 Change Buffer의 영속 저장소 같은 걸 담고 있다.
- **File-Per-Table Tablespaces**: 
  - `innodb_file_per_table=ON`이면 테이블마다 별도의 `.ibd` 파일이 생긴다(테이블 만들면 파일 하나가 새로 생기는 그 방식).
- **General Tablespaces**: 
  - 여러 테이블을 사용자가 명시적으로 하나의 공용 테이블스페이스 파일에 묶어 저장할 수 있는 방식이다.
- **Doublewrite Buffer Files**: 
  - 실제 데이터 페이지를 원래 위치에 쓰기 전에, 먼저 이 파일에 통째로 한 번 써두는 안전장치다. 
  - 쓰다가 중간에 크래시가 나서 페이지가 반쪽만 써지는 사고(partial write)가 나도, 여기서 복구할 수 있다.
- **Undo Tablespaces**: 
  - undo 로그를 저장하는 공간이다. 롤백할 때, 그리고 MVCC로 예전 버전의 값을 읽어야 할 때 여기서 가져온다.
- **Redo Log (#ib_redo_N)**: 
  - WAL 프로토콜이 실제로 구현된 곳이다. 
  - 로그 버퍼의 내용이 여기로 flush되고, 크래시가 나면 재기동 시 이 로그를 replay해서 데이터를 복구한다.
- **Temporary Tablespaces**: 
  - 정렬용 임시 데이터나 세션별 임시 테이블 같은 걸 담는 공간이다.

### 관계 및 흐름
- 데이터 페이지 쪽 흐름은 **Buffer Pool → O_DIRECT → 디스크(System Tablespace, Doublewrite Buffer, File-per-table 등**)다. 
  - `O_DIRECT`는 OS 캐시를 건너뛰고 디스크에 직접 쓰는 방식이라, 버퍼 풀(InnoDB 자체 캐시)과 OS 캐시가 같은 내용을 두 번 들고 있는 낭비를 막는다.
- 로그 쪽 흐름은 **Log Buffer → Operating System Cache → Redo Log**다. 
  - 데이터 페이지와 달리 로그는 OS 캐시를 거쳐서 나간다(그림에서 화살표가 O_DIRECT 쪽이 아니라 OS Cache 쪽으로 내려가는 걸 보면 이 차이를 확인할 수 있다).
- Change Buffer는 버퍼 풀 안에서 세컨더리 인덱스 변경분을 들고 있다가, 나중에 실제 인덱스 페이지(버퍼 풀 안의 해당 페이지)로 병합된다. 
- 정리하면, 급한 것(로그)은 최소한으로 빨리 디스크에 남기고, 무거운 것(실제 데이터 페이지)은 메모리에서 최대한 굴리다가 나중에 한꺼번에 내려보내는 구조다. 
  - 그래서 크래시가 나도 redo log만 있으면 복구가 되고, 정상 운영 중에는 디스크 IO를 최소화할 수 있다.

### SQL 쿼리의 실행 순서
UPDATE 하나가 커밋되기까지 실제로 이런 순서로 흘러간다.
1. Tablespace(.ibd)에 있는 데이터 페이지를 Buffer Pool로 읽어온다.
2. Buffer Pool 안에서 그 페이지를 변경한다. 아직 디스크에는 반영 안 됐으니 이 상태를 Dirty Page라고 부른다.
3. 변경 전 값은 Undo Log에 남긴다. 롤백할 때, 그리고 MVCC로 과거 버전을 읽을 때 쓰인다.
4. 변경 내용 자체는 Log Buffer에 쓰고, 그게 Redo Log로 flush된다. 크래시 복구용이다.
5. Redo Log가 디스크에 안전하게 쓰이면 그 순간 COMMIT이 완료된 것으로 처리한다.
6. 실제 데이터 페이지(Dirty Page)는 그 뒤에 Page Cleaner라는 백그라운드 스레드가 비동기로 디스크에 내려쓴다.
7. 내려쓰기 전에 먼저 Doublewrite Buffer에 통째로 한 번 써둔다(쓰다가 크래시 나는 걸 대비).
8. 최종적으로 진짜 Tablespace(.ibd) 파일에 기록된다.

- 여기서 중요한 포인트는, 커밋이 완료되는 시점은 5번(Redo Log가 디스크에 쓰인 시점)이라는 것이다. 
- 실제 데이터 페이지가 .ibd 파일에 반영되는 건 6, 7, 8번으로 그보다 훨씬 나중에, 비동기로 일어난다. 
- 그래서 커밋 직후 전원이 꺼져도 데이터 페이지는 아직 옛날 상태일 수 있지만, Redo Log로 재기동 시 다시 복구할 수 있다.

## Data Page
### 개념
- 디스크의 읽고 쓰기 단위는 Block이다. 그래서 디스크를 Block Device라고 부른다.
- InnoDB는 이 Block 여러 개를 묶어서 Page(보통 16KB)라는 논리적 단위로 다룬다. 
- 디스크 IO는 항상 이 Page 단위로 일어난다. 위에서 계속 나온 Buffer Pool도 결국 이 Page들을 메모리에 캐싱해두는 공간이다.

### 구조
한 Page 안의 구조는 대략 이렇다.
- Page header: 페이지에 대한 메타 정보
- Data row: 실제 레코드들이 쌓이는 부분
- Free space: 아직 안 쓴 빈 공간
- Slot array: 페이지 뒤쪽에서 각 레코드의 위치(오프셋)를 가리키는 포인터 배열

레코드는 varchar 같은 가변 길이 컬럼 때문에 크기가 서로 다를 수 있다. 그래서 한 페이지에 레코드가 몇 개 들어있는지 미리 정해져 있지 않고, 각 레코드가 정확히 어디 있는지도 Slot array를 거쳐서 찾아가야 한다.

### 용어
용어를 헷갈리기 쉬운데 정리하면 이렇다.
- Disk: 물리적인 저장 장치, Block 단위로 읽고 쓴다.
- Block: 디스크의 최소 IO 단위.
- Page: InnoDB가 다루는 논리적 단위, 여러 Block으로 구성된다(보통 16KB).
- Record: Page 안에 들어있는 실제 한 줄(row) 데이터.
- Slot: Page 안에서 각 Record의 위치를 가리키는 포인터.

## ReadView와 MVCC
- InnoDB의 MVCC는 여러 버전의 레코드를 전부 저장해두고 그중 골라 읽는 방식이 아니다.
- 실제로는 테이블(clustered index)에는 항상 최신 레코드 딱 하나만 있다.
- 대신 각 레코드에는 숨겨진 컬럼 두 개가 있다.
    - DB_TRX_ID: 이 레코드를 마지막으로 바꾼 트랜잭션 ID
    - DB_ROLL_PTR: 그 이전 버전이 저장된 Undo Log 위치를 가리키는 포인터
- 내가 지금 보고 있어야 할 버전이 최신 레코드가 아니라면(즉 내 트랜잭션이 시작된 이후에 다른 트랜잭션이 이 레코드를 바꿔버렸다면), DB_ROLL_PTR을 따라 Undo Log를 거슬러 올라가면서 과거 버전을 재구성해서 읽는다.
- ReadView는 이 판단의 기준이 되는 자료구조다. "지금 이 트랜잭션이 어떤 버전까지 봐야 하는지"를 담고 있어서, 최신 레코드가 ReadView 기준으로 보이는 버전인지 아닌지를 판단하고, 안 보이면 어디까지 Undo Log를 타고 올라가야 하는지 알려주는 역할을 한다.
