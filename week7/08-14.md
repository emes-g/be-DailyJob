## 작업 과정에서 어려웠던 점 & 배운 점
### 프로젝트 전반에 대한 이해
스쿼드 세션에서 '라이더의 위치가 백그라운드 상황에서도 실시간으로 전송되고 있냐'는 질문을 받았는데, 즉각 대답하지 못했다.

'라이더의 위치가 어떻게 수집되어 고객에게 전달되는지' 전체 흐름은 이해하고 있었지만, 세부적인 상황들에 대해서까지는 아직 숙지하고 있지 못했기 때문이다.

물론 내 담당 파트도 아니었고, 각자 담당했던 파트를 주말 간 정리해서 다음 주에 공유하자고 한 상황이라, '현재 해당 질문에 대해 즉각 답변하지 못했다'는 사실이 큰 문제가 되는 것은 아니었다.

하지만 위 질문은 내게 '주요 기능의 경우에는 단순히 전체 흐름만이 아니라, 그 흐름 속에서 발생 가능한 상황에 대해서도 어느 정도 생각해 둬야 한다'는 경각심을 심어주었다. 설령 담당자가 아닐지라도 말이다.  

데모 부스에서 역시 비슷한 경험을 했다.

'권한이 허용되어 있음에도 왜 라이더의 실시간 위치를 확인할 수 없냐'는 질문을 받았는데, 이 역시 즉각 대답하지 못했다.

'앱이 아니라 웹 브라우저로 접속해서 그런 것이 아닐까'라는 생각은 갖고 있었으나, 확신이 없었기 때문이다.

왜 확신이 없었을까? 결론부터 말하면, 프로젝트 실행 환경에 대한 이해가 부족했다.

담당 파트에서는 고객/라이더 2개의 브라우저만 띄우면 됐지, 앱을 구동해야 할 필요가 없었다. 그래서 잊고 있었는데, 데모 부스에서 질문을 받은 덕에 다시금 생각해 볼 수 있게 되었다.

연이은 경험을 통해, '프로젝트를 원활히 마무리하기 위해서는 담당/비담당 파트뿐만 아니라 실행 환경까지 모두 숙지해 둬야 한다'는 깨달음을 얻을 수 있었다.

- 고객과 라이더의 매칭은 실시간 퀵서비스 플랫폼의 핵심 기능 중 하나이다.
- 콜 목록 조회를 거쳐 매칭이 이루어져야, 비로소 이후의 기능들로 연결될 수 있다. 그렇기 때문에 해당 기능의 완성도를 높이는 것이, 그 어느 작업보다 중요하다고 생각했다. 
- 그래서 최근 며칠 간 해당 기능의 완성도를 높이는 데 주력했으며, 주말 동안에는 어디를 더 보완해야 할지 리스트업해 두었다.
- 단순 프로그램의 동작에 만족하지 않고, 지속적으로 완성도를 높이고자 하는 태도가 좋았다고 생각하며 앞으로도 유지하고 싶다.

- 배포 환경에서 모든 기능을 하나씩 꼼꼼하게 테스트하지 않고, 핵심 흐름(주문 생성부터 배송 완료까지)에만 집중했던 것이 원인이었다고 생각한다.

## 개선할 점
### 꼼꼼하게 테스트하기
- 데모 부스, 산출물 제출, 프로젝트 발표 등 주요 이벤트에 앞서 배포 환경을 꼼꼼히 테스트할 수 있도록 하자.

# 3. 학습 내용
## Redis와 Lua 스크립트
### Redis
- **인메모리 key-value 데이터 저장소:** 
  - 데이터를 디스크가 아니라 메모리에 두고 다루기 때문에 응답 속도가 매우 빠르다.
- **다양한 자료구조 지원:** 
  - 단순 문자열뿐 아니라 List, Hash, Set, Sorted Set, 그리고 Stream 같은 자료구조를 기본으로 지원한다.
- **싱글 스레드로 명령을 처리한다:** 
  - 한 번에 하나의 명령만 순서대로 실행하고, 명령 하나가 끝나야 다음 명령이 실행된다. 
  - 이 특성 덕분에 개별 명령은 항상 원자적으로 처리된다는 게 보장된다. 
  - 후술할 락, Lua 스크립트 이야기가 다 이 전제 위에 서 있다.
- **영속성 옵션도 있다:** 
  - RDB 스냅샷이나 AOF로 디스크에 백업을 남길 수 있지만, 기본적으로는 메모리 기반 저장소로 쓰인다.
- **주로 쓰이는 용도:** 
  - 캐시, 세션 저장, 실시간 카운터나 랭킹, 그리고 Pub/Sub이나 Stream을 이용한 메시지 전달 같은 데 많이 쓰인다.

### Lua 스크립트
- **Redis에 내장된 스크립팅 언어:** 
  - `EVAL`이나 `EVALSHA` 명령으로 실행하는, Redis 서버 안에 내장된 Lua 인터프리터를 통해 동작한다.
- **Lua 인터프리터가 내장된 이유:** 
  - Lua는 원래 다른 프로그램 안에 가볍게 내장하기 위해 만들어진 경량 스크립트 언어라, Redis 서버 프로세스 안에 인터프리터를 통째로 넣기에 적합했다.
- **핵심 특성:** 
  - 싱글 스레드 처리 방식과 맞물려서, 하나의 Lua 스크립트가 실행되는 동안에는 다른 클라이언트의 명령이 절대 끼어들 수 없다. 
  - 즉 스크립트 안에 여러 Redis 명령을 넣으면, 그 전체가 하나의 원자적인 단위로 실행된다.
- **EVALSHA:** 
  - 같은 스크립트를 매번 통째로 네트워크로 보내지 않고, 미리 등록해둔 스크립트를 SHA1 해시값으로 참조해서 실행할 수 있다. 
  - 반복 실행되는 스크립트의 네트워크 비용을 줄여준다.

## Redis에서 동시성 제어하는 방법
### 애플리케이션 레벨 락 (SETNX 기반)
가장 단순한 분산 락은 `SET key value NX PX ttl` 하나로 만든다.

```
SET lock:order:123 "token-abc" NX PX 5000
```

- **NX:** 
  - 키가 없을 때만 세팅한다. 
  - 이미 누가 락을 잡고 있으면 실패하니, 이 명령 자체가 원자적인 "잡기"가 된다.
- **PX ttl:** 
  - 락에 만료 시간을 걸어서, 락을 잡은 클라이언트가 죽어도 일정 시간 뒤엔 자동으로 풀리게 한다.
- **value(토큰):** 
  - 락을 잡을 때 클라이언트마다 고유한 값을 넣어둔다. 
  - 나중에 락을 풀 때 이 값이 내가 넣은 값과 같은지 확인하고 지워야, 다른 클라이언트가 이미 새로 잡은 락을 실수로 지우는 사고를 막을 수 있다.

문제는 여기서 생긴다. "값을 확인하고(GET) 같으면 지운다(DEL)"는 두 단계짜리 로직인데, 이 두 명령 사이에 다른 클라이언트가 끼어들 여지가 있다. 즉 확인은 원자적으로 했는데, 확인 후 삭제까지는 원자적이지 않다.

### Lua 스크립트 락
Redis는 싱글 스레드로 명령을 처리하고, Lua 스크립트는 `EVAL`로 실행하는 동안 다른 명령이 절대 끼어들 수 없다. 그래서 위에서 문제였던 "확인하고 지우기"를 하나의 Lua 스크립트로 묶으면 통째로 원자적이 된다.

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

- **애플리케이션 레벨 락:** 락을 잡는 것(SET NX)은 원자적이지만, 해제 로직(확인 후 삭제)은 여러 명령으로 쪼개져 있어 그 사이에 경쟁이 생길 수 있다.
- **Lua 스크립트 락:** 해제까지 포함한 전체 로직을 한 번의 원자적 실행으로 묶어서, 이 경쟁 자체를 없앤다.

### Lua 스크립트로 락 없이 동시성 제어하기
여기서 한 걸음 더 나가면, Lua 스크립트는 락이라는 개념 자체를 안 쓰고도 동시성 문제를 풀 수 있다. 락은 결국 "누가 지금 이 자원을 쓰고 있다"는 걸 별도의 키로 표시해두는 방식인데, Lua 스크립트는 애초에 "조회하고 조건에 맞으면 변경한다"는 로직 자체를 원자적으로 실행할 수 있다.

- **예시:** 
  - 재고 차감 로직에서 "재고를 잠그고, 확인하고, 차감하고, 락을 푼다" 대신, "재고가 남아있으면 차감한다"는 조건부 로직 자체를 Lua 스크립트 하나로 실행한다. 
  - 락 키를 만들고 지우는 과정 자체가 필요 없다.
- 이런 방식은 MySQL의 조건부 UPDATE(Compare-And-Set)와 비슷한 발상이다. 락으로 자원을 선점하는 대신, 원자적인 조건부 연산으로 경쟁을 처리한다.

### Redlock, Redisson
- **Redisson:** 
  - 락 획득, TTL 자동 연장(watchdog), 해제까지 다 구현해주는 클라이언트 라이브러리다. 
  - 위의 Lua 스크립트 로직을 라이브러리가 대신 처리해준다고 보면 된다.
- **Redlock:** 
  - 여러 대의 독립된 Redis 인스턴스 중 과반수에서 락을 획득해야 유효하다고 보는 알고리즘이다. 
  - Redis 노드 하나가 죽어도 락의 정합성을 지킬 수 있다.
- 단일 Redis 인스턴스만 쓰는 환경이면 Redlock까지는 필요 없다. 여러 노드에 걸친 장애를 대비하기 위한 것이라, 단일 인스턴스에서는 오버스펙이다.

## Redis Pub/Sub vs Stream vs Kafka
### Pub/Sub
- 발행된 메시지를 그 순간 구독 중인 클라이언트에게만 전달한다.
- 메시지를 저장하지 않는다. 구독하고 있지 않았으면 그 메시지는 그냥 유실된다.
- 재연결해도 놓친 메시지를 다시 받을 방법이 없다.

### Stream
- 로그처럼 메시지를 순서대로 쌓아두는 자료구조다(append only log).
- Consumer Group을 지원해서, 여러 소비자가 나눠서 읽고 ACK로 처리 완료를 표시할 수 있다.
- 메시지가 저장되어 있으니, 나중에 다시 연결해도 놓친 구간부터 이어 읽을 수 있다.

**비교**

| | Pub/Sub | Stream |
|---|---|---|
| 메시지 저장 | 안 함 | 로그로 저장 |
| 재연결 시 유실 | 유실됨 | 이어 읽기 가능 |
| 소비자 그룹 | 없음 | 있음(Consumer Group) |
| 적합한 용도 | 실시간 팬아웃, 유실 허용 가능한 알림 | 이벤트 로그, 순서 보장이 필요한 처리 |

### Kafka와 비교
- **Kafka:** 
  - 파티션 기반으로 분산된 로그를 디스크에 영속화하고, 리텐션 기간 동안 데이터를 보관한다. 
  - 컨슈머 그룹 리밸런싱, 높은 처리량과 내구성을 목표로 설계됐다.
- **Redis Stream:** 
  - 기본적으로 인메모리 자료구조라 Kafka만큼의 파티셔닝, 복제, 장기 보존 기능은 없다. 
  - 대신 가볍고 지연이 낮다.
- **언제 사용할까?**
  - 이미 Redis 인프라가 있고 별도로 Kafka 클러스터를 운영할 이유가 없는 가벼운 워크로드라면 Stream이 낫다. 
  - 대용량 이벤트 스트리밍, 다수의 컨슈머 그룹, 장기 보존이 필요하면 Kafka가 맞다.
  - Pub/Sub은 이 셋 중 가장 가볍지만, 메시지를 저장하지 않는다는 특성 때문에 이벤트 로그나 재처리가 필요한 용도로는 못 쓴다. 
    - "지금 연결된 사람에게만 전달되면 충분한" 실시간 팬아웃에 적합하다.

## 실시간 전달과 Redis Pub/Sub (폴링 / SSE / 웹소켓)
### 폴링 (Polling)
- 클라이언트가 주기적으로 서버에 물어보는 방식이다.
- 구현은 가장 단순하지만, 물어보는 주기만큼 지연이 생기고 불필요한 요청으로 서버 부하가 늘어난다.

### SSE (Server-Sent Events)
- 서버에서 클라이언트로 단방향 스트림을 여는 방식이다.
- 브라우저의 `EventSource`가 연결 끊김을 감지하면 자동으로 재연결해준다.

### 웹소켓 (WebSocket)
- 클라이언트와 서버가 양방향으로 통신할 수 있다.
- SSE보다 무겁고 구현도 복잡하다(연결 유지, 하트비트 등). 서버에서 클라이언트로만 흐르면 되는 경우엔 오버스펙이다.

### Pub/Sub이 왜 필요한가
- SSE든 웹소켓이든, 연결은 결국 특정 WAS 인스턴스가 붙잡고 있다. 인스턴스를 여러 대로 늘리면, 어떤 클라이언트가 어느 인스턴스에 연결돼 있는지 다른 인스턴스는 알 방법이 없다.
- 그래서 이벤트가 발생하면 먼저 Redis Pub/Sub으로 모든 인스턴스에 방송(브로드캐스트)한다. 각 인스턴스는 그 방송을 받고 나서, 자기 자신에게 실제로 연결된 클라이언트가 있으면 그 연결로 릴레이한다.
- 결과적으로 클라이언트가 어느 인스턴스에 붙어 있든 상관없이 이벤트를 받을 수 있게 된다. 폴링은 이런 팬아웃 인프라 없이 매번 최신 값을 다시 조회하면 되니 구조는 단순하지만, 그만큼 실시간성과 서버 부하를 맞바꾼 것이다.

# 4. 주간 프롬프트 회고
### 1. 내가 최종 선택한 가장 잘 작성했다고 생각하는 프롬프트
원본 프롬프트:
```text
배차CAS 문서에 대해 질문 있어. 

1. UPDATE가 실패한 이유를 정확히 반영하는 이유
  - "이 재조회는 앞의 조건부 UPDATE가 이미 그 행을 건드리고 간 바로 다음에 실행됩니다. 그래서 여기서 보는 값은 방금 그 UPDATE가 실패한 이유를 정확히 반영합니다." 고 하는데, 그 이유는 조건부 UPDATE가 잡은 락이 아직 @Transactional에 의해 유지되고 있기 때문이야? 
  - deliveryOrderRepository.findById 자체는 단순 SELECT인 것 같은데, 그러면 트랜잭션 시작 시점의 스냅샷을 보는거 아니야? 
  - 'UPDATE가 실패한 이유를 어떻게 정확히 반영한다는건지'에 대한 설명이 부족해.
2. uk_delivery_active_rider UNIQUE 제약
  - uk_delivery_active_rider UNIQUE 제약이 필요한 이유가, 결국 한 라이더가 두 개의 주문을 동시에 잡지 못하게 막는다는거잖아. 
  - 만약 이게 없으면, 한 라이더가 주문 A와 주문 B를 동시에 잡을 수 있게 되는거라고? 
  - 어떤 주문이 먼저 왔든, 먼저 온 주문에 의해 해당 라이더가 BUSY 상태로 변하기 때문에 늦게 온 주문은 받지 못할텐데 어떻게 가능하다는거야? 
  - 내가 상황을 잘못 이해한 건가? 조건부 UPDATE만으로 못 잡는 사각지대가 어딨는지 모르겠어. 
  - 즉, 9부에서 말하는 "한 라이더 두 주문" 자체가 어차피 라이더의 조건부 UPDATE에서 막힐텐데 앞단에서부터 막는게 왜 사각지대를 잡는다는건지 모르겠다는거지.
3. USING INDEX와 같은 방언을 사용하지 않음에도, 네이티브 쿼리를 사용한 이유가 뭐야?
```

**선택한 이유:**
- 단순히 "문서 내용이 이해되지 않는다"고 묻는 대신, 내가 가진 기술적 지식(트랜잭션 스냅샷, 조건부 UPDATE 등)을 바탕으로 논리적 모순점과 가설을 구체적으로 제시했기 때문이다.
- AI가 일반적인 개념 설명을 나열하는 것을 방지하고, 내가 헷갈리는 부분을 정확히 타겟팅하여 설명하도록 유도했다.
  - DB 락(Lock), 트랜잭션 격리 수준(MVCC), 동시성 제어의 사각지대(Race Condition) 등

### 2. 원본 프롬프트 구조 분석
- **문제 상황:**
  - 배차 CAS(Compare-And-Set) 관련 문서를 학습하던 중, 내가 이해하고 있는 바와 문서의 설명 간에 논리적 충돌이 발생한 상황이다.
    - DB 트랜잭션의 읽기 일관성과 조건부 업데이트, UNIQUE 제약 조건의 필요성 등
- **원하는 결과를 어떻게 요구했는가:**
  - 해결해야 할 의문점을 3가지로 넘버링하여 제시했다. 
  - 각 질문마다 내가 이해한 논리적 전개 과정을 먼저 서술하고, 내 논리 중 어느 부분이 잘못되었는지(어떤 사각지대가 존재하는지, 왜 특정 쿼리 방식을 택했는지) 정확히 짚어달라고 요구했다.
- **필요한 맥락이 포함되어 있는가:**
  - @Transactional로 인한 락 유지 여부, findById의 스냅샷 읽기 특성, 라이더의 상태(BUSY) 전이 등 Spring Data JPA 및 데이터베이스 동시성 제어 환경과 관련된 깊이 있는 기술적 맥락이 잘 포함되어 있다.
  - 또한 서두를 '배차CAS 문서에 대해 질문 있어.'로 시작하면서, 관련 문서를 다루는 서브 에이전트가 동작하도록 설정하였다.
- **판단 기준이나 제약 조건이 있는가:**
  - 2번 질문에서 "어차피 조건부 UPDATE에서 막힐 텐데"라는 전제를 설정했다. 
  - 이를 통해 AI가 UNIQUE 제약 조건의 일반적인 용도를 설명하는 데 그치지 않고, '조건부 UPDATE만으로 방어할 수 없는 정확한 엣지 케이스(사각지대)'를 증명하도록 답변의 기준을 제약했다.
- **출력 방식이 명확한가:**
  - 특정한 포맷(표 등)을 강제하지는 않았다. 
  - 하지만 질문을 3가지 항목으로 구조화하여, AI 역시 1, 2, 3번에 맞춰 논리적으로 분리된 형태의 답변을 출력하도록 자연스럽게 유도했다.
- **나의 가설, 우려, 의도가 드러나는가:**
  - 1번에서는 '단순 SELECT이므로 트랜잭션 시작 시점의 스냅샷을 읽어 최신 실패 이유를 반영하지 못할 것'이라는 나의 가설이 뚜렷하게 드러난다. 
  - 2번에서 역시 '상태 변경 로직만으로 동시 수락을 막을 수 있다'는 나의 가설이 명확하게 제시되어 있다.

### 3. AI에게 프롬프트를 개선 요청하기
- 프롬프트 개선안
```text
배차 CAS(Compare And Set) 문서 내용 중 이해되지 않는 3가지 항목에 대해 질문이 있어. 내가 궁금해하는 포인트들을 읽고, 논리적으로 잘못된 부분을 구체적인 예시나 DB 메커니즘을 바탕으로 바로잡아 줘.

1. UPDATE 실패 이유 반영 매커니즘
- 궁금한 점: deliveryOrderRepository.findById는 단순 SELECT이므로 트랜잭션 시작 시점의 스냅샷을 읽을 텐데, 어떻게 방금 실패한 조건부 UPDATE의 결과를 정확히 반영한다는 것인지 이해가 안 돼.
- 요청: MySQL의 MVCC(다중 버전 동시성 제어)나 트랜잭션 격리 수준과 연관지어, 스냅샷 읽기가 아닌 최신 상태를 읽어올 수 있는 이유를 설명해 줘.

2. uk_delivery_active_rider UNIQUE 제약의 진짜 필요성 (사각지대)
- 궁금한 점: 한 라이더가 두 주문을 동시에 잡으려 해도, 먼저 도착한 요청이 라이더를 BUSY로 만들면 뒤늦은 요청은 조건부 UPDATE에서 막힐 텐데 왜 굳이 UNIQUE 제약이 앞단에 필요한지 모르겠어.
- 요청: 조건부 UPDATE만으로는 절대 방어할 수 없는 정확한 엣지 케이스(Race Condition)를 시간 흐름에 따른 시나리오(예: 트랜잭션 A와 B의 교차 실행)로 증명해 줘.

3. 네이티브 쿼리 사용 이유
- 궁금한 점: USING INDEX 같은 DB 방언을 쓰지 않는데도 네이티브 쿼리를 쓴 이유.
- 요청: JPQL이나 QueryDSL로 처리하지 않고 굳이 네이티브 쿼리를 쓴 이유에 대해 알려 줘.
```

### 4. AI가 개선한 프롬프트 분석
- **더 명확해진 목표 및 출력 형식:**
  - 각 질문별로 '궁금한 점'과 '요청'을 명시적으로 분리하여, AI로 하여금 '내가 어느 포인트에서 의문을 가졌는지' 먼저 정확히 파악하고 그에 맞춘 검증을 수행하도록 구조화했다. 
  - 단순히 설명해 달라는 요청을 넘어, '시간 흐름에 따른 시나리오', 'MVCC와 연관지어' 등 구체적인 출력 형태를 지정했다.
- **추가된 제약 조건:**
  - '구체적인 예시나 DB 메커니즘을 바탕으로 바로잡아 줘'라는 조건을 추가하여, 추상적인 겉핥기식 답변이 아닌 철저히 DB 동작 원리 기반의 답변을 하도록 강제했다.
- **구체적 판단 기준 제시:**
  - 1번 질문에서는 'MVCC나 트랜잭션 격리 수준'을, 2번 질문에서는 '조건부 UPDATE만으로 방어할 수 없는 시간 흐름에 따른 엣지 케이스'를 판단 기준으로 제시하여 답변의 해상도를 높였다.
- **답변 품질이 좋아질 것으로 예상되는 이유:**
  - 단순히 의문을 제기하는 것에 그치지 않고, AI가 답변의 근거로 삼아야 할 기술적 키워드(MVCC, Race Condition 등)를 미리 제시했기 때문이다. 
  - 내가 가진 의문점(궁금한 점)을 해소하는 과정에서 시나리오 기반의 증명을 요구했으므로, 복잡한 동시성 제어 상황을 훨씬 직관적이고 정확하게 검증받을 수 있을 것이다.
