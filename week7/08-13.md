## 작업 과정에서 어려웠던 점 & 배운 점
### 프론트엔드 연동 과정
API만 구현할 때는 몰랐는데, 프론트엔드와 연동해 보니 누락된 부분이 많았다.

어제 발견한 '콜 목록 조회 시 라이더가 위치 정보를 넘기지 않는 문제'를 해결하는 과정에서, 두 가지 문제가 추가적으로 발견되었다.
1. API는 페이지네이션까지 고려하여 구현되었으나, 정작 프론트엔드에서 페이지네이션 기능을 활용하지 않고 있었다. 
   - 즉, 다음 페이지를 받아올 방법이 없었다.
2. API는 요금/배송거리 필터링 및 정렬 기준/방향 설정 기능까지 고려하여 구현되었으나, 정작 프론트엔드에서 이를 활용하지 않고 있었다.
   - 현재는 물품/픽업거리 필터링만 지원하고, 정렬 또한 픽업거리 오름차순으로만 가능한 상태였다.

공통적으로 API는 있는데 프론트엔드에서 고려하지 못해 발생한 문제였다. 구현 당시에 미처 생각하지 못한 이유가 뭘까?

API를 구현하는 과정에서도 느끼긴 했지만, 결국 기획과 와이어프레임이 탄탄하지 못했기 때문이라고 생각한다.

중간에 요구사항 변경이 발생하는 프로젝트가 아니었기 때문에, 초기에 기획과 와이어프레임을 확실히 잡고 갔다면 가장 좋았을 것이다.

하다못해 기획-이슈 내용 불일치, 와이어프레임 내 화면 누락 등 문제가 발생했더라도, 이를 체크리스트 형태로 기록해 두었다가 관련 기능 구현 시점에 고려했다면, 오늘과 같은 문제는 발생하지 않았을 것이다.

초기 설계(기획, 와이어프레임 등)뿐만 아니라, 사후 대처의 중요성을 느낄 수 있었던 하루였다.

# 2. 종합 회고
## 잘한 점
### UX를 고려한 구현
- 콜 목록 조회 기능에서는 라이더의 현재 위치 정보를 받아와야 한다. 만약 받아오지 못할 경우, 일정 반경이 아니라 생성 시점을 기준으로 콜 목록을 조회하게 된다.
- 그런데 위치 정보를 받아오도록 수정했음에도, 생성 시점을 기준으로 콜 목록을 조회하는 문제를 마주할 수 있었다.
- 원인은 권한 문제였다. 브라우저/앱 권한 뿐만 아니라, 시스템 설정에서도 위치 권한을 허용해야 했던 것이다.
- 하지만 브라우저/앱 화면에는 관련 내용이 아예 없었기 때문에, 단순히 앱을 사용하는 라이더의 입장에서는 이 사실을 알기 어렵겠다고 생각했다.
- 그래서 콜 목록 조회 화면에 해당 사실을 알리는 간단한 배너를 추가하였는데, 이러한 'UX를 고려한 구현'이 좋았던 점이라고 생각한다.

## 아쉬웠던 점
### 계획했던 학습 분량을 달성하지 못했다
- 학습 초기 범위는 잘 설정했으나, 모르는 내용을 너무 깊게 타고 들어가다 보니 본래 학습하려던 내용에서 많이 벗어나게 되었다.
- 나아가 중간중간 회의나 버그 수정 등 다른 업무도 처리해야 했기 때문에, 계획했던 학습 분량을 절반도 채우지 못했다.

## 개선할 점
### 한 번에 너무 많은 것을 알려고 하지 말자
- 모르는 내용은 원 주제를 이해하는 데 지장이 없을 정도로만 학습하고 넘어가자.
- 어차피 중요한 내용이라면 반복적으로 나올 테니, 그때마다 조금씩 학습 깊이를 늘려가면 된다.

# 3. 학습 내용
## 인덱스 설계 기초
인덱스는 무조건 많을수록 좋은 게 아니다. 읽기 성능과 쓰기 비용 사이에 균형이 있다.

### 종류
- **단일 인덱스:** 컬럼 하나에 인덱스를 거는 가장 단순한 형태다.
  ```sql
  CREATE INDEX idx_trades_status ON trades(status);
  CREATE INDEX idx_trades_price ON trades(price);
  ```
- **복합 인덱스:** 여러 컬럼을 묶어서 하나의 인덱스로 만드는 형태다.
  ```sql
  CREATE INDEX idx_trades_status_created_at ON trades(status, created_at);
  ```

### leftmost prefix rule
복합 인덱스는 앞쪽 컬럼 순서가 중요하다. 앞쪽 컬럼을 조건에 안 쓰면 인덱스를 제대로 활용하지 못할 수 있다.

- `(status, created_at)` 인덱스는 status 조건에 유리하다.
  - created_at만 단독으로 쓰면 기대와 다르게 인덱스를 못 탈 수 있다(맨 앞 컬럼인 status가 조건에 없어서).
- status와 created_at을 함께 쓰면 더 좋다.

### 커버링 인덱스
조회하는 컬럼이 인덱스에 다 들어 있으면, 테이블 레코드까지 안 가고 인덱스만으로 조회를 끝낼 수 있다.
```sql
EXPLAIN
SELECT seller_id, created_at
FROM trades
WHERE status = 'DONE'
ORDER BY created_at DESC
LIMIT 20;
```
- 위 쿼리는 인덱스 설계에 따라 훨씬 가벼워질 수 있다. 
- status, created_at, seller_id를 함께 담은 복합 인덱스를 만들면 Extra에 Using index가 뜨면서 커버링 인덱스로 처리된다.

## SARGable 쿼리
인덱스를 잘 타는 조건을 SARGable하다고 부른다. 실무에서는 다음 실수를 자주 본다.
- **컬럼에 함수를 씌우는 경우:** 
  - `WHERE DATE(created_at) = '2026-08-12'` 처럼 컬럼을 함수로 감싸면 인덱스를 못 탄다.
- **컬럼과 다른 타입을 비교하는 경우:** 
  - `WHERE seller_id = '1001'` 처럼 숫자 컬럼을 문자열과 비교하면 암묵적 형변환이 일어나 인덱스를 못 탄다.
- **앞에 와일드카드가 붙는 경우:** 
  - `WHERE item_name LIKE '%phone'` 처럼 LIKE 패턴 앞에 `%`가 붙으면 인덱스를 못 탄다.

바꾸는 방법은 각각 이렇다.
```sql
-- 함수 대신 범위 조건으로
WHERE created_at >= '2026-08-12 00:00:00'
  AND created_at <  '2026-08-13 00:00:00'

-- 타입을 맞춘다
WHERE seller_id = 1001
```

핵심은 세 가지다.
- 컬럼 가공을 줄인다.
- 비교 타입을 맞춘다.
- 범위 조건으로 바꾸면 인덱스 활용 가능성이 높아진다.

## JOIN 튜닝과 optimizer_trace
### JOIN 튜닝
조인은 보통 작은 집합에서 시작하는 게 유리하지만, 실제로는 데이터 분포와 인덱스에 따라 달라진다. 체크할 포인트는 이렇다.
- 조인 키에 인덱스가 있는가
- 필터가 먼저 적용되는가
- 불필요하게 큰 중간 결과가 생기지 않는가
- LEFT JOIN이 정말 필요한가

### optimizer_trace
옵티마이저가 왜 이 계획을 골랐는지 끝까지 파보고 싶을 때 쓴다.
- 계획을 왜 이렇게 골랐는지 궁금할 때
- 인덱스를 추가했는데도 선택이 안 될 때
- 조인 순서가 어떻게 결정됐는지 보고 싶을 때

다만 출력이 너무 길다. 처음부터 이걸 읽기보다는 `EXPLAIN`으로 1차 판단부터 하고, 그래도 이유가 안 보일 때만 들어가는 게 낫다.

## 쿼리 튜닝
### 체크리스트
쿼리를 튜닝할 때 아래 순서로 점검하면 된다.
- 쿼리 목적이 무엇인지 먼저 정리한다.
- 실제 실행 시간을 재본다.
- EXPLAIN으로 읽는 테이블 순서를 본다.
- key가 적절한지 본다.
- rows 추정이 이상하지 않은지 본다.
- Extra에 불필요한 Using filesort, Using temporary가 있는지 본다.
- 인덱스가 쿼리 패턴과 맞는지 본다.
- 통계를 갱신했는지 확인한다.
- SARGable하게 바꿀 수 있는지 본다.
- 인덱스보다 쿼리 재작성으로 더 단순하게 해결할 수 있는지 본다.

### 자주 하는 실수
- EXPLAIN만 보고 실제 시간을 확인하지 않는다.
- 인덱스를 만들고 ANALYZE TABLE을 잊는다.
- 복합 인덱스 컬럼 순서를 대충 정한다.
- 함수와 형변환 때문에 인덱스를 못 타게 만든다.
- LEFT JOIN이 꼭 필요한지 검토하지 않는다.
- 결과가 빨라졌는지보다 인덱스가 생겼는지만 본다.

### 요약
마무리하면, 쿼리 튜닝은 다음 순서로 접근한다.
- 느린 쿼리를 찾는다.
- EXPLAIN으로 계획을 본다.
- EXPLAIN ANALYZE로 실제를 본다.
- 인덱스와 통계를 점검한다.
- 필요하면 쿼리를 재작성한다.
- 다시 측정한다.

핵심은 추측이 아니라 측정이다.
