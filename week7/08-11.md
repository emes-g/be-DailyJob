## 작업 과정에서 어려웠던 점 & 배운 점
### 간단하게 생각하자
원격 환경에서의 테스트를 어떻게 수행해야 할지가 막막했다.

로컬 환경에서는 단위/통합/E2E 테스트를 통해 정합성을 검증했고, 부하 테스트를 통해 서버의 강건성을 확인할 수 있었다. 작업 회고에서 언급했던 '배차 수락 과정에서 데드락이 발생하는 문제' 역시, 로컬 부하 테스트를 통해 발견한 문제였다.

원격 환경에서도 동일하게 테스트를 수행하면 되는 걸까 싶었지만, 몇 가지 다른 점이 있었다. 가령,
- 인스턴스를 공유한다. 즉, 로컬과 달리 원격 환경에서의 테스트는 모든 팀원들에게 영향이 갔다.
- 성능이 다르다. 정합성 테스트는 차치하더라도, 부하 테스트는 새롭게 진행해야 했다. 
- 숙련도가 다르다. 로컬 환경에서는 내가 테스트하고 싶은 부분만 테스트하는 것이 어렵지 않은데, 원격 환경에서는 어떻게 수행할 수 있을까에 대한 막막함이 있었다.
- ...

위와 같은 요인들이 테스트를 지연시켰고, 결국 원격 환경에서의 테스트를 진행하지 못한 채 퇴근하게 되었다.

퇴근길에 '내일은 이 문제를 어떻게 해결해야 할까'에 대해 계속 고민했다. 내일이 된다고, 자연스럽게 해결 방법이 떠오르는 것은 아니니 말이다.

그러다 문득 오늘의 상황이 지난 회고에서 겪었던 상황과 유사하다는 생각이 들었다. '복잡한 작업부터 수행하려다 보니, 작업에 진척이 별로 없었다'는 내용 말이다.

그래서 단순하게, 할 수 있는 것부터 해보자고 생각하게 되었다.
1. 로컬 환경에서 구현할 기능부터 확정하기
2. 테스트는 차치하고, 일단 원격 환경에서 모든 기능이 정상적으로 동작하는지부터 확인하기
3. 로컬 환경에서 정상적으로 테스트된 항목 중, 원격 환경에서 추가로 테스트해야 할 항목들 찾아내기

명료하지는 않더라도, 작업 개요를 정리하고 나니 마음이 한결 가벼워졌다.

그 덕분일까, '정합성 검증을 위해 작성해 두었던 단위/통합/E2E 테스트 코드는 그대로 활용하고, 부하 테스트만 추가적으로 고민해보면 되겠다'는 생각으로도 이어질 수 있었다.  

물론 이 방법이 정답이 아닐 수 있다. 하지만 정답을 모른다고 해서, 아무것도 수행하지 않으면 아무것도 바뀌지 않는다.

잘 모르겠으면, 일단 간단한 것부터 생각하고 실행해보는 자세가 중요하다. 실패를 너무 두려워하지 말자.

# 2. 종합 회고
## 잘한 점
### AI를 비판적으로 사용한 것
- AI를 통해 코드를 생성하는 것은 좋지만, 해당 코드를 전적으로 신뢰해서는 안 된다.
- 실제로 오늘 AI와 함께 '주문 취소 기능 개선' 코드를 작성했는데, '주문 생성 즉시 주문이 취소되는 문제'를 발견할 수 있었다.
- 서버에서 클라이언트로 주문 생성 시각을 넘길 때 UTC라는 정보를 제공하지 않아, 클라이언트 단에서 바로 만료 판정을 내려버렸기 때문이다.
- 만약 AI가 구현해 준 코드를 전적으로 신뢰했다면, 이러한 문제는 발견하지 못했을 것이다.
- 앞으로도 AI를 비판적으로 사용하는 태도를 유지하려고 한다.

## 아쉬웠던 점
### 뭘 해야 할지에 대한 막막함이 있었다
- 대략적인 기능도 구현되었고 담당 파트에 대한 테스트도 진행되고 있어서, 개인적으로 뭘 해야 할지에 대한 막막함이 있었다.
- 그래서 중간에 시간을 효율적으로 활용하지 못한 구간이 발생했다.

## 개선할 점
### 해야 할 일부터 쳐내자
- 개인적으로 뭘 해야 할지 모르겠다면, 팀 차원에서 해야 할 일부터 하나씩 쳐내도록 하자.
- 기획서, 리드미, 위키 등 수행해야 할 문서화 작업이 많다.
- 어차피 미루면 나중에 해야 하는데, 뭘 해야 할지 모르겠을 때 미리 해 둔다면 추후 다른 작업에 할애할 시간을 확보할 수 있다.

# 3. 학습 내용
## TransactionTemplate
- `@Transactional`은 AOP 프록시 기반이라 몇 가지 한계가 있다. 같은 클래스 안에서 메서드를 직접 호출하면(self invocation) 프록시를 안 거치니까 적용이 안 되고, 메서드 전체가 아니라 그 중 일부 블록만 트랜잭션으로 묶고 싶을 때도 애매하다.
- `TransactionTemplate`은 이런 걸 프로그래밍 방식으로 직접 제어하는 도구다. `execute(callback)`에 람다로 로직을 넘기면 그 블록 자체가 트랜잭션 경계가 된다.
```java
transactionTemplate.execute(status -> {
    // 이 블록만 트랜잭션 안에서 실행됨
    return repository.save(entity);
});
```
- 전파 방식(Propagation), 격리 수준(Isolation), 읽기 전용 여부(readOnly) 같은 것도 인스턴스에 설정해서 쓸 수 있다(`setPropagationBehavior`, `setIsolationLevel` 등).
- 주로 쓰는 경우는 메서드 안에서 트랜잭션이 필요한 부분과 필요 없는 부분(외부 API 호출, 파일 IO 같은 것)이 섞여 있을 때다.
- 외부 호출까지 트랜잭션에 묶이면 DB 커넥션을 그만큼 오래 붙잡고 있게 되니, DB 작업만 `TransactionTemplate`으로 좁게 감싸는 식으로 쓴다.

## Presigned URL
### 개념
- S3 같은 오브젝트 스토리지에서, 클라이언트가 직접 AWS 자격증명 없이도 특정 파일에 제한된 시간 동안 접근(업로드나 다운로드)할 수 있게 서버가 미리 서명을 붙여 발급해주는 URL이다.

### 흐름
- 서버가 자기 IAM 자격증명으로 URL에 서명을 만들어서 클라이언트에게 내려주면, 클라이언트는 그 URL로 S3에 직접 PUT이나 GET 요청을 보낸다.
- 즉 파일 자체는 서버를 거치지 않고 클라이언트와 S3 사이에서 바로 오간다.

### 특징
- 이렇게 하면 서버가 파일 바이트를 직접 다 처리하지 않아도 되니 서버 부하와 네트워크 비용이 줄어든다. 특히 큰 파일 업로드에 유리하다.
- 보통 만료 시간(TTL)을 짧게 잡아서, URL이 어딘가에 노출돼도 일정 시간 뒤엔 못 쓰게 만든다.
- 업로드용과 다운로드용 URL을 따로 발급하는 게 일반적이다.

## UTC / KST
### 개념
- UTC(협정 세계시)는 시간대 기준이 되는 표준 시각이다. KST(한국 표준시)는 UTC보다 9시간 빠르다(UTC+9).

### 특징
- 보통 서버나 DB 내부에는 UTC로 통일해서 저장하고, 사용자에게 보여줄 때만 KST로 변환하는 패턴을 쓴다.
- 처음부터 KST로 저장하면 서버 리전이 바뀌거나 여러 시간대 사용자를 다뤄야 할 때 계산이 꼬이기 쉽다.

### 종류
- Java에서는 이런 구분이 중요하다.
  - `Instant`: 시간대 개념 없이 UTC 기준의 한 시점 그 자체
  - `ZonedDateTime`, `OffsetDateTime`: 시간대(오프셋) 정보를 포함
  - `LocalDateTime`: 시간대 정보가 전혀 없음, 어느 시간대인지 코드만 봐서는 알 수 없어서 조심해서 써야 함
- MySQL도 컬럼 타입에 따라 다르게 동작한다.
  - `TIMESTAMP`: 내부적으로 UTC로 저장하고 커넥션의 `time_zone` 설정에 맞춰 변환해서 보여줌
  - `DATETIME`: 시간대 정보 없이 입력한 그대로 저장
- 어떤 타입을 쓰는지에 따라 동작이 완전히 달라지니 확인이 필요하다.
