# 1. 작업 회고
## 당일 수행 작업 목록
### 메인 프로젝트
- [시스템] 주문 취소 기능 개선
- 주문 상태 전달 방식 논의
- 프론트엔드 동작 환경 구축 (안드로이드 스튜디오 포함)
- 데모 부스
- Redis Pub/Sub, SSE 학습

### 조별 활동
- 스쿼드 세션
- 그룹 회고

### 수업
- 프로젝트 피드백

## 작업 과정에서 어려웠던 점 & 배운 점
### 다른 프로젝트에서 배우기
한 주를 마무리하는 금요일이 되었다. 금요일에는 데모 부스, 스쿼드 세션, 주간 수업 그리고 그룹 회고까지 진행되는 만큼, 개발에 쏟을 수 있는 시간은 거의 없다.

특히 오늘은 해커톤 조 편성과 프로젝트 발표 순서 결정으로 인해, 분위기가 한 층 더 어수선해진 것도 한 몫 했다.

그럼 금요일은 어떻게 보내야 할까?

답은 간단하다. 우리 프로젝트에 쏟을 시간은 부족하지만, 그만큼 다른 프로젝트를 관찰할 시간은 많다.

그러니 다른 프로젝트를 통해, 내가 생각치 못한 부분들에 대한 인사이트를 얻어 오는 것에 집중하면 된다. 가령,
- 특정 기능 개발 과정에서 어떤 방안들을 고려했고, 개중에 선택된 방안과 이유는 무엇인지
- 프로젝트 진행 과정에서 개발 외적으로 겪는 어려움은 없었는지
- 남은 기간에는 어떤 작업을 수행할 생각인지, 시간 배분은 어떻게 할 생각인지
- ...

데모 부스와 스쿼드 세션을 진행하면서 놀랐던 건, 주제가 다르더라도 배울 점은 정말 많다는 점이었다.

실제로 같은 주제를 하는 팀이 한 팀밖에 없어서 '주어진 시간을 유효하게 쓸 수 있을까' 걱정했는데, 걱정이 무색할 만큼 많은 인사이트를 얻을 수 있었다.

매주 다른 팀의 프로젝트 진행 경과를 살펴볼 수 있는 것은, 정말 유익하다고 생각한다.

단순히 기술적인 호기심을 해결하는 것을 넘어, 현재 우리 팀이 놓치고 있는 부분에 대해서도 돌아볼 수 있기 때문이다.

데모 부스와 스쿼드 세션도 어느덧 한 번 밖에 남지 않았다.

다른 프로젝트를 여유롭게 볼 수 있는 마지막 기회인 만큼, 어떻게 하면 이 시간을 최대한으로 활용할 수 있을지 고민해 보자.

# 3. 학습 내용
## 테스트
### 단위 테스트 (Unit Test)
- 가장 작은 단위, 보통 하나의 클래스나 메서드를 독립적으로 검증하는 테스트다.
- DB, Redis, 외부 API 같은 의존성은 실제로 붙지 않고 Mock이나 Fake로 대체한다. 스프링 컨텍스트도 띄우지 않는다. 그래서 실행이 아주 빠르고, 로직 자체(분기, 계산, 예외 조건)만 콕 집어 검증하기에 좋다.
- JUnit과 AssertJ로 작성한다. "스프링 없이 도는 것"이 단위 테스트와 통합 테스트를 구분하는 핵심 기준이다.

### 통합 테스트 (Integration Test)
- 여러 컴포넌트가 실제로 연결된 상태에서 동작을 검증하는 테스트다. Service, Repository, 실제 DB, 실제 Redis까지 이어붙여서 스프링 컨텍스트를 띄운 채로 돈다(`@SpringBootTest` 등).
- 이 저장소는 인메모리 대체 대신 로컬 Docker DB, 로컬 Docker Redis에 실제로 붙는 방식을 쓴다. Mock으로는 매핑 오류, 락 경쟁, 트랜잭션 커밋 시점 같은 걸 검증하기 어렵기 때문이다.

### E2E 테스트 (End to End Test)
- 실제 사용자 요청과 똑같이 HTTP 계층부터 시작해서 끝까지 흐름 전체를 검증하는 테스트다. 컨트롤러 진입점, 인터셉터, 인증, 실제 DB, 실제 Redis를 전부 거친다.
- API의 실제 계약(상태 코드, 응답 형식, 헤더, 인증 흐름 등)을 검증하는 데 쓴다. 예를 들면 오류 응답이 진짜 원하는 상태 코드로 나가는지, SSE가 여러 인스턴스에서도 제대로 전달되는지 같은 것들이다.
- 가장 느리고 유지비도 크지만, 실제 사용자가 겪는 시나리오와 가장 가까운 테스트다.

### 테스트 피라미드
보통 아래 그림처럼 비중을 둔다.
```
        E2E (적게)
     통합 테스트 (중간)
   단위 테스트 (많이)
```
아래로 갈수록 빠르고 안정적이라 많이 쓰고, 위로 갈수록 느리고 깨지기 쉬워서(flaky) 필요한 만큼만 최소로 둔다.

# 주간 프롬프트 회고
### 1. 내가 최종 선택한 가장 잘 작성했다고 생각하는 프롬프트
원본 프롬프트:
```text
현재 상황을 크게 3가지로 정리해볼 수 있을 것 같아.
1. 주문 생성 이후, 논리적 만료 이전 시점에 취소하는 상황
2. 논리적 만료를 포함한 구간(논리적 만료 전후 상황)
3. 스캐너에 의해 물리적 만료된 상황

우선 1번 같은 경우에는, 명백한 수동 취소이므로 문제가 되는 부분이 없다고 생각해.
다음으로 3번 같은 경우에는, SSE를 통해 서버가 클라이언트에게 '물리적으로 만료되었다(CANCEL)'는 상태를 알릴 수만 있다면 문제가 되는 부분이 없다고 생각해.
마지막으로 2번 같은 경우가 문제인데, 당장 생각나는 해결 방법은 클라이언트 단에 논리적 만료 여부를 판별(주문 생성 시점으로부터 5분 경과했는지)할 수 있는 타이머를 두는 방법이야. 클라이언트가 본인이 '논리적으로 만료되었다'는 사실을 서버에게 알리기만 하면, 서버가 바로 물리적 만료 상태로 전환할 수 있는 거잖아.

혹시 내가 잘못 판단했거나, 누락된 상황이 있을까? 
요약해보면 결국 '수동 취소'는 전혀 문제될 게 없는데, '자동 취소' 기능을 구현하는 과정에서 '간극 문제'가 발생했고 이를 어떻게 해결해야 할지를 고민하는 과정에서 나온 상황들이잖아. 
```

선택한 이유:
- 주문 만료 및 취소라는 복잡한 상태 전이 과정을 시간 흐름에 따라 3가지 시나리오로 명확하게 구조화하여 제시했다. 
- 단순히 문제 해결을 AI에게 떠넘기지 않고, '수동 취소'와 '물리적 만료'는 통제 가능함을 명시해 논의의 초점을 좁혔으며, '간극 문제'에 대해서는 구체적인 해결 방안(클라이언트 타이머)을 제시해 검증을 요청했기 때문이다.

### 2. 원본 프롬프트 구조 분석
- **문제 상황:**
  - 주문에 대한 '자동 취소' 기능을 구현할 때, 도메인 규칙에 의한 논리적 만료(5분 경과) 시점과 실제 시스템/스캐너에 의해 물리적으로 만료 처리가 완료되는 시점 사이에 상태 불일치(간극 문제)가 발생하는 상황이다.
- **원하는 결과를 어떻게 요구했는가:**
  - 본인이 도출한 3가지 상황 분류와 해결 방안(클라이언트 타이머)을 제시한 후, 이 설계에 논리적 결함(잘못 판단한 부분)이나 예외 케이스(누락된 상황)가 있는지 팩트 체크 및 리뷰를 요구했다.
- **필요한 맥락이 포함되어 있는가:**
  - 주문 생성부터 취소/만료까지의 상태 주기(논리적 만료 5분 조건), SSE(Server-Sent Events)를 이용한 서버-클라이언트 간 상태 전달 메커니즘 등 도메인 지식과 기술적 맥락이 구체적으로 포함되어 있다.
- **판단 기준이나 제약 조건이 있는가:**
  - 1번(수동 취소)과 3번(스캐너에 의한 물리적 만료) 상황은 이미 문제가 해결되었다고 선언함으로써, AI가 불필요한 영역을 분석하지 않고 2번(논리적 만료 구간의 간극) 문제에만 집중하도록 논의의 범위를 강력하게 제약했다.
- **출력 방식이 명확한가:**
  - 특정 출력 형태를 요구하지는 않았으나, 마지막 문단에서 문제의 본질('자동 취소의 간극 문제 해결')을 요약하여 제시함으로써 AI의 답변 방향성을 설계 리뷰로 명확히 유도했다.
- **나의 가설, 우려, 의도가 드러나는가:**
  - 클라이언트 단의 타이머(5분)를 트리거로 사용하여 서버에 알리면 상태 불일치(간극) 문제를 즉시 해결할 수 있을 것이라는 명확한 설계 가설이 드러난다. 
  - 동시에 상태를 동기화할 때 미처 파악하지 못한 엣지 케이스가 존재할 수 있다는 우려가 함께 포함되어 있다.

### 3. AI에게 프롬프트를 개선 요청하기
- 프롬프트 개선안
```
현재 주문에 대한 '자동 취소' 기능을 구현하는 과정에서, 도메인 규칙에 의한 논리적 만료 시점(주문 생성 후 5분)과 스캐너에 의한 물리적 만료 시점 간의 '상태 불일치(간극)' 문제를 해결하고자 합니다. 

현재 상황과 해결 방안을 3가지로 정리했습니다.
1. 논리적 만료 이전: 명백한 수동 취소이므로 문제없음.
2. 논리적 만료 전후 구간 (간극 발생): 클라이언트 단에 5분 타이머를 두어, '논리적 만료' 시 클라이언트가 서버에 알리면 서버가 물리적 만료로 즉시 전환하는 방안을 고려 중.
3. 스캐너에 의해 물리적 만료된 이후: SSE를 통해 클라이언트에게 'CANCEL' 상태를 푸시하면 문제없음.

위 내용을 바탕으로 다음 두 가지 항목에 대해 답변해 주세요.
첫째, 2번에서 제안한 '클라이언트 타이머 기반 상태 전환' 방식이 가질 수 있는 기술적 결함(예: 네트워크 지연, 클라이언트 시간 조작 및 백그라운드 전환 등)과 엣지 케이스를 분석해 주세요.
둘째, 이 간극 문제를 해결하기 위해 클라이언트 요청에 의존하지 않고 서버(백엔드) 주도적으로 상태를 보장하거나, 스캐너와의 동시성(Race Condition) 이슈를 방지할 수 있는 더 견고한 아키텍처 대안을 제시해 주세요.
```

### 4. AI가 개선한 프롬프트 분석
- **더 명확해진 목표 및 출력 형식:**
  - 원본 프롬프트에서는 "내가 잘못 판단했거나 누락된 상황이 있을까?"라고 포괄적으로 질문했으나, 개선안에서는 이를 '클라이언트 타이머 방식의 기술적 결함 분석'과 '서버 주도의 안전한 아키텍처 대안 제시'라는 두 가지 명확한 목표로 구조화했다.
- **추가된 제약 조건:**
  - 분석해야 할 결함의 예시(네트워크 지연, 시간 조작, 클라이언트 백그라운드 상태 전환 등)를 프롬프트에 직접 명시하여, AI가 클라이언트 환경의 불확실성을 집중적으로 파헤치도록 분석 범위를 제약했다.
- **구체적 판단 기준 제시:**
  - 대안을 요청할 때 단순히 '다른 방법'을 묻는 것이 아니라, '서버 주도의 상태 보장' 및 '동시성(Race Condition) 이슈 방지'라는 백엔드 엔지니어링 관점의 구체적인 평가 기준을 추가했다.
- **답변 품질이 좋아질 것으로 예상되는 이유:**
  - 원본 프롬프트대로라면 AI가 사용자의 아이디어(클라이언트 타이머)에 동조하여 표면적인 구현 방법론만 설명할 위험이 컸다.
  - 하지만 개선안은 클라이언트를 신뢰할 수 없는(Zero-Trust) 환경으로 가정하고 설계의 허점을 찌르도록 유도했기 때문에, 실제 프로덕션 레벨에서 발생 가능한 문제를 고려한 아키텍처 피드백을 기대할 수 있게 되었다.
