# 1. 작업 회고
## 당일 수행 작업 목록
### 메인 프로젝트

- 주문 상태 전달 방식 논의

- 데모 부스
- Redis Pub/Sub, SSE 학습

### 조별 활동
- 스쿼드 세션
- 그룹 회고

### 수업
- 프로젝트 피드백

## 작업 과정에서 어려웠던 점 & 배운 점
### 다른 프로젝트에서 배우기
한 주를 마무리하는 금요일이 되었다. 금요일에는 데모 부스, 스쿼드 세션, 주간 수업 그리고 그룹 회고까지 진행되는 만큼, 개발에 쏟을 수 있는 시간은 거의 없다.

특히 오늘은 해커톤 조 편성과 프로젝트 발표 순서 결정으로 인해, 분위기가 한 층 더 어수선해진 것도 한 몫 했다.

그럼 금요일은 어떻게 보내야 할까?

답은 간단하다. 우리 프로젝트에 쏟을 시간은 부족하지만, 그만큼 다른 프로젝트를 관찰할 시간은 많다.

그러니 다른 프로젝트를 통해, 내가 생각치 못한 부분들에 대한 인사이트를 얻어 오는 것에 집중하면 된다. 가령,
- 특정 기능 개발 과정에서 어떤 방안들을 고려했고, 개중에 선택된 방안과 이유는 무엇인지
- 프로젝트 진행 과정에서 개발 외적으로 겪는 어려움은 없었는지
- 남은 기간에는 어떤 작업을 수행할 생각인지, 시간 배분은 어떻게 할 생각인지
- ...

데모 부스와 스쿼드 세션을 진행하면서 놀랐던 건, 주제가 다르더라도 배울 점은 정말 많다는 점이었다.

실제로 같은 주제를 하는 팀이 한 팀밖에 없어서 '주어진 시간을 유효하게 쓸 수 있을까' 걱정했는데, 걱정이 무색할 만큼 많은 인사이트를 얻을 수 있었다.

매주 다른 팀의 프로젝트 진행 경과를 살펴볼 수 있는 것은, 정말 유익하다고 생각한다.

단순히 기술적인 호기심을 해결하는 것을 넘어, 현재 우리 팀이 놓치고 있는 부분에 대해서도 돌아볼 수 있기 때문이다.

데모 부스와 스쿼드 세션도 어느덧 한 번 밖에 남지 않았다.

다른 프로젝트를 여유롭게 볼 수 있는 마지막 기회인 만큼, 어떻게 하면 이 시간을 최대한으로 활용할 수 있을지 고민해 보자.

# 2. 종합 회고
## 잘한 점
### 인사이트 기록
- 데모 부스와 스쿼드 세션에서 느꼈던 인사이트들을 간단히 기록해 두었다.
- 지난 회고에서 '기억은 휘발되니까 간단하게나마 기록해 두는 것이 중요하다'고 했었는데, 이를 잘 지킨 것 같아서 좋았다.

## 아쉬웠던 점
### 핵심 기능을 구현하고 나니 느슨해졌다
- 핵심 기능을 대부분 구현하고 나니, 조금 느슨해진 감이 있다.
- 문서화, 성능 테스트, 다른 파트 이해 등 해야 할 일이 많은데, 중간중간 시간을 효율적으로 활용하지 못한 것 같아 아쉽다.

## 개선할 점
### 남은 작업을 명확히 정의하고 실행하자 
- 남은 작업을 명확히 정의하고, 시간을 효율적으로 활용할 수 있도록 하자.

# 3. 학습 내용
## 테스트
### 단위 테스트 (Unit Test)
- 가장 작은 단위, 보통 하나의 클래스나 메서드를 독립적으로 검증하는 테스트다.
- DB, Redis, 외부 API 같은 의존성은 실제로 붙지 않고 Mock이나 Fake로 대체한다. 스프링 컨텍스트도 띄우지 않는다. 그래서 실행이 아주 빠르고, 로직 자체(분기, 계산, 예외 조건)만 콕 집어 검증하기에 좋다.
- JUnit과 AssertJ로 작성한다. "스프링 없이 도는 것"이 단위 테스트와 통합 테스트를 구분하는 핵심 기준이다.

### 통합 테스트 (Integration Test)
- 여러 컴포넌트가 실제로 연결된 상태에서 동작을 검증하는 테스트다. Service, Repository, 실제 DB, 실제 Redis까지 이어붙여서 스프링 컨텍스트를 띄운 채로 돈다(`@SpringBootTest` 등).
- 이 저장소는 인메모리 대체 대신 로컬 Docker DB, 로컬 Docker Redis에 실제로 붙는 방식을 쓴다. Mock으로는 매핑 오류, 락 경쟁, 트랜잭션 커밋 시점 같은 걸 검증하기 어렵기 때문이다.

### E2E 테스트 (End to End Test)
- 실제 사용자 요청과 똑같이 HTTP 계층부터 시작해서 끝까지 흐름 전체를 검증하는 테스트다. 컨트롤러 진입점, 인터셉터, 인증, 실제 DB, 실제 Redis를 전부 거친다.
- API의 실제 계약(상태 코드, 응답 형식, 헤더, 인증 흐름 등)을 검증하는 데 쓴다. 예를 들면 오류 응답이 진짜 원하는 상태 코드로 나가는지, SSE가 여러 인스턴스에서도 제대로 전달되는지 같은 것들이다.
- 가장 느리고 유지비도 크지만, 실제 사용자가 겪는 시나리오와 가장 가까운 테스트다.

### 테스트 피라미드
보통 아래 그림처럼 비중을 둔다.
```
        E2E (적게)
     통합 테스트 (중간)
   단위 테스트 (많이)
```
아래로 갈수록 빠르고 안정적이라 많이 쓰고, 위로 갈수록 느리고 깨지기 쉬워서(flaky) 필요한 만큼만 최소로 둔다.
