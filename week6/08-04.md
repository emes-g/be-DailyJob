### 주문 취소 기능 구현하기
오전에 출근해서 확인했을 때, 이번 스프린트에서 내게 남은 이슈는 3개였다. 
1. 배차 대기 시간이 만료된 주문을 자동으로 취소하는 기능 구현
2. 콜 목록 조회 기능 수정
3. 콜 목록 정렬/필터링 기능 구현

우선순위로 따지면 2번이 가장 중요했지만, 2번과 3번은 팀원 작업이 선행되어야 해결할 수 있는 상황이었기에 1번을 택했고, 이후에도 이처럼 매 순간 적합한 근거를 기반으로 행동하고자 했다.
- 자동 취소 기능을 구현하려고 했는데, 선행되어야 할 '포인트 환급' 기능이 구현되어 있지 않았다. 팀원에게 할당된 작업이었지만, 다음의 이유에서 내가 구현하였다.
  - 이미 '포인트 차감' 기능이 구현되어 있었기 때문에, 담당 파트가 아님에도 개발 공수가 크게 들지 않았다.
  - 포인트 환급 기능 구현을 먼저 요청드릴 수도 있었지만, 해당 팀원이 이번 스프린트에서 맡은 작업이 많아서 부담을 덜어 주고 싶었다.
  - 어려운 작업도 아닌데 구현이 안 되어 있다는 이유만으로 Mocking하는 것은, 이후의 책임 소재도 애매하고 무엇보다 번거로울 것 같았다.
- 자동 취소 기능 설계 과정에서 파악한 건데, 만료된 주문을 자동 취소하는 스케줄러(스캐너)만 구현하게 되면 '간극 문제'를 해결할 수 없었다.
  - 간극 문제란, 논리적 만료 시간(주문 요청 생성 시간 + 5분)과 물리적 만료 시간(논리적 만료 이후 스캐너가 실제로 해당 주문을 자동 취소하기까지의 시간) 사이에서 고객이 포인트를 환급받지 못하고, 주문 또한 새로 생성할 수 없는 문제였다.
  - 이에 '논리적으로 만료됐을 때, 고객이 해당 사실을 인지하고 만료된 주문을 취소시킬 수만 있다면 되지 않을까?' 라는 생각을 하게 되었지만, 현재 상황에서는 고객이 '현재 본인의 주문 요청이 만료되었다'는 사실을 알 수 있는 방법이 없었다.
  - '주문 상세 조회' 페이지에서 해당 사실을 확인할 수 있어야 하는데, 해당 기능이 아직 구현되지 않았을 뿐 아니라 피그마 화면에 페이지조차 존재하지 않았기 때문이다.
  - '자동 취소 기능'을 구현하려 했는데, 어느새 '주문 상세 조회 페이지'를 구상해야 하는 상황에 다다른 것이다.

주문 상세 조회 페이지를 같이 구상하던 팀원이, 이런 말을 했다. "애초에 복잡한 자동 취소 말고, 수동 취소부터 구현했으면 되는거 아니야?"

사실 고려하긴 했었는데, '수동 취소' 역시 팀원에게 할당된 기능이었고, 출근 당시에는 내게 배정된 3개의 기능 구현이 우선이라고 생각하여 자연스레 배제시켰던 것이었다. 

틀린 판단은 아니었다고 생각하는데, 돌이켜 보니 '이번 스프린트의 작업 목록을 조금 더 능동적으로 바라봤으면 좋았을 것 같다'는 아쉬움이 남았다.

앞으로는 단순히 내게 할당된 기능만을 바라보기 보다, 더 넓은 시야로 프로젝트를 바라볼 수 있는 개발자로 성장했으면 좋겠다.

그렇게 될 수 있도록, 평소부터 넓게 생각하는 습관을 가져 보려고 노력하자.

# 3. 학습 내용
## Redis GEO
### 개념
- GEO는 Redis의 Sorted Set(ZSET)을 그대로 활용하는 자료구조다. 별도의 전용 타입이 아니라, 위경도 좌표를 **Geohash 알고리즘으로 52비트 정수로 인코딩**한 뒤 그 값을 ZSET의 score로 저장하는 방식이다.
- 따라서 `ZADD`, `ZRANGE`, `ZREM` 등 일반 ZSET 명령으로도 GEO 데이터를 조작할 수 있고, `TYPE` 명령으로 확인하면 `zset`으로 나온다.
- 각 member는 임의의 문자열(예: `rider:123`)이고, score는 해당 좌표의 Geohash 값이다. 이 score 순서가 공간적으로 가까운 좌표를 가까운 score로 묶어주기 때문에, 반경 검색/거리 계산 같은 지리 연산이 가능해진다.
- 정확도는 지구를 격자로 나눠 표현하는 Geohash 특성상 **비트 수에 비례**하며, Redis는 위경도 각각 26비트씩 52비트 정밀도를 쓴다(위도 ±85.05112878도 범위로 제한되므로 극지방은 표현할 수 없다).

### 명령어
- `GEOADD key longitude latitude member [longitude latitude member ...]`
  - 좌표를 등록/갱신한다. 
  - 내부적으로 `ZADD key geohash-score member`와 동일하게 동작한다.

- `GEOPOS key member [member ...]`
  - 등록된 member의 좌표(경도, 위도)를 반환한다. 
  - Geohash → 좌표로 디코딩하는 과정을 거치므로 원본 좌표와 미세한 오차가 생길 수 있다.

- `GEODIST key member1 member2 [unit]`
  - 두 member 간의 거리를 계산한다. 
  - unit은 m(기본값), km, mi, ft 중 선택한다.

- `GEOSEARCH key FROMMEMBER member | FROMLONLAT lon lat BYRADIUS radius unit | BYBOX width height unit [ASC|DESC] [COUNT count] [WITHCOORD] [WITHDIST] [WITHHASH]`
  - 기준점(등록된 member 또는 임의의 좌표)에서 반경(원) 또는 사각형 범위 안의 member를 검색한다. 
  - 예전 명령어인 `GEORADIUS`를 대체하는 명령이며,` WITHDIST`/`WITHCOORD` 옵션으로 결과에 거리/좌표를 함께 받을 수 있다.

- `GEOSEARCHSTORE destination source FROMMEMBER member | FROMLONLAT lon lat BYRADIUS radius unit ...`
  - `GEOSEARCH`와 동일한 검색을 수행하되 결과를 새로운 key(ZSET)에 저장한다. 
  - 검색 결과를 다시 GEO 연산에 활용하고 싶을 때 쓴다.

- `GEOHASH key member [member ...]`
  - member의 좌표를 표준 Geohash 문자열(11자리 base32)로 반환한다. 
  - geohash.org 같은 외부 서비스와 좌표를 주고받을 때 쓰기 좋다.

- `ZREM key member`
  - GEO 전용 삭제 명령이 따로 없으므로, member를 제거할 때는 일반 ZSET의 ZREM을 사용한다.

### 해석 방식
- score(=Geohash 정수값)는 사람이 직접 읽고 해석할 값이 아니다. `GEOPOS`나 `GEOHASH`처럼 디코딩을 거치는 명령을 통해서만 의미 있는 좌표/문자열로 확인한다.
- 반경 검색 결과의 정확도는 Geohash 셀 경계 특성상 완벽한 원이 아니라 근사치로 이해해야 한다. 경계에 걸친 좌표는 실제 거리와 미세하게 다르게 판정될 수 있다.
- 하나의 key 안에 여러 member를 저장해 "이 GEO 인덱스 전체에서 반경 내 후보를 찾는다"는 식으로 사용하는 것이 기본 패턴이며, member 하나당 key 하나를 따로 만들지 않는다.
- 위경도 인자 순서는 항상 경도(longitude) 먼저, 위도(latitude) 나중이다. 일반적으로 익숙한 "위도, 경도" 표기 순서와 반대이므로 헷갈리지 않도록 주의해서 해석한다.
