## 작업 과정에서 어려웠던 점 & 배운 점
### 간단하게나마 기록하기
개발에 착수한 지 어느덧 일주일이 지났다.

하루하루 지날 때는 몰랐는데, 돌이켜보니 다룬 내용이 정말 많았다.
- 콜 목록/상세 조회, 콜 목록 정렬/필터링, 주문 자동/수동 취소, 포인트 환급 등 여러 기능을 구현하고,
- Redis GEO, Redis Pub/Sub, Bounding Box, 하버사인, SSE 등 여러 개념을 학습했다.

프로젝트에서 다룬 내용만 하더라도 상당한데, 데모 부스, 스쿼드 세션, 프로젝트 멘토링, 백엔드 정규 수업 등 프로젝트 외적 활동도 수차례 진행한 만큼 더더욱 그렇게 느껴진 것 같다.

하지만 다뤘다고 해서 내 지식이 되는 것은 아니다. 실제로 접한 지 일주일이 채 되지 않았음에도, 일부 항목들에 대해서는 온전히 기억하고 있지 못한다.

그러면 어떻게 해야 할까?

사실 기억이 휘발되는 것은 필연적이다. 그렇기 때문에 그날 다뤘던 개념을 내 언어로 변환한 후 기록해 두는 것이 중요하다.

물론 변환이나 기록 중 하나만 수행하더라도 그냥 접하고 넘어가는 것보다는 효율적이지만, 두 작업은 확실한 시너지가 나는 것 같다.

내 언어로 변환하는 과정에서 더 깊이 이해하게 되고, 기록하는 과정에서 더 오래 기억하게 된다.

실제로 오늘 '주문 취소 기능'과 관련한 Discussion을 직접 작성하는 과정에서, 그 효과를 더욱 실감할 수 있었다.

프로젝트 일정상 모든 내용을 깊이 있게 다룰 수는 없겠지만, 간단하게나마 내 언어로 변환하고 기록하는 습관을 들일 수 있도록 노력해 보자.

# 3.학습 내용
## 페이지네이션 (Pagination)
### 공통 개념
- 대량의 결과를 한 번에 다 내려주지 않고, **일정 개수(size)씩 나눠서** 클라이언트에 제공하는 기법이다.
- 구현 방식은 크게 **Offset 기반**과 **Cursor(Keyset) 기반**으로 나뉘며, 둘의 차이는 "몇 번째부터 가져올지"를 **숫자**(위치)로 표현하는지 **마지막으로 본 항목의 값**으로 표현하는지에 있다.

### Offset 기반 페이지네이션
- SQL의 `LIMIT n OFFSET m` (또는 `LIMIT m, n`)을 그대로 쓰는 방식이다.
  ```sql
  SELECT * FROM delivery_order ORDER BY created_at DESC LIMIT 20 OFFSET 40; -- 3페이지
  ```
- Spring Data JPA의 `Pageable`/`Page<T>`(`PageRequest.of(page, size)`)가 기본으로 채택한 방식이다.

**장점**
- 구현이 단순하고, `page` 번호만 있으면 **임의의 페이지로 즉시 점프**할 수 있다(5페이지 → 2페이지 등).
- 전체 개수(`totalElements`)와 총 페이지 수를 함께 보여주는 UI(번호 매기기)에 적합하다.

**단점**
- DB는 OFFSET만큼의 행을 **일단 다 읽고 버린 뒤** 그 다음부터 LIMIT만큼 반환한다. 
  - 즉 OFFSET이 커질수록 스캔량이 늘어 **O(offset + limit)** 비용이 든다 — 뒷페이지로 갈수록 느려진다.
- 조회하는 동안 데이터가 삽입/삭제되면 **행이 밀리면서 중복 또는 누락**이 발생할 수 있다(예: 1페이지를 보는 사이 새 행이 앞에 추가되면, 2페이지에서 이전에 본 행이 다시 보이거나 하나가 빠짐).
- 실시간으로 갱신되는 목록(무한 스크롤, 피드 등)에는 잘 맞지 않는다.

### Cursor 기반 페이지네이션 (Keyset Pagination)
- "몇 번째"가 아니라 **마지막으로 조회한 항목의 정렬 키 값**(cursor)을 기준으로, 그보다 이후/이전 값을 조건절(WHERE)로 걸러 `LIMIT`만 적용하는 방식이다. 
- **OFFSET을 쓰지 않는다.**
  ```sql
  -- created_at 내림차순, 마지막으로 본 항목이 (created_at = X, id = Y)일 때 다음 페이지
  SELECT * FROM delivery_order
  WHERE created_at < :lastCreatedAt
     OR (created_at = :lastCreatedAt AND id < :lastId)
  ORDER BY created_at DESC, id DESC
  LIMIT 20;
  ```
- 정렬 키가 **유일하지 않을 수 있으므로**(같은 `created_at`이 여러 행에 존재), 동률을 깨기 위해 **PK 등 유일한 컬럼을 tie-breaker로 함께** 조건과 정렬에 넣는 복합 커서(composite cursor)가 일반적이다.

**동작 원리 / 성능**
- WHERE 조건이 인덱스의 리프 노드를 바로 찾아가므로, **인덱스가 정렬 키와 일치**하면 앞의 행을 스캔하지 않고 바로 시작 지점부터 `LIMIT`만큼만 읽는다.
  - 뒷페이지로 가도 성능이 거의 일정하다(`O(limit)`에 가깝다).
- Offset 방식과 달리 데이터가 계속 삽입/삭제돼도, "내가 마지막으로 본 값보다 뒤"라는 조건 자체는 변하지 않으므로 **중복/누락이 훨씬 적다.**

**단점 / 트레이드오프**
- **임의 페이지로 점프할 수 없다** — 오직 "다음 페이지"/"이전 페이지"만 자연스럽게 지원한다(양방향을 지원하려면 정렬 방향을 반대로 뒤집은 커서를 따로 계산해야 한다).
- 전체 개수(총 페이지 수)를 구하려면 별도의 `COUNT` 쿼리가 필요하고, 그 자체도 비용이 크다 — 그래서 보통 "총 개수" UI 없이 무한 스크롤/"더 보기" 형태로 쓴다.
- 커서 값(정렬 키 원본)을 그대로 노출하면 내부 구조가 드러나므로, 보통 **Base64 등으로 인코딩**해서 클라이언트에 opaque한 토큰처럼 전달한다.
- 정렬 기준이 여러 개(멀티 컬럼 정렬)이거나 동적으로 바뀌면, 그만큼 커서에 담을 값과 WHERE 조건도 같이 복잡해진다.

**요약 비교**

| | Offset 기반   | Cursor 기반 |
|---|-------------|---|
| 페이지 점프 | 가능          | 불가능(순차 이동만) |
| 대용량/뒷페이지 성능 | 뒤로 갈수록 저하   | 거의 일정 |
| 실시간 삽입/삭제 안전성 | 중복/누락 발생 가능 | 상대적으로 안전 |
| 총 개수/총 페이지 표시 | 쉬움          | 별도 COUNT 필요, 비쌈 |
| 적합한 UI | 번호형 페이지네이션  | 무한 스크롤, "더 보기" |
