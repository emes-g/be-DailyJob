# 3. 학습 내용
## Redis (Remote Dictionary Server)
- **인메모리 (In-Memory) 저장소:** 
  * 데이터를 디스크가 아닌 메모리(RAM)에 저장하여 데이터 접근 속도가 매우 빠르고 지연 시간(Latency)이 낮다.
- **Key-Value 데이터 구조:** 
  - 단순한 String 외에도 Hash, List, Set, Sorted Set 등 다양한 자료구조를 지원하여 복잡한 데이터를 효율적으로 처리할 수 있다.
- **싱글 스레드 (Single Thread):** 
  - 이벤트 루프 기반의 싱글 스레드로 동작한다. 
  - 명령어의 원자적(Atomic) 처리를 보장하여 동시성 문제(Race Condition)를 제어하기 용이하다.
- **영속성 (Persistence) 지원:** 
  - 기본적으로 메모리 기반이지만, 서버 재시작 시 데이터 유실을 방지하기 위해 RDB(스냅샷)와 AOF(로그) 방식으로 디스크에 데이터를 백업할 수 있다.

## Redis Pub/Sub 구조
발행-구독(Publish-Subscribe) 패턴을 구현한 메시징 기능이다. 발행자(Publisher)와 구독자(Subscriber)가 특정 채널(Channel)을 통해 실시간으로 데이터를 주고받는다.
- **Decoupling (완전한 분리):** 
  - 발행자는 구독자가 누구인지 알 필요 없이 채널에 메시지를 전송하고, 구독자는 원하는 채널을 구독하여 메시지를 수신한다.
- **Fire-and-Forget (휘발성):** 
  - 전송된 메시지는 Redis 내부에 저장되지 않는다. 
  - 메시지가 발행되는 순간 해당 채널을 구독 중인 클라이언트가 없다면, 그 메시지는 즉시 소멸한다.
- **At-Most-Once 전송 보장:** 
  - 메시지는 최대 한 번만 전송된다. 
  - 네트워크 단절 등으로 인해 구독자가 메시지를 받지 못하더라도 시스템 차원에서 재전송(Retry)을 지원하지 않는다.

### 분산 아키텍처에서의 활용
메시지의 영속성이 필요 없는 실시간 이벤트 처리에 적합하다.

- 마이크로서비스(MSA) 환경에서의 로컬 캐시 동기화 및 무효화(Invalidation) 이벤트 브로드캐스팅
- 다중 웹소켓(WebSocket) 서버 인스턴스 간의 실시간 채팅 메시지 라우팅
- 시스템 상태 모니터링 및 실시간 알림 시스템

### 도입 시 주의할 점
- 결제나 주문 처리처럼 데이터의 유실이 절대 발생해서는 안 되며, 이벤트의 순서 보장과 재처리 능력이 필수적인 도메인에서는 Apache Kafka와 같은 영속성 기반의 이벤트 브로커를 도입하는 것이 적절하다. 
- 반면, 높은 처리량과 짧은 지연 시간이 요구되는 상황에서는 Redis Pub/Sub이 효율적으로 동작할 수 있다.
